5.1Purpose of STP▾

5.1.1 Redundancy in Layer 2 Switched Networks

Redundancy eliminates single points of failure — if one switch or cable fails, traffic takes an alternate path. This is critical for enterprise network design. However, physical redundancy in a Layer 2 network creates a serious problem: Layer 2 loops.

ProtocolHas Loop Prevention?Mechanism
IPv4 (Layer 3)✅ YesTTL field — decremented at every router, packet dropped at 0
IPv6 (Layer 3)✅ YesHop Limit field — same concept as TTL
Ethernet (Layer 2)❌ NoNo TTL equivalent — frames loop forever without STP
🚨
Layer 2 has no TTL. A frame caught in a Layer 2 loop circulates forever. There is nothing built into Ethernet to stop it. STP was created specifically and exclusively to solve this problem.

5.1.2 Spanning Tree Protocol

STP (Spanning Tree Protocol) is a loop-prevention protocol that allows physical redundancy to exist while logically blocking the ports that would create loops — creating a single active path between any two devices.

  • Standard: IEEE 802.1D (original specification)
  • STP is enabled by default on all Cisco switches
  • STP does NOT remove the redundant physical cables — it just disables them logically
  • When an active link fails, STP detects the change and unblocks a previously blocked port to restore connectivity
  Normal operation (STP active):
  [S1 ROOT]──────────[S2]
      │                │
      └──────[S3]──────┘
              X  ← S3's port to S2 is BLOCKED by STP
  One path only — no loop possible.

  Link S1-S2 fails:
  [S1 ROOT]──×──────[S2]
      │                │
      └──────[S3]──────┘
              ↑ STP unblocks this port → connectivity restored

5.1.4–5.1.5 Issues with Redundant Links — Layer 2 Loops

Without STP, three catastrophic problems occur the instant a loop exists — sometimes within seconds:

Problem 1
MAC Address Table Instability
A broadcast frame enters the loop and circles continuously. Each time it arrives on a different port, the switch updates its MAC table with the source MAC on that port — then the frame circles back and arrives on a different port again. The MAC table thrashes constantly. The switch can never stabilize its table and cannot make reliable forwarding decisions.
Problem 2
Link Saturation
Looping frames consume 100% of available bandwidth on every link in the loop. No useful user traffic can get through — all bandwidth is consumed by looping garbage frames.
Problem 3
High CPU Utilization
Every looping frame is processed by the switch CPU. Frames multiply exponentially with each loop iteration. The CPU becomes overwhelmed and the switch becomes completely unusable — often within just a few seconds.
💡
Both broadcast frames AND unknown unicast frames can loop. Unknown unicast frames (destination MAC not in the table) are flooded out all ports — in a loop this creates duplicate frames arriving at destination devices on top of the broadcast storm.

5.1.6 Broadcast Storm

A broadcast storm is the specific catastrophic result of a Layer 2 loop — an exponentially growing flood of broadcast frames that completely overwhelms the network.

  ARP broadcast enters loop on S1:
  Round 1:  1 frame  → flooded out all ports
  Round 2:  2 frames → each flooded again
  Round 3:  4 frames → each flooded again
  Round 4:  8 frames → ...
  Seconds later: thousands of frames per second
  Result: network completely unusable
  • Network becomes completely unusable within seconds
  • All switches in the loop domain overwhelmed — CPU at 100%
  • End devices also suffer — their NICs receive and must process every looping frame
  • Both broadcasts and unknown unicast frames can loop
⚠️
Even IPv6 is affected — IPv6 never uses Layer 2 broadcasts, but ICMPv6 Neighbor Discovery uses Layer 2 multicast frames. Switches forward multicasts the same way as broadcasts by default — they also loop.

5.1.7 The Spanning Tree Algorithm (STA)

STP is based on the Spanning Tree Algorithm (STA), invented by Radia Perlman in 1985. The STA creates a loop-free topology in three logical steps:

  1. Select a single root bridge — one switch becomes the reference point for the entire topology
  2. Determine least-cost paths — every non-root switch finds the single cheapest path to the root bridge
  3. Block redundant paths — any port that would create a loop is placed in blocking state
💡
Historical note: The IEEE standard and all STP documentation refers to switches as "bridges" — a legacy term from early Ethernet when the devices were called bridges. So "Bridge ID (BID)" simply means "Switch ID" in modern networks. Don't let this terminology trip you up.

5.2STP Operations▾

5.2.1 Steps to a Loop-Free Topology

STP builds a loop-free topology in four sequential steps. Switches communicate using BPDUs (Bridge Protocol Data Units) — sent every 2 seconds by default — which carry all the information needed for every election decision.

Step 1
Elect the Root Bridge
One switch per network becomes the central reference point. All path calculations are made toward the root bridge.
Step 2
Elect Root Ports
Every non-root switch selects exactly one port — the port with the lowest-cost path to the root bridge.
Step 3
Elect Designated Ports
Every segment between two switches gets one designated port — the port with the best path to the root bridge on that segment.
Step 4
Elect Alternate (Blocked) Ports
Everything remaining — not a root port, not a designated port — becomes an alternate port in blocking state. This is the loop prevention.

BID Understanding the Bridge ID (BID)

Before the four steps make sense, you must understand the BID (Bridge ID) — every STP election is decided by comparing BIDs. The BID is a unique identifier every switch carries in every BPDU it sends.

🎯 THE GOLDEN RULE OF STP
The lowest BID wins every STP election. Lower is ALWAYS better in STP.

Lower bridge priority = more likely to be root bridge.
Priority 0 = highest possible preference (always wins priority comparisons).
Priority 4096 beats the default 32768.

Students often think "higher priority = more important" — in STP the opposite is true.

5.2.2 Step 1 — Elect the Root Bridge

The root bridge is the central reference point for the entire spanning tree. Think of it as the trunk of a tree — all other switches are branches reaching toward it.

Root bridge election process — what happens when switches boot 
All switches boot
  ↓
Every switch declares ITSELF the root bridge
  ↓
Every switch sends BPDUs advertising its own BID as the "Root ID"
  ↓
Switches receive each other's BPDUs and compare:
  "Is the received BID lower than mine?"
  YES → accept that switch as the superior root candidate
  NO  → continue advertising myself
  ↓
Exchange continues until all switches agree on ONE root bridge
  ↓
The switch with the LOWEST BID = Root Bridge

Tiebreaker order — evaluated left to right, stop at first difference:

PriorityTiebreakerRuleAdmin Controllable?
1stBridge PriorityLower wins. Default 32768.✅ Yes — set with spanning-tree vlan [id] priority [value]
2ndExtended System IDLower VLAN number wins. Rarely the deciding factor.❌ No — auto-set to VLAN number
3rdMAC AddressLower hexadecimal MAC wins. Pure tiebreaker.❌ No — burned in at factory
🔍 WORKED EXAMPLE — Three Switches, All Default Priority
S1: Priority 32769, MAC 000A.0033.1111
S2: Priority 32769, MAC 000A.0033.2222
S3: Priority 32769, MAC 000A.0033.3333

Step 1: Compare priorities → 32769 = 32769 = 32769 → TIE
Step 2: Compare extended system IDs → all VLAN 1 → TIE
Step 3: Compare MAC addresses in hexadecimal:
000A.0033.1111 < 000A.0033.2222 < 000A.0033.3333

→ S1 wins — S1 becomes the root bridge

Problem: you cannot predict which switch has the lowest factory MAC. Always manually set the priority on the switch you want to be root!
Manually control root bridge placement (best practice) 
! Method 1 — Manually set priority (most control)
S1(config)# spanning-tree vlan 1 priority 4096

! Method 2 — Let IOS auto-set the right priority
S1(config)# spanning-tree vlan 1 root primary
! (IOS sets priority to 24576, or lower if another switch already has <24576)

! Set the backup root bridge
S2(config)# spanning-tree vlan 1 root secondary
! (IOS sets priority to 28672)

5.2.4 Determine the Root Path Cost

Once the root bridge is elected, every non-root switch calculates its internal root path cost — the total accumulated cost of all port costs along the path to the root bridge. The path with the lowest total cost is preferred.

Link SpeedSTP Cost (IEEE 802.1D)RSTP Cost (IEEE 802.1w)
10 Gbps22,000
1 Gbps420,000
100 Mbps19200,000
10 Mbps1002,000,000
🔍 WORKED EXAMPLE — Calculating Root Path Cost
Topology: S1 (root) ── S2 ── S3 (all 100 Mbps links, cost = 19 each)
S1 also connects directly to S3 via a 100 Mbps link.

S3's path options to root bridge S1:
Path 1: S3 → S2 → S1 = cost 19 + 19 = 38
Path 2: S3 → S1 direct = cost 19

Path 2 has the lower cost → S3 uses the direct link as its root port.
Path 1 link on S3 becomes the alternate (blocked) port.
✅
Port costs are configurable. Use spanning-tree cost [value] on an interface to override the default. Administrators use this to steer STP toward a preferred path when automatic cost selection doesn't match the desired topology.

5.2.5 Step 2 — Elect Root Ports

Every non-root switch selects exactly one root port — the single port with the lowest-cost path to the root bridge. Root ports are always in forwarding state. The root bridge itself has no root port — all its ports are designated ports.

What happens when two paths to the root bridge have equal cost? This is where the tiebreaker chain applies — and the most important rule is that tiebreakers always use the sender's information, not the local switch's.

PriorityTiebreakerWhose Info?Rule
1stRoot path costCalculated locallyLowest total cost to root wins outright
2ndSender's BIDNeighboring switchThe neighboring switch with the lower BID — its connected port wins
3rdSender's port priorityNeighboring switchDefault 128. Admin can lower to influence decision.
4thSender's port IDNeighboring switchLower port number wins (Fa0/1 beats Fa0/2)
🔍 WORKED EXAMPLE — Tiebreaker Using Sender's Port ID
Topology: S1 (root bridge) connected to S4 via TWO cables:
  S1 Fa0/1 ──── S4 Fa0/5
  S1 Fa0/2 ──── S4 Fa0/6

Both paths: cost = 19 → TIE (equal cost)
Both from same sender S1: BID is equal → TIE
Both sender port priority = 128: equal → TIE
Sender port ID: Fa0/1 (port 1) < Fa0/2 (port 2) → Fa0/1 WINS

→ S4 Fa0/5 (connected to S1's Fa0/1) becomes the ROOT PORT
→ S4 Fa0/6 (connected to S1's Fa0/2) becomes the ALTERNATE (BLOCKED) PORT

The decision is based on S1's port numbers — not S4's port numbers.
❌
Critical exam trap — tiebreakers use the SENDER's information.
When S4 has two equal-cost paths to root bridge S1, the tiebreaker decision is based on S1's port priority and port ID — NOT S4's. The question "which of S4's ports becomes the root port?" is answered by looking at what S4 is receiving from S1, not at S4's own port numbers.

5.2.6 Step 3 — Elect Designated Ports

Every segment (link between two switches) must have exactly one designated port — the port with the best path to the root bridge on that segment. Designated ports are always in forwarding state.

Three rules that cover every possible scenario:

  1. All ports on the root bridge are designated ports. The root bridge has zero cost to itself — it always wins. All its ports are designated, always.
  2. If one end of a segment is a root port, the other end is the designated port. A root port is already the best path toward root on that switch — the port at the other end of the same cable is automatically designated.
  3. When two non-root switches connect and neither port is a root port: compare root path costs — lower cost wins designated port. If tied, lower BID wins. All ports connecting to end devices (PCs, phones, printers) are always designated — no competition on those segments.
🔍 WORKED EXAMPLE — Rule 3 (BID Tiebreaker)
S2 and S3 are both connected to root bridge S1, and also to each other.
S2 root path cost to S1: 19
S3 root path cost to S1: 19 → TIE

Compare BIDs:
S2 BID: 32769:000A.0033.2222
S3 BID: 32769:000A.0033.3333

S2 has the lower BID →
→ S2's port toward S3 = DESIGNATED PORT (forwarding)
→ S3's port toward S2 = ALTERNATE PORT (blocking)

5.2.7 Step 4 — Elect Alternate (Blocked) Ports

Any port that is not a root port and not a designated port becomes an alternate port in blocking state. This is the loop-prevention step. Blocked ports do not forward user traffic but they DO receive BPDUs so they can monitor the network and react to failures.

Root PortDesignated PortAlternate (Blocked)
Forwards user traffic✅ Yes✅ Yes❌ No
Sends BPDUs✅ Yes✅ Yes❌ No
Receives BPDUs✅ Yes✅ Yes✅ Yes
Available for failover——✅ Yes — immediately
Count per switchOne (non-root only)One per segmentAll remaining ports
✅
Blocked ports receive BPDUs — this is critical. By monitoring BPDUs, a blocked port knows when an active link has failed and can immediately begin transitioning to forwarding to restore connectivity. Without receiving BPDUs, the blocked port would have no way to detect topology changes.

5.2.9 STP Timers and Port States

STP uses three timers to control convergence. All timers are set on the root bridge and communicated to all other switches via BPDUs — do not set timers on non-root switches.

TimerDefaultRangePurpose
Hello Timer2 seconds1–10 secHow often the root bridge sends BPDUs
Forward Delay Timer15 seconds4–30 secTime spent in Listening state AND in Learning state (15 sec each)
Max Age Timer20 seconds6–40 secHow long a switch waits without receiving a BPDU before assuming a topology change

STP Port States — a port transitions through these as STP converges:

Port StateSends BPDUsReceives BPDUsUpdates MAC TableForwards TrafficDuration
Blocking❌ No✅ Yes❌ No❌ NoUp to 20 sec (Max Age)
Listening✅ Yes✅ Yes❌ No❌ No15 sec (Forward Delay)
Learning✅ Yes✅ Yes✅ Yes❌ No15 sec (Forward Delay)
Forwarding✅ Yes✅ Yes✅ Yes✅ YesIndefinite (active)
Disabled❌ No❌ No❌ No❌ NoUntil admin re-enables
STP convergence timeline — port moving from blocked to forwarding 
Port connects (or topology changes)
         ↓
  BLOCKING (up to 20 sec — Max Age timer)
  "I receive BPDUs but do not forward or send anything"
         ↓
  LISTENING (15 sec — Forward Delay timer)
  "I send and receive BPDUs — determining my role"
         ↓
  LEARNING (15 sec — Forward Delay timer)
  "I know my role — building MAC table, not yet forwarding"
         ↓
  FORWARDING (active — forwarding user traffic)

Total worst-case time: up to 50 seconds
Typical (blocked → forwarding): 30 seconds (Listening 15s + Learning 15s)

Why Learning exists: the switch builds its MAC table BEFORE forwarding.
Without Learning, forwarding would cause a flood of unknown unicast frames
the moment the port activated.
🚨
The 30-second convergence delay breaks DHCP on access ports. When a PC connects, the port takes 30 seconds to reach forwarding. During this time, the PC's DHCP Discover is not forwarded. The DHCP process may time out and the PC receives no IP address. This is exactly the problem PortFast solves (see Section 5.3.4).

5.2.11 Per-VLAN Spanning Tree (PVST+)

In a multi-VLAN network, PVST+ runs a separate STP instance for every VLAN. Each instance can have a different root bridge, and blocked ports for one VLAN can be forwarding for another — enabling load balancing across redundant links.

  PVST+ Load Balancing Example:
  ┌─────────────────────────────────────────────┐
  │   S1                       S2               │
  │  (VLAN 10 root)           (VLAN 20 root)    │
  │    │                           │            │
  │    └──────────[S3]─────────────┘            │
  │                                             │
  │  VLAN 10: S3 uses link toward S1 (active)   │
  │           S3-S2 link is BLOCKED for VLAN 10  │
  │  VLAN 20: S3 uses link toward S2 (active)   │
  │           S3-S1 link is BLOCKED for VLAN 20  │
  │                                             │
  │  Result: BOTH links carry traffic!          │
  │  (Different VLANs use different paths)      │
  └─────────────────────────────────────────────┘
💡
Without PVST+, original 802.1D STP runs ONE instance for ALL VLANs. All VLANs share the same blocked ports. No load balancing is possible — one redundant link sits completely idle.
5.3Evolution of STP▾

5.3.1 Different Versions of STP

STP — IEEE 802.1D-1998 (Original)

One instance for ALL VLANs. Slow convergence (30–50 seconds). Also called Common Spanning Tree (CST). Historical baseline — you need to know it to understand everything that came after.

PVST+ — Cisco Proprietary

Per-VLAN Spanning Tree Plus. One 802.1D STP instance per VLAN. Supports PortFast, BPDU Guard, Root Guard, Loop Guard. Cisco default on older IOS versions.

RSTP — IEEE 802.1w

Rapid Spanning Tree Protocol. Convergence in milliseconds to seconds. Backward compatible with 802.1D. Alternate ports can immediately replace failed root ports — no timer wait.

✅ Rapid PVST+ — Cisco Default on IOS 15.0+

Cisco's implementation of RSTP running a separate instance per VLAN. Combines the speed of RSTP with the per-VLAN flexibility of PVST+. Supports PortFast, BPDU Guard, Root Guard, Loop Guard. THIS is what Cisco switches run by default.

MSTP / MST — IEEE 802.1s / Cisco MST

Maps multiple VLANs into fewer spanning tree instances — efficient for networks with many VLANs. Cisco MST supports up to 16 RSTP instances. Beyond CCNA scope but know the name.

🎯 EXAM TIP — What Does Cisco Run by Default?
Cisco switches running IOS 15.0 or later run Rapid PVST+ by default.

Not original STP. Not PVST+. Not RSTP. Rapid PVST+.

This is a direct, one-answer exam question that appears frequently.

5.3.2 RSTP Concepts

RSTP (IEEE 802.1w) supersedes original 802.1D while remaining backward compatible. Key improvements:

  • Convergence in milliseconds to a few seconds (vs. 30–50 seconds for 802.1D)
  • An alternate port can immediately transition to forwarding when the root port fails — no waiting for timers
  • RSTP actively negotiates port roles with neighbors using a proposal/agreement handshake — rather than passively waiting for timers to expire
  • Uses the same STA algorithm as original STP — same BID, same root bridge election, same path cost concepts
💡
Rapid PVST+ = Cisco's implementation of RSTP running a separate RSTP instance for each VLAN. This is what all modern Cisco switches run. The "Rapid" means RSTP-based convergence, and "PVST+" means one instance per VLAN.

5.3.3 RSTP Port States and Port Roles

RSTP reduces port states from 5 to 3 by merging the inactive states into a single discarding state:

RSTP port roles — two new roles replace the old STP blocked port:

Port RoleIn STP?In RSTP?Description
Root Port✅ Yes✅ YesBest path to root bridge — one per non-root switch — forwarding

The alternate port is the speed advantage of RSTP. In original STP, a blocked port had to wait through the full convergence cycle (up to 50 seconds) before forwarding. In RSTP, an alternate port transitions immediately to forwarding when the root port fails — no timers, no listening, no learning.

5.3.4 PortFast and BPDU Guard

The problem without PortFast: When a PC, phone, or printer connects to a switch port, that port must pass through Listening (15 sec) and Learning (15 sec) before it can forward — a 30-second delay. During this window:

  • DHCP Discover from the device is not forwarded
  • DHCP may time out → device gets no IP address
  • User cannot access the network for 30 seconds every time they plug in
Port state comparison — with and without PortFast 
Without PortFast (normal STP):
  Link up → Blocking → Listening (15s) → Learning (15s) → Forwarding
                       ↑ DHCP fails here — port not yet forwarding ↑

With PortFast:
  Link up → Forwarding (IMMEDIATE)
             ↑ DHCP succeeds immediately ↑
Configure PortFast 
! Enable PortFast on a single access port
S1(config)# interface fa0/6
S1(config-if)# spanning-tree portfast

! Enable PortFast globally on ALL access ports (recommended)
S1(config)# spanning-tree portfast default
🚨
PortFast is ONLY for access ports connected to end devices. Never enable PortFast on a port connecting to another switch. If PortFast is active on a switch-to-switch port, a loop can form before STP has time to react — because the PortFast port immediately starts forwarding without waiting for STP convergence.

BPDU Guard — always pair with PortFast:

End devices (PCs, phones, printers) never send BPDUs — only switches send BPDUs. So if a BPDU arrives on a PortFast-enabled port, it means a switch was connected there — a serious misconfiguration that could create a loop.

BPDU Guard immediately shuts the port into err-disabled state the instant any BPDU is received:

BPDU Guard process and recovery 
BPDU arrives on PortFast-enabled port
    ↓
BPDU Guard triggers immediately
    ↓
Port enters err-disabled state (completely shut down, no traffic)
    ↓
Log message: "%SPANTREE-2-BLOCK_BPDUGUARD: Received BPDU on port Fa0/6"
    ↓
Administrator must manually investigate and re-enable:
  S1(config)# interface fa0/6
  S1(config-if)# shutdown
  S1(config-if)# no shutdown

! Verify err-disabled ports
S1# show interfaces fa0/6 status
Port    Name   Status        Vlan  Duplex  Speed  Type
Fa0/6          err-disabled  1     auto    auto   10/100BaseTX
Configure BPDU Guard 
! Enable BPDU Guard on a single interface
S1(config-if)# spanning-tree bpduguard enable

! Enable BPDU Guard globally on all PortFast-enabled ports (recommended)
S1(config)# spanning-tree portfast bpduguard default
🎯 BEST PRACTICE — PortFast + BPDU Guard Together
Always deploy PortFast and BPDU Guard together on every access port.

PortFast = eliminates the 30-second convergence delay for end devices
BPDU Guard = shuts down the port immediately if a switch is accidentally connected

The err-disabled state does NOT auto-recover. An administrator must investigate and manually re-enable the port with shutdown then no shutdown. This forces accountability — a misconfigured port cannot quietly re-enable itself.

5.3.5 Alternatives to STP

As networks grew from a few switches to hierarchical designs with hundreds of switches and thousands of VLANs, STP limitations became more visible — slow convergence, blocked ports wasting bandwidth, complex per-VLAN management.

Modern trend: Many organizations are moving to Layer 3 everywhere — replacing Layer 2 uplinks between access and distribution switches with routed (Layer 3) links. Since Layer 3 routing handles redundant paths natively without blocking ports, STP is only needed at the access layer where end devices connect.

💡
Other STP alternatives exist — MLAG (Multi-System Link Aggregation), SPB (Shortest Path Bridging), and TRILL (Transparent Interconnection of Lots of Links) — but these are beyond the scope of the CCNA exam. Know the names if asked.

🎯Common Exam Traps — Module 5▾
❌
Trap 1: Layer 2 has no TTL — that is why STP exists.
IPv4 uses TTL, IPv6 uses Hop Limit — both decrement at every router hop and drop the packet at 0. Layer 2 frames have NO equivalent mechanism. Frames loop forever without STP.
❌
Trap 2: Lowest BID wins — lower is ALWAYS better in STP.
Lower priority = more preferred for root bridge. Priority 0 beats everything. Priority 4096 beats the default 32768. Students often assume "higher priority = more important" — in STP the opposite is true.
❌
Trap 3: You usually see 32769 in output, not 32768.
Default bridge priority (32768) + VLAN 1 extended system ID (1) = 32769. For VLAN 10: 32778. For VLAN 100: 32868. This is normal, not a misconfiguration. The extended system ID is automatically added and cannot be removed.
❌
Trap 4: Bridge priority must be a multiple of 4096.
Valid values: 0, 4096, 8192, 12288, 16384, 20480, 24576, 28672, 32768, 36864, 40960, 45056, 49152, 53248, 57344, 61440. IOS rejects any other value. Priority 32000 or 33000 will fail.
❌
Trap 5: The root bridge has NO root port — all its ports are designated.
The root bridge has zero cost to itself. It always wins cost comparisons on its own segments. Only non-root switches have root ports. Students frequently forget this.
❌
Trap 6: STP tiebreakers use the SENDER's information — not the local switch's.
When two equal-cost paths exist, the decision is based on the neighboring switch's BID, then the neighboring switch's port priority, then the neighboring switch's port ID. The exam will present this from the wrong switch's perspective to trap you.
❌
Trap 7: PortFast is ONLY for access ports — never for uplinks to switches.
PortFast bypasses STP convergence delays. On an access port this is safe because end devices never send BPDUs. On a switch-to-switch port, a loop can form immediately when the PortFast port starts forwarding before STP can react.
❌
Trap 8: BPDU Guard puts a port into err-disabled — it does NOT auto-recover.
An administrator must investigate the cause, then manually re-enable with shutdown followed by no shutdown. This is intentional security behavior — a misconfigured port cannot quietly re-enable itself.
⚠️
Trap 9: STP convergence takes 30 seconds minimum without PortFast.
Listening (15 sec) + Learning (15 sec) = 30 seconds before a port forwards. During this time DHCP fails on that port. Worst case with Max Age: up to 50 seconds total. PortFast eliminates this on access ports.
⚠️
Trap 10: Rapid PVST+ is the Cisco default on IOS 15.0+ — not original STP, not PVST+.
This is a direct exam question. The answer is Rapid PVST+. Switches must be explicitly configured to run original STP or PVST+ — Rapid PVST+ runs automatically.
⚠️
Trap 11: RSTP has three states — Discarding, Learning, Forwarding.
Original STP's disabled, blocking, and listening states are ALL merged into a single RSTP Discarding state. The exam will show five states and ask which are RSTP — the answer is only three of them.
⚠️
Trap 12: PVST+ and Rapid PVST+ are different protocols.
PVST+ = per-VLAN version of original slow 802.1D STP. Rapid PVST+ = per-VLAN version of fast RSTP (802.1w). These are not interchangeable. The exam uses both terms and expects you to know the difference.
⚠️
Trap 13: The RSTP alternate port transitions immediately — no timer wait.
This is the key speed advantage of RSTP over original STP. An alternate port replaces a failed root port without waiting for Max Age (20 sec) or transitioning through Listening/Learning (30 sec). This is why RSTP converges in milliseconds to seconds.
✅
Quick STP summary — the numbers to memorize:

Hello Timer: 2 seconds
Forward Delay: 15 seconds (Listening) + 15 seconds (Learning)
Max Age: 20 seconds
Convergence time without PortFast: 30 seconds typical, 50 seconds worst case
Default bridge priority: 32768 (appears as 32769 for VLAN 1 in output)
Priority increment: 4096 (must be a multiple of this)
root primary sets priority to: 24576
root secondary sets priority to: 28672
