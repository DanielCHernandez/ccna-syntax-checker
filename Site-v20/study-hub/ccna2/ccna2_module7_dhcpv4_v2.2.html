7.1DHCPv4 Concepts▾

7.1.1 DHCPv4 Server and Client

DHCPv4 (Dynamic Host Configuration Protocol version 4) automatically assigns IPv4 addresses and network configuration to clients — eliminating manual configuration of every device on the network.

Without DHCPWith DHCP
Manually configure IP on every PC, phone, printerDevices automatically receive their IP when they connect
Manually update when devices move or are replacedAddresses are managed automatically by the server
Track used addresses manually to prevent duplicatesServer tracks all leases — no duplicate assignments

How leasing works:

  • DHCP server assigns an IP for a limited time called a lease
  • Typical lease duration: 24 hours to one week (configurable — default is 1 day)
  • Client must renew before expiration — usually gets the same address back
  • If a device powers off, the lease expires and the address returns to the pool
Deployment OptionWhen Used
Dedicated DHCP serverLarge enterprise networks — scalable, centrally managed
Cisco IOS router as DHCP serverSmall branch, SOHO — no dedicated server needed

7.1.2 DHCPv4 Operation

DHCPv4 works in a client/server model. The server maintains a pool of available addresses and leases them to clients on request. The lease mechanism ensures that addresses are reclaimed when devices leave the network — clients that power off without releasing their address have their leases expire naturally.

  DHCP Server maintains address pool: 192.168.10.10 – 192.168.10.253
  
  PC1 connects → requests address → leased 192.168.10.10 for 1 day
  PC2 connects → requests address → leased 192.168.10.11 for 1 day
  
  PC1 powers off without releasing:
  → Lease for 192.168.10.10 expires after 1 day
  → Address returns to pool → available for the next device

7.1.3 Steps to Obtain a Lease — The DORA Process

When a device joins the network with no IP address, it goes through four steps — commonly called DORA: Discover, Offer, Request, Acknowledge.

  Client                                              DHCP Server
    |                                                      |
    |── DHCPDISCOVER (BROADCAST) ─────────────────────>  |  Step 1
    |   src: 0.0.0.0    dst: 255.255.255.255               |
    |   MAC dst: FF:FF:FF:FF:FF:FF                          |
    |   "Is there a DHCP server out there?"                 |
    |                                                      |
    |<──────────────────────── DHCPOFFER (unicast) ──────|  Step 2
    |   "Here is an offer: IP, mask, gateway, DNS, lease"  |
    |                                                      |
    |── DHCPREQUEST (BROADCAST) ──────────────────────>  |  Step 3
    |   "I accept your offer — all other servers, release" |
    |   Still broadcast — notifies ALL DHCP servers        |
    |                                                      |
    |<────────────────────────── DHCPACK (unicast) ──────|  Step 4
    |   "Confirmed — the address is yours"                 |
    |   Client binds the IP and starts using it            |
Step 1 — CLIENT sends
DHCPDISCOVER (Broadcast)
Client has no IP yet — sends Layer 2 and Layer 3 broadcast.
  • Source IP: 0.0.0.0 (no IP assigned yet)
  • Destination IP: 255.255.255.255
  • Destination MAC: FF:FF:FF:FF:FF:FF
  • "I need a DHCP server — is anyone out there?"
Step 2 — SERVER sends
DHCPOFFER (Unicast)
Server receives Discover, reserves an IP for the client, creates an ARP entry, and sends an offer back.
  • Includes: IP address, subnet mask, default gateway, DNS, lease duration
  • Multiple DHCP servers may each send an offer
Step 3 — CLIENT sends
DHCPREQUEST (Broadcast)
Client accepts one offer and sends DHCPREQUEST as a broadcast — critical because there may be multiple DHCP servers.
  • Broadcast notifies ALL servers which offer was accepted
  • Other servers release their reserved addresses back to their pools
  • If unicast were used, other servers would never know — their reserved addresses would be wasted
Step 4 — SERVER sends
DHCPACK (Unicast)
Server confirms the lease and sends DHCPACK.
  • May send an ICMP ping to the address first to check for conflicts
  • Creates a new ARP entry for the client
  • Client receives DHCPACK, does an ARP lookup for the IP — if no reply, starts using it
🎯 DORA MEMORY TRICK
Discover → Offer → Request → Acknowledge

Steps 1 and 3 = sent by the CLIENT (both odd numbers)
Steps 2 and 4 = sent by the SERVER (both even numbers)

Steps 1 and 3 = BROADCASTS  |  Steps 2 and 4 = UNICASTS

7.1.4 Steps to Renew a Lease

Before the lease expires, the client goes through a simpler two-step renewal process:

  1. DHCPREQUEST (unicast) — Client sends directly to the original DHCP server using unicast. "I would like to renew my current lease." If no DHCPACK is received, the client broadcasts a DHCPREQUEST to find any available server.
  2. DHCPACK (unicast) — Server verifies the lease and sends DHCPACK. Lease timer resets. Client keeps the same IP address.
Initial Lease (DORA)Lease Renewal
Number of steps42
Starts withDHCPDISCOVER (broadcast)DHCPREQUEST (unicast)
DHCPREQUEST sent asBroadcastUnicast (to known server)
Why?Client has no IP, doesn't know server addressClient already knows the server's IP from the original lease
💡
Key exam comparison: Renewal uses unicast because the client already knows the DHCP server's IP. Initial lease uses broadcast because the client has no IP and doesn't know where the server is. This distinction is a direct exam question.
7.2Configure a Cisco IOS DHCPv4 Server▾

7.2.1 Cisco IOS DHCPv4 Server

A Cisco router running IOS can be configured as a full-featured DHCPv4 server — assigning and managing IP addresses from configured address pools. Common in small branch offices and SOHO environments where a dedicated DHCP server is not justified.

  Topology:
  PC1 ──────┐
  PC2 ──────┤──── G0/0/0 [R1]     R1 = DHCP server
  PC3 ──────┘                      for 192.168.10.0/24
     192.168.10.0/24

7.2.2 Steps to Configure a Cisco IOS DHCPv4 Server

Always follow these three steps in this exact order:

Step 1
Exclude IPv4 Addresses
Before creating the pool, exclude addresses reserved for routers, servers, printers, and other statically configured devices. Must be done at global config mode BEFORE the pool is created.
Step 2
Define the DHCPv4 Pool Name
Create a named pool with ip dhcp pool [name]. IOS enters dhcp-config mode — prompt changes to Router(dhcp-config)#.
Step 3
Configure the DHCPv4 Pool
From dhcp-config mode, set the network, gateway, DNS, domain name, and lease. Network and default-router are required; everything else is optional.
Pool CommandWhat It ConfiguresRequired?
network [net] [mask]Subnet of addresses to lease out✅ Required
default-router [ip]Default gateway for clients — up to 8 addresses✅ Required
dns-server [ip]DNS server address — up to 8 addressesOptional
domain-name [name]Domain suffix given to clientsOptional
lease [days] [hours] [minutes]Lease duration — default is 1 dayOptional
netbios-name-server [ip]NetBIOS WINS server (legacy)Optional

7.2.3 Configuration Example

R1 — Complete DHCPv4 Server Configuration for 192.168.10.0/24 
! STEP 1: Exclude static addresses BEFORE creating pool
R1(config)# ip dhcp excluded-address 192.168.10.1 192.168.10.9
R1(config)# ip dhcp excluded-address 192.168.10.254

! STEP 2: Create the pool (enters dhcp-config mode)
R1(config)# ip dhcp pool LAN-POOL-1

! STEP 3: Configure pool parameters
R1(dhcp-config)# network 192.168.10.0 255.255.255.0
R1(dhcp-config)# default-router 192.168.10.1
R1(dhcp-config)# dns-server 192.168.11.5
R1(dhcp-config)# domain-name example.com
R1(dhcp-config)# end
💡
What clients receive from this pool:
IP address from 192.168.10.10 to 192.168.10.253 (pool minus excluded .1–.9 and .254)
Subnet mask: 255.255.255.0  |  Default gateway: 192.168.10.1
DNS: 192.168.11.5  |  Domain: example.com  |  Lease: 1 day
🚨
Exclude addresses BEFORE creating the pool. If you create the pool first and forget to exclude the router's own IP (192.168.10.1), DHCP may assign it to a client — creating an IP conflict and breaking network connectivity for both the router and the client.

7.2.7 Disable the Cisco IOS DHCPv4 Server

DHCP is enabled by default on Cisco IOS routers — even without any pool configured.

Disable and re-enable the DHCP service 
R1(config)# no service dhcp    ! Disable DHCP service
R1(config)# service dhcp       ! Re-enable DHCP service
⚠️
Stopping and restarting the DHCP service or clearing bindings can result in duplicate IP addresses being temporarily assigned on the network. Perform this only during a maintenance window.

7.2.8 DHCPv4 Relay — Deep Dive

The Core Problem

In enterprise networks, DHCP servers are centralized but clients are spread across many subnets. This creates a fundamental problem: DHCP relies on broadcasts, and routers do not forward broadcasts.

  WITHOUT ip helper-address:
  
  PC1 (192.168.10.0/24) ──G0/0/0──[R1]──G0/0/1──── DHCP Server (192.168.11.6)
  
  1. PC1 sends DHCPDISCOVER broadcast (src: 0.0.0.0, dst: 255.255.255.255)
  2. R1 receives the broadcast on G0/0/0
  3. R1 DROPS IT -- routers do not forward broadcasts
  4. DHCP server never sees the request
  5. PC1 times out -- falls back to APIPA (169.254.x.x)
     No real network access

The Solution — ip helper-address

The ip helper-address command converts the DHCP broadcast into a directed unicast and forwards it to the DHCP server. The router becomes a DHCP relay agent.

Configure ip helper-address on the client-facing interface 
R1(config)# interface GigabitEthernet0/0/0    ! Client-facing interface
R1(config-if)# ip helper-address 192.168.11.6 ! Address of the DHCP server
R1(config-if)# end

What Happens to the Packet — Step by Step

📦 Packet flow with ip helper-address configured
1
PC1 sends DHCPDISCOVER broadcast: src=0.0.0.0, dst=255.255.255.255
2
R1 receives it on G0/0/0 — sees ip helper-address is configured on this interface
3
R1 modifies the packet: changes src to 192.168.10.1 (R1's own G0/0/0 IP), changes dst to 192.168.11.6 (server — now unicast), fills the giaddr field with 192.168.10.1
4
R1 forwards the modified packet as unicast out G0/0/1 toward the DHCP server
5
DHCP server reads giaddr=192.168.10.1 → "This client is on the 192.168.10.0/24 subnet" → selects the correct pool → sends DHCPOFFER back to 192.168.10.1 (R1)
6
R1 receives the DHCPOFFER and forwards it to PC1
7
PC1 completes DORA normally and receives an IP address
💡
The giaddr field is critical — and often overlooked. When R1 relays a DHCPDISCOVER, it automatically inserts its own client-facing interface IP address into the giaddr (Gateway IP Address) field of the DHCP packet. The DHCP server reads this field to determine which subnet the client is on, then selects the matching pool. Without giaddr, the server would not know which subnet the client belongs to and could not make the correct assignment. This is the entire mechanism that allows one server to serve many subnets simultaneously.

Where Exactly Does ip helper-address Go?

❌
The #1 ip helper-address exam trap. The command goes on the interface FACING the clients — the one that receives the DHCP broadcast. NOT on the interface facing the server.
Correct vs incorrect placement 
Topology: [Clients 192.168.10.0/24] ──G0/0/0──[R1]──G0/0/1──[DHCP Server]

! CORRECT -- on the client-facing interface
R1(config)# interface GigabitEthernet0/0/0
R1(config-if)# ip helper-address 192.168.11.6

! WRONG -- on the server-facing interface (does nothing useful)
R1(config)# interface GigabitEthernet0/0/1
R1(config-if)# ip helper-address 192.168.11.6
! Broadcasts arrive on G0/0/0 and are dropped BEFORE reaching G0/0/1
! The command on G0/0/1 never gets triggered

Multiple Subnets — One Central DHCP Server

In enterprise networks one central DHCP server often serves many client subnets simultaneously. Each client-facing interface needs its own ip helper-address command.

R1 — Three client VLANs, one central DHCP server 
! Topology:
! [VLAN 10 - 192.168.10.0/24] ──G0/0/0──┐
! [VLAN 20 - 192.168.20.0/24] ──G0/0/1──┤ [R1] ──G0/0/3──── DHCP Server (10.0.0.10)
! [VLAN 30 - 192.168.30.0/24] ──G0/0/2──┘

R1(config)# interface GigabitEthernet0/0/0
R1(config-if)# ip helper-address 10.0.0.10

R1(config)# interface GigabitEthernet0/0/1
R1(config-if)# ip helper-address 10.0.0.10

R1(config)# interface GigabitEthernet0/0/2
R1(config-if)# ip helper-address 10.0.0.10

! VLAN 10 Discover relayed with giaddr=192.168.10.1 → server assigns from VLAN10 pool
! VLAN 20 Discover relayed with giaddr=192.168.20.1 → server assigns from VLAN20 pool
! VLAN 30 Discover relayed with giaddr=192.168.30.1 → server assigns from VLAN30 pool
! One server, three subnets, all working simultaneously
⚠️
The DHCP server must have a matching pool for every giaddr subnet. If the server has a pool for 192.168.10.0/24 but not 192.168.20.0/24, VLAN 20 clients still won't get addresses — even if the relay is perfectly configured.

Verify the Relay is Configured

show ip interface — confirms relay is active 
R1# show ip interface GigabitEthernet0/0/0
GigabitEthernet0/0/0 is up, line protocol is up
  Internet address is 192.168.10.1/24
  Broadcast address is 255.255.255.255
  Helper address is 192.168.11.6      ← confirms relay is active on this interface

Troubleshoot DHCP Relay — Step by Step

🔍 TROUBLESHOOT SCENARIO
PC1 on 192.168.10.0/24 cannot get a DHCP address. DHCP server is at 192.168.11.6. Follow these steps in order:
  1. Verify R1 can reach the DHCP server:
    ping test from R1 to DHCP server 
    R1# ping 192.168.11.6
!!!!!
! If this fails, fix routing FIRST -- relay cannot forward if no route exists
  2. Verify ip helper-address is on the correct interface:
    show ip interface — check for Helper address line 
    R1# show ip interface GigabitEthernet0/0/0
  Internet address is 192.168.10.1/24
  Helper address is 192.168.11.6     ← must appear here
! If missing: add ip helper-address 192.168.11.6 on this interface
  3. Verify the DHCP server has a pool matching the relay subnet:
    show running-config | section dhcp — on the DHCP server 
    DHCP-SVR# show running-config | section dhcp
ip dhcp pool VLAN10
 network 192.168.10.0 255.255.255.0    ← must match the giaddr subnet
 default-router 192.168.10.1
! If pool is missing or network statement doesn't match, create the correct pool
  4. Verify bindings are being created on the DHCP server:
    show ip dhcp binding 
    DHCP-SVR# show ip dhcp binding
IP address      Client-ID/Hardware address    Lease expiration
192.168.10.10   0100.5056.b3ed.d8             Sep 15 2019 8:42 AM
! If no bindings appear but relay and pool are correct, check if DHCP is disabled
  5. Check DHCP message flow with statistics:
    show ip dhcp server statistics — diagnose message flow 
    DHCP-SVR# show ip dhcp server statistics
DHCPDISCOVER     4    ← server IS receiving relayed Discovers
DHCPOFFER        4    ← server IS sending Offers
DHCPREQUEST      0    ← client never sent a Request back
! Discovers arriving but no Requests = client receives Offer but doesn't respond
! Check client VLAN assignment, firewall, or whether Offer is actually reaching client

🎯 EXAM TIP
The exam asks directly: "How many services does ip helper-address relay by default?"

7.3Configure a DHCPv4 Client▾

7.3.1 Cisco Router as a DHCPv4 Client

A Cisco router can act as a DHCP client on one interface while simultaneously acting as a DHCP server on another — common in SOHO environments where the WAN interface gets an IP from the ISP dynamically while the LAN interface serves local clients.

  ISP Network ──── G0/0/1 [SOHO Router] G0/0/0 ──── LAN Clients
                  ip address dhcp          ip dhcp pool LAN-POOL
                  (DHCP client)            (DHCP server)
  
  WAN side: gets IP from ISP via DHCP (ip address dhcp)
  LAN side: serves IP to local clients (ip dhcp pool)

7.3.2 Configuration and Verification

Configure router interface as DHCP client 
SOHO(config)# interface GigabitEthernet0/0/1
SOHO(config-if)# ip address dhcp
SOHO(config-if)# no shutdown

! IOS confirms the assignment with a console message:
%DHCP-6-ADDRESS_ASSIGN: Interface GigabitEthernet0/0/1 assigned DHCP address
209.165.201.12, mask 255.255.255.224, hostname SOHO
show ip interface — verify DHCP assigned the address 
SOHO# show ip interface GigabitEthernet0/0/1
GigabitEthernet0/0/1 is up, line protocol is up
  Internet address is 209.165.201.12/27
  Broadcast address is 255.255.255.255
  Address determined by DHCP        ← key phrase confirming DHCP assignment
(output omitted)
💡
"Address determined by DHCP" is the key phrase in show ip interface output confirming the address came from a DHCP server. If the output shows "Address determined by setup command" the address was manually configured — not from DHCP. This distinction is a direct exam question.

7.3.3 Home Router as a DHCPv4 Client

Home routers (wireless routers) are pre-configured to obtain their WAN IP from the ISP via DHCP by default. The WAN setup page typically shows "Automatic Configuration – DHCP" as the internet connection type. This is how residential customers automatically receive an internet-routable IP from their ISP without any manual configuration.

✅
Home routers are simultaneously DHCP clients (WAN side — gets IP from ISP) and DHCP servers (LAN side — assigns IPs to home devices like phones, laptops, TVs). This dual role is the same as the SOHO router scenario above.

🎯Common Exam Traps — Module 7▾
❌
Trap 1: DORA — Steps 1 and 3 are from the CLIENT. Steps 2 and 4 are from the SERVER.
Discover (client broadcast) → Offer (server unicast) → Request (client broadcast) → Acknowledge (server unicast). Students regularly reverse these on exams.
❌
Trap 2: Step 3 (DHCPREQUEST) is a BROADCAST — not unicast.
Even though the client already received an offer, the DHCPREQUEST is broadcast so ALL DHCP servers know which offer was accepted. This lets other servers release their reserved addresses. If it were unicast, only the selected server would know — others would hold reserved addresses unnecessarily.
❌
Trap 3: Lease renewal DHCPREQUEST is UNICAST. Initial DHCPREQUEST is BROADCAST.
During renewal the client already knows the server's IP and sends directly (unicast). During the initial lease the client has no IP and no knowledge of the server's location — it must broadcast. This comparison is a direct exam question.
❌
Trap 4: Exclude addresses BEFORE creating the pool.
ip dhcp excluded-address is global config and must come before ip dhcp pool. Forgetting to exclude the router's own IP means DHCP may assign it to a client, causing an IP conflict and network outage for both the client and the router.
❌
Trap 5: ip helper-address goes on the interface FACING the clients — not the server.
DHCP broadcasts arrive on the client-facing interface. Placing ip helper-address on the server-facing interface accomplishes nothing — the broadcast was already dropped before ever reaching that interface.
❌
Trap 6: The giaddr field tells the DHCP server which subnet the client is on.
When R1 relays a DHCPDISCOVER, it inserts its own client-facing interface IP into the giaddr field. The server reads this to select the matching pool. Without giaddr the server cannot determine the correct subnet — which is why the relay must be on the correct interface (its IP becomes the giaddr).
❌
Trap 7: ip helper-address relays EIGHT UDP services — not just DHCP.
Ports 37, 49, 53, 67, 68, 69, 137, and 138. DHCP is ports 67 and 68. DNS (53) and TFTP (69) are also relayed. The exam asks "how many services" directly — the answer is eight.
⚠️
Trap 8: The DHCP server must have a pool matching every relayed subnet's giaddr.
A perfectly configured relay still fails if the DHCP server has no pool for that subnet. One server can serve many subnets only if it has a correctly configured pool for each one.
⚠️
Trap 9: DHCP service is ENABLED by default on Cisco IOS.
Use no service dhcp to disable it. Deleting the pool does NOT disable the service — the DHCP service keeps running. This distinction matters when troubleshooting.
⚠️
Trap 10: show ip dhcp binding is the most important verification command.
It shows IP-to-MAC mappings for all active leases — this is how you confirm a specific client received an address and identify which device holds a specific IP. Use this before anything else when a client says "I'm not getting a DHCP address."
⚠️
Trap 11: Default lease duration is 1 DAY (24 hours).
Not 8 hours, not 1 week. Exactly 1 day. Change with the lease command in dhcp-config mode. lease infinite is possible but not recommended in production.
⚠️
Trap 12: A router can be both DHCP server and DHCP client simultaneously on different interfaces.
The WAN interface uses ip address dhcp to get an IP from the ISP. The LAN interface uses ip dhcp pool to serve local clients. These are independent operations on separate interfaces.
⚠️
Trap 13: "Address determined by DHCP" confirms DHCP client operation.
This phrase appears in show ip interface output when the address was assigned by a DHCP server. "Address determined by setup command" means it was manually configured. This is how you verify a Cisco router interface got its IP via DHCP.
❌
Trap 14: APIPA (169.254.x.x) means DHCP failed completely.
When a Windows client cannot reach a DHCP server at all, it self-assigns a 169.254.x.x address (Automatic Private IP Addressing). If you see this on a client, DHCP failed entirely — check relay configuration and connectivity to the DHCP server first.
✅
Quick DORA summary to memorize:

Discover — Client → Broadcast (0.0.0.0 → 255.255.255.255) "Any DHCP servers?"
Offer — Server → Unicast "Here's an IP offer"
Request — Client → Broadcast "I accept — everyone else release" ← most tested
Acknowledge — Server → Unicast "Confirmed — it's yours"

Renewal: Client unicasts DHCPREQUEST directly to known server → Server unicasts DHCPACK back. Only 2 steps, both unicast.
