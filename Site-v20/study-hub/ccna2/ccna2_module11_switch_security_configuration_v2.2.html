11.1Implement Port Security▾

11.1.1 Secure Unused Ports

Switch ports are enabled by default — the opposite of router interfaces. Every unused enabled port is an open entry point into the network. The first step in switch hardening is shutting down all unused ports.

Disable unused ports using interface range 
! Shut down ports Fa0/8 through Fa0/24:
S1(config)# interface range fa0/8 - 24
S1(config-if-range)# shutdown
%LINK-5-CHANGED: Interface FastEthernet0/8, changed state to administratively down
(output omitted)
%LINK-5-CHANGED: Interface FastEthernet0/24, changed state to administratively down

! To re-enable a port later:
S1(config-if-range)# no shutdown
✅
Best practice: Assign unused ports to an unused VLAN and shut them down. Two layers of protection — even if someone accidentally re-enables a port, it lands in an isolated VLAN with no network access.

11.1.2 Mitigate MAC Address Table Attacks

Port security is the simplest and most effective method to prevent MAC address table overflow attacks. It limits the number of valid MAC addresses allowed on a port. When a frame arrives, its source MAC is compared against the port's secure MAC list. If the MAC is unknown and the maximum is reached, a violation occurs.

By setting the maximum to 1, only one device can communicate through that port — any other device triggers an immediate violation response.

11.1.3 Enable Port Security

🚨
Port security cannot be configured on dynamic (DTP) ports. By default, switch ports are set to dynamic auto. You must first set the port to switchport mode access (or switchport mode trunk) before enabling port security. Forgetting this step is the most common lab error in Module 11.
Enable port security — access mode required first 
S1(config)# interface f0/1

! This will fail on a dynamic port:
S1(config-if)# switchport port-security
Command rejected: FastEthernet0/1 is a dynamic port.

! Set mode first, then enable:
S1(config-if)# switchport mode access
S1(config-if)# switchport port-security
S1(config-if)# end
📋 PORT SECURITY DEFAULTS (when enabled with no other commands)

Violation mode: Shutdown
Aging: Disabled
MAC learning: Dynamic (first learned MAC is secured)

11.1.4 Limit and Learn MAC Addresses

The switch can learn which MAC addresses are allowed on a port in three different ways:

Method 1 — Static (Manually Configured)
  • Admin manually types the allowed MAC address
  • Stored in running config — persists after save
  • Most secure — admin controls exactly which device is allowed
  • Most labor-intensive — must type every MAC manually
  • Command: switchport port-security mac-address aaaa.bbbb.1234
Method 2 — Dynamic (Auto-Learned)
  • Switch learns the first MAC that appears on the port
  • Stored in RAM only — lost on reboot
  • Port must re-learn the MAC address after a switch restart
  • Just enter switchport port-security — no extra commands
Method 3 — Sticky (Dynamic + Persistent)
  • Switch learns MACs dynamically AND adds them to running config
  • When saved with write memory, sticky MACs go to NVRAM and survive reboots
  • Best of both worlds — no manual typing, but persists across reboots
  • Most common method in production environments
  • Command: switchport port-security mac-address sticky
Complete port security config — max 4, one static + sticky for rest 
S1(config)# interface fa0/1
S1(config-if)# switchport mode access
S1(config-if)# switchport port-security
S1(config-if)# switchport port-security maximum 4
S1(config-if)# switchport port-security mac-address aaaa.bbbb.1234  ! static
S1(config-if)# switchport port-security mac-address sticky           ! sticky for rest
S1(config-if)# end

! Verify:
S1# show port-security interface fa0/1
Port Security              : Enabled
Port Status                : Secure-up
Violation Mode             : Shutdown
Maximum MAC Addresses      : 4
Total MAC Addresses        : 1
Configured MAC Addresses   : 1
Sticky MAC Addresses       : 0
Security Violation Count   : 0

11.1.5 Port Security Aging

Aging automatically removes secure MAC addresses after a set time — useful for shared spaces like conference rooms where different devices connect each day.

Aging TypeBehaviorUse Case
AbsoluteMAC deleted exactly after the timer expires, regardless of activityFixed-time rotation — strict control
InactivityMAC deleted only if no traffic from that source for the specified timeRemove inactive devices — keeps active ones
Configure aging — 10 minutes of inactivity 
S1(config)# interface fa0/1
S1(config-if)# switchport port-security aging time 10
S1(config-if)# switchport port-security aging type inactivity

! Also enable aging for statically configured MACs (disabled by default):
S1(config-if)# switchport port-security aging static

! Aging time range: 0–1440 minutes (0 = disabled)

11.1.6 Port Security Violation Modes

A violation occurs when a frame arrives from an unauthorized MAC address and the maximum has been reached. The three modes determine what happens next:

Protect
Least Secure
  • ✅ Drops frames from unauthorized MACs
  • ❌ No syslog message sent
  • ❌ Violation counter NOT incremented
  • ❌ Port stays up — no err-disable
  • ⚠️ Silent drop — you may never know an attack occurred
Restrict
Middle Ground
  • ✅ Drops frames from unauthorized MACs
  • ✅ Syslog message sent
  • ✅ Violation counter incremented
  • ❌ Port stays up — no err-disable
  • Good when you want visibility without disrupting the port
Shutdown
Default — Most Secure
  • ✅ Drops frames from unauthorized MACs
  • ✅ Syslog message sent
  • ✅ Violation counter incremented
  • ✅ Port immediately placed in err-disabled state
  • ✅ Port LED turns off
  • Admin must manually re-enable the port
ModeDrops TrafficSyslogCounterShuts Port
Protect✅ Yes❌ No❌ No❌ No
Restrict✅ Yes✅ Yes✅ Yes❌ No
Shutdown✅ Yes✅ Yes✅ Yes✅ Yes
Set violation mode 
S1(config-if)# switchport port-security violation restrict
! Options: protect | restrict | shutdown (default)

11.1.7 Ports in Error-Disabled State

When a violation occurs with shutdown mode, the port enters err-disabled state — port LED off, all traffic stopped. Console messages appear immediately:

Console messages when port enters err-disabled 
%PM-4-ERR_DISABLE: psecure-violation error detected on Fa0/18, putting Fa0/18 in err-disable state
%PORT_SECURITY-2-PSECURE_VIOLATION: Security violation caused by MAC address 000c.292b.4c75 on port FastEthernet0/18.
%LINEPROTO-5-PPDOWN: Line protocol on Interface FastEthernet0/18, changed state to down
%LINK-3-UPDOWN: Interface FastEthernet0/18, changed state to down
Verify err-disabled state 
S1# show interface fa0/18
FastEthernet0/18 is down, line protocol is down (err-disabled)

S1# show port-security interface fa0/18
Port Security              : Enabled
Port Status                : Secure-shutdown    ← err-disabled state
Violation Mode             : Shutdown
Security Violation Count   : 1                  ← counter incremented
Manual recovery — shutdown then no shutdown 
! Step 1: First remove the offending device from the port
! Step 2: Then re-enable the port:
S1(config)# interface fa0/18
S1(config-if)# shutdown
S1(config-if)# no shutdown

! Optional — automatic recovery (use with caution):
S1(config)# errdisable recovery cause psecure-violation
S1(config)# errdisable recovery interval 30   ! seconds before auto-re-enable
⚠️
Always investigate and remove the offending device first before re-enabling the port. Auto-recovery repeatedly re-enables a port that may still be under attack.

11.2Mitigate VLAN Attacks▾

11.2.2 Five Steps to Mitigate VLAN Hopping Attacks

VLAN hopping works because DTP auto-trunking is enabled by default. These five steps eliminate that attack surface:

  1. Force access mode on all non-trunking ports — disables DTP negotiation on user-facing ports
    switchport mode access
  2. Disable unused ports AND assign them to an unused VLAN — even if re-enabled, the port is isolated
    switchport access vlan 1000 then shutdown
  3. Manually configure trunk links — do not rely on DTP negotiation
    switchport mode trunk
  4. Disable DTP on trunk ports too — prevents DTP negotiation even on trunks
    switchport nonegotiate
  5. Change the native VLAN from VLAN 1 to an unused VLAN — eliminates double-tagging attack
    switchport trunk native vlan 999
Complete VLAN attack mitigation — full switch example 
! Active access ports (Fa0/1–16): disable DTP
S1(config)# interface range fa0/1 - 16
S1(config-if-range)# switchport mode access
S1(config-if-range)# exit

! Unused ports (Fa0/17–20): isolate and disable
S1(config)# interface range fa0/17 - 20
S1(config-if-range)# switchport mode access
S1(config-if-range)# switchport access vlan 1000   ! unused VLAN
S1(config-if-range)# shutdown
S1(config-if-range)# exit

! Trunk ports (Fa0/21–24): manual trunk, no DTP, change native VLAN
S1(config)# interface range fa0/21 - 24
S1(config-if-range)# switchport mode trunk
S1(config-if-range)# switchport nonegotiate
S1(config-if-range)# switchport trunk native vlan 999  ! not VLAN 1
S1(config-if-range)# end
11.3Mitigate DHCP Attacks▾

11.3.2 DHCP Snooping — Trusted vs Untrusted Ports

DHCP snooping classifies every port as either trusted or untrusted. It then filters DHCP messages based on which type of port they arrive on:

🔍 DHCP Snooping Port Classification
TRUSTED
Allowed to pass all DHCP messages including Offers and ACKs (server responses). Assign to: uplink ports, trunk links, ports directly connected to a legitimate DHCP server.
UNTRUSTED
Only client-side messages (Discover, Request) are allowed. DHCP Offers and ACKs arriving here are dropped immediately — indicates a rogue DHCP server. This is the default for all ports.
💡
DHCP snooping also builds a binding table mapping client MAC → assigned IP → VLAN → interface. This table is the foundation for DAI (Dynamic ARP Inspection) in section 11.4. DHCP snooping must be configured before DAI.

11.3.3–11.3.4 Four Steps to Implement DHCP Snooping

  1. Enable DHCP snooping globally
    ip dhcp snooping
  2. Mark trusted ports (uplinks and server-facing ports)
    ip dhcp snooping trust on the interface
  3. Rate-limit DHCP messages on untrusted ports — stops starvation attacks
    ip dhcp snooping limit rate 6 (6 packets per second)
  4. Enable DHCP snooping on specific VLANs
    ip dhcp snooping vlan 5,10,50-52
DHCP snooping — complete configuration example 
! Step 1: Enable globally
S1(config)# ip dhcp snooping

! Step 2: Trust the uplink to the DHCP server
S1(config)# interface f0/1
S1(config-if)# ip dhcp snooping trust
S1(config-if)# exit

! Step 3: Rate-limit untrusted access ports (stops starvation attacks)
S1(config)# interface range f0/5 - 24
S1(config-if-range)# ip dhcp snooping limit rate 6
S1(config-if-range)# exit

! Step 4: Enable per VLAN
S1(config)# ip dhcp snooping vlan 5,10,50-52
S1(config)# end
Verify DHCP snooping 
S1# show ip dhcp snooping

11.4Mitigate ARP Attacks▾

11.4.1 Dynamic ARP Inspection (DAI)

🚨
DAI requires DHCP snooping. DAI validates ARP packets by checking them against the DHCP snooping binding table (MAC → IP mappings). Without DHCP snooping running first, there is no table to validate against — DAI cannot function. Always configure DHCP snooping before enabling DAI.

DAI intercepts and validates all ARP packets on untrusted ports. For each intercepted ARP:

  • Checks the IP-to-MAC mapping against the DHCP snooping binding table
  • Forwards valid ARPs — drops and logs invalid ones
  • Does NOT relay gratuitous ARPs to other ports in the same VLAN
  • Rate-limits ARP packets — err-disables the interface if the rate is exceeded

11.4.2 DAI Implementation Guidelines

General rule: all access ports = untrusted, all uplink ports = trusted.

🔍 DAI Trusted vs Untrusted — Same Logic as DHCP Snooping
TRUSTED
ARP packets pass without inspection. Assign to: uplink ports connecting to routers or other switches where you control both sides.
UNTRUSTED
All ARP Requests and Replies are intercepted and validated against the DHCP snooping binding table. Invalid ARPs are dropped and logged. Default for all ports.
⚠️
Trusted for DHCP snooping ≠ trusted for DAI. These are two separate commands on the same interface. Setting ip dhcp snooping trust does NOT automatically make the port trusted for DAI. You must configure ip arp inspection trust separately on the same interface.

11.4.3 DAI Configuration Example

DAI — complete configuration (DHCP snooping must come first) 
! Prerequisite: DHCP snooping must be configured first
S1(config)# ip dhcp snooping
S1(config)# ip dhcp snooping vlan 10

! Enable DAI on the VLAN
S1(config)# ip arp inspection vlan 10

! Configure trusted uplink — both DHCP snooping AND DAI trust must be set
S1(config)# interface fa0/24
S1(config-if)# ip dhcp snooping trust      ! for DHCP snooping
S1(config-if)# ip arp inspection trust     ! for DAI — separate command!
S1(config-if)# exit

Optional — DAI Additional Validation

DAI can also validate fields inside the ARP packet body. These three checks can be combined on a single line:

ValidationWhat It Checks
src-macSender MAC in ARP body must match source MAC in Ethernet header
dst-macTarget MAC in ARP body must match destination MAC in Ethernet header
ipARP body must not contain invalid IPs: 0.0.0.0, 255.255.255.255, or multicast addresses
DAI validate — MUST be configured on ONE line 
! ❌ WRONG — each command overwrites the previous:
S1(config)# ip arp inspection validate src-mac
S1(config)# ip arp inspection validate dst-mac   ! overwrites above
S1(config)# ip arp inspection validate ip         ! overwrites above
! Result: only "ip" validation is active

! ✅ CORRECT — all three on ONE line:
S1(config)# ip arp inspection validate src-mac dst-mac ip

! Verify:
S1(config)# do show run | include validate
ip arp inspection validate src-mac dst-mac ip
🚨
This is one of the most commonly tested exam traps in Module 11. Multiple ip arp inspection validate commands each overwrite the previous one. Always enter all desired validations on a single line.
11.5Mitigate STP Attacks▾

11.5.1 PortFast and BPDU Guard — Overview

PortFast
What it does: Bypasses STP Listening (15s) and Learning (15s) states — port goes immediately to Forwarding.

Use on: Access ports connected to end devices only (PCs, printers, IP phones).

Why: Eliminates the 30-second STP convergence wait on ports that will never form loops.

Risk: If enabled on a switch-to-switch link, a loop forms instantly before STP can intervene.
BPDU Guard
What it does: Immediately err-disables any PortFast port that receives a BPDU.

Use on: All PortFast-enabled ports — always pair these two together.

Why: End devices never send BPDUs. If a BPDU arrives on an access port, something unauthorized (rogue switch or attacker) is connected.

Recovery: Manual shutdown/no shutdown or errdisable auto-recovery.
✅
Always enable BPDU Guard on all PortFast-enabled ports. PortFast alone still listens for BPDUs — it just ignores the STP state machine. BPDU Guard is the enforcement mechanism that prevents rogue switches from participating in STP elections via PortFast ports.

11.5.2 Configure PortFast

PortFast — per interface and global 
! Per interface (access port):
S1(config)# interface fa0/1
S1(config-if)# switchport mode access
S1(config-if)# spanning-tree portfast
%Warning: portfast should only be enabled on ports connected to a single
 host. Connecting hubs, concentrators, switches, bridges, etc... to this
 interface when portfast is enabled, can cause temporary bridging loops.
 Use with CAUTION

! Globally on ALL access ports (no need to configure each port):
S1(config)# spanning-tree portfast default
%Warning: this command enables portfast by default on all interfaces. You
 should now disable portfast explicitly on switched ports leading to hubs,
 switches and bridges as they may create temporary bridging loops.
Verify PortFast configuration 
! Check global status:
S1# show running-config | begin span
spanning-tree mode pvst
spanning-tree portfast default     ← global PortFast enabled
spanning-tree extend system-id

! Check specific interface:
S1# show running-config interface fa0/1
interface FastEthernet0/1
 switchport mode access
 spanning-tree portfast             ← per-interface PortFast

! Show spanning tree summary:
S1# show spanning-tree summary
Portfast Default             is enabled

11.5.3 Configure BPDU Guard

BPDU Guard — per interface and global 
! Per interface:
S1(config)# interface fa0/1
S1(config-if)# spanning-tree bpduguard enable
S1(config-if)# exit

! Globally on all PortFast-enabled ports (recommended):
S1(config)# spanning-tree portfast bpduguard default
S1(config)# end
Verify BPDU Guard and recover from err-disabled 
! Verify both PortFast and BPDU Guard are active:
S1# show spanning-tree summary
Switch is in pvst mode
Portfast Default             is enabled
PortFast BPDU Guard Default  is enabled    ← confirmed
Portfast BPDU Filter Default is disabled

! Manual recovery from BPDU Guard err-disable:
S1(config)# interface fa0/1
S1(config-if)# shutdown
S1(config-if)# no shutdown

! Automatic recovery (optional):
S1(config)# errdisable recovery cause bpduguard
S1(config)# errdisable recovery interval 30

🎯Common Exam Traps — Module 11▾
❌
Trap 1: Port security cannot be configured on dynamic (DTP) ports.
Must set switchport mode access first. The exam frequently shows the rejected command and asks why it failed. Switch ports are dynamic auto by default — this is the opposite of router interfaces which are shutdown by default.
❌
Trap 2: Port security defaults are max=1 and violation=shutdown.
Just entering switchport port-security gives you these defaults. No other parameters are required. The exam tests whether you know what happens with just this one command.
❌
Trap 3: Sticky MACs must be saved or they are lost on reboot.
Sticky adds learned MACs to the running config — but write memory must be used to save them to NVRAM. Without saving, sticky MACs are lost on a switch reload, defeating their purpose.
❌
Trap 4: Protect is the LEAST secure violation mode — silent drop, no log.
Protect drops frames but sends no syslog and increments no counter. A threat actor flooding the port would never be detected. Students often think "protect" sounds most secure — it is actually the least secure because you get no visibility.
❌
Trap 5: DAI requires DHCP snooping — configure DHCP snooping first.
DAI validates ARP packets against the DHCP snooping binding table. Without DHCP snooping, there is no table and DAI cannot validate anything. This prerequisite is frequently tested in exam scenarios and labs.
❌
Trap 6: ip arp inspection validate — all options must be on ONE line.
Each separate ip arp inspection validate command overwrites the previous one. The only correct way to combine validations: ip arp inspection validate src-mac dst-mac ip on a single line. This is explicitly tested in labs and quizzes.
❌
Trap 7: ip dhcp snooping trust and ip arp inspection trust are separate commands.
Configuring a port as trusted for DHCP snooping does NOT make it trusted for DAI. Both commands must be entered on the same uplink interface independently. Forgetting one or the other causes DAI to inspect traffic it shouldn't — or fail to inspect traffic it should.
❌
Trap 8: PortFast only on end-device access ports — never on switch uplinks.
PortFast bypasses STP convergence entirely. On a link connecting two switches, this instantly creates a loop before STP has any chance to detect and block it. The IOS warning message says this explicitly — and the exam tests it.
⚠️
Trap 9: BPDU Guard recovery requires manual shutdown then no shutdown.
A port err-disabled by BPDU Guard does not automatically recover. Admin must manually issue shutdown followed by no shutdown. Auto-recovery requires explicitly configuring errdisable recovery cause bpduguard.
⚠️
Trap 10: show port-security vs show port-security interface.
show port-security = one-line summary per port across all ports. show port-security interface [int] = full details for one interface including violation count, aging settings, sticky count, and last violating MAC. Know which to use when.
⚠️
Trap 11: Changing the native VLAN eliminates double-tagging attacks.
The double-tagging attack requires the attacker's port to be in the same VLAN as the native VLAN of the trunk. Changing the native VLAN to an unused VLAN (e.g., VLAN 999) that carries no user traffic prevents this entirely — not just mitigates it.
⚠️
Trap 12: DHCP snooping rate limiting stops starvation — not spoofing.
Rate limiting (ip dhcp snooping limit rate) limits DHCP Discover messages per second, slowing starvation attacks. It does NOT stop DHCP spoofing (rogue server). DHCP spoofing is stopped by the trusted/untrusted port model — DHCP Offers on untrusted ports are dropped.
✅
Module 11 quick summary — attack to command:

MAC flooding → switchport port-security (on access ports)
DHCP starvation → ip dhcp snooping limit rate [pps]
DHCP spoofing → ip dhcp snooping (trusted/untrusted model)
ARP poisoning → ip arp inspection vlan [id] (requires DHCP snooping first)
STP manipulation → spanning-tree bpduguard enable / portfast bpduguard default
VLAN hopping → switchport mode access + switchport nonegotiate
Double-tagging → switchport trunk native vlan 999 (change from VLAN 1)
