10.1Endpoint Security▾

10.1.1 Network Attacks Today

Attack TypeDescription
DDoSCoordinated attack from many compromised devices (zombies) that degrades or halts public access to an organization's website and resources
Data BreachAttack where servers or hosts are compromised to steal confidential information
MalwareHosts infected with malicious software. Example: ransomware like WannaCry encrypts data and demands payment before restoring access

10.1.2 Network Security Devices

VPN-Enabled Router

Provides a secure encrypted connection to remote users across a public network. VPN services can be integrated into the firewall. Ensures remote workers securely access the enterprise network.

NGFW — Next-Generation Firewall

Provides: stateful packet inspection, application visibility and control, next-generation IPS (NGIPS), advanced malware protection (AMP), and URL filtering.

NAC — Network Access Control

Includes AAA services — authentication, authorization, and accounting. Manages access policies across all user and device types. Cisco ISE (Identity Services Engine) is an example of a NAC device.

10.1.3 Endpoint Protection

Endpoints — laptops, desktops, servers, IP phones, and BYODs — are particularly susceptible to malware via email or web browsing. Traditional protection (antivirus, host firewalls, HIPS) is no longer sufficient alone.

Modern best practice combines four technologies:

  • NAC — controls which devices can connect to the network
  • Host-based AMP — detects and blocks malware on the endpoint (e.g., Cisco AMP for Endpoints)
  • ESA — filters malicious email before it reaches the user
  • WSA — filters malicious web traffic before it reaches the user
🚨
Many attacks originate inside the network. A compromised internal host can become a launching point for attacks on servers and sensitive data — bypassing perimeter defenses entirely.

10.1.4 Cisco Email Security Appliance (ESA)

The Cisco ESA monitors SMTP and filters email threats. Updated by real-time feeds from Cisco Talos — threat intelligence data is pulled every 3 to 5 minutes.

ESA FunctionDetail
Block known threatsUses Cisco Talos threat intelligence updated every 3–5 minutes
Remediate stealth malwareCatches malware that evaded initial detection
Discard emails with bad linksURL reputation checking against known malicious sites
Block access to newly infected sitesReal-time URL analysis
Encrypt outgoing emailPrevents data loss via email exfiltration
⚠️
Spear phishing is the #1 threat vector: According to the SANS Institute, 95% of all attacks on enterprise networks result from a successful spear phishing attack. The ESA is the primary technical defense.

10.1.5 Cisco Web Security Appliance (WSA)

The Cisco WSA controls and secures web-based traffic between users and the internet:

  • Blacklisting of URLs and URL categorization
  • Malware scanning of web content
  • Web application filtering
  • Encryption and decryption of HTTPS web traffic
  • Acceptable use policy enforcement — restrict chat, video, audio by time or category
  • Reporting and visibility into all web activity
💡
ESA vs WSA: ESA monitors and filters email (SMTP). WSA monitors and filters web traffic (HTTP/HTTPS). These are two separate appliances serving different purposes — both integrate with Cisco Talos threat intelligence.
10.2Access Control▾

10.2.1 Authentication with a Local Password

The simplest remote access method — but also the weakest:

  • No accountability — no username is recorded in logs
  • Password sent in plaintext — anyone who intercepts the connection sees it
  • Anyone with the password gains full access
Weak: vty password (avoid in production) 
R1(config)# line vty 0 4
R1(config-line)# password ci5c0
R1(config-line)# login
Better: SSH with local database 
R1(config)# ip domain-name example.com
R1(config)# crypto key generate rsa general-keys modulus 2048
R1(config)# username Admin secret Str0ng3rPa55w0rd
R1(config)# ssh version 2
R1(config)# line vty 0 4
R1(config-line)# transport input ssh
R1(config-line)# login local
💡
Limitations of local database authentication: Accounts must be configured individually on every device. No fallback if the admin forgets credentials. In large networks, a central AAA server solves both problems — one set of credentials applies to all devices.

10.2.2 AAA Components

AAA = Authentication, Authorization, and Accounting — the primary framework for controlling access to network devices.

ComponentQuestion It AnswersCredit Card Analogy
AuthenticationWho are you? — verify identityThe card identifies who can use it
AuthorizationWhat can you do? — governs allowed actionsHow much the card allows to be spent
AccountingWhat did you do? — logs all actionsThe statement of what was purchased

10.2.3 Authentication — Local vs Server-Based + RADIUS vs TACACS+

Local AAAServer-Based AAA
Where credentials storedOn the router/switch itselfCentral AAA server
Best forSmall networks — few devicesLarge networks — multiple routers/switches
ScalabilityPoor — must update every deviceExcellent — change once, applies everywhere
Protocol usedLocal database lookupRADIUS or TACACS+

RADIUS vs TACACS+ — Expanded Comparison

RADIUS — Open Standard
Standard: Open (RFC 2865) — works across vendors
Transport: UDP (ports 1812/1813)
Encryption: Encrypts password only — rest of packet is plaintext
AAA handling: Combines Authentication + Authorization into one process
Best for: Network access control — VPN, wireless, ISP dial-in
Accounting: Full accounting support (port 1813)
TACACS+ — Cisco Proprietary
Standard: Cisco proprietary — Cisco devices only
Transport: TCP (port 49) — more reliable delivery
Encryption: Encrypts entire payload — more secure
AAA handling: Separates Authentication, Authorization, and Accounting independently
Best for: Device administration — managing Cisco routers/switches
Granularity: Command-level authorization (can permit/deny specific IOS commands)
🎯 EXAM TIP — RADIUS vs TACACS+
RADIUS = open standard, UDP, encrypts password only, combines Auth+Authz → best for network access (VPN, wireless users).

TACACS+ = Cisco proprietary, TCP, encrypts entire packet, separates AAA → best for device administration (managing Cisco routers and switches).

Memory aid: TACACS+ = TCP. RADIUS = RFC (open standard).

10.2.4 Authorization

After authentication, authorization determines what the user can and cannot do. It is automatic — the user performs no additional steps after logging in.

  • The AAA server stores a set of attributes (permissions) per user
  • Router sends an authorization request to the AAA server
  • Server evaluates the request against the user's profile and returns PASS or FAIL
  • Example: a user may be allowed show commands but denied configure terminal

10.2.5 Accounting

AAA accounting collects and logs all usage data for auditing, billing, and forensics. The AAA server maintains a detailed log including:

  • Username and date/time of every login and logout
  • Every EXEC and configuration command executed
  • Connection start and stop times
  • Number of packets and bytes transferred
✅
Accounting provides evidence when users perform malicious acts — it creates an audit trail of exactly what every authenticated user did on every device, timestamped and associated with a specific username.

10.2.6 IEEE 802.1X

802.1X is a port-based access control and authentication protocol. The switch port remains in an unauthorized state — blocking all traffic except 802.1X authentication traffic — until the connected device successfully authenticates.

Role 1 — Client
Supplicant
The end device requesting network access — PC, laptop, IP phone, or any device with 802.1X-compliant client software. Sends credentials when challenged by the authenticator.
Role 2 — Switch or Wireless AP
Authenticator
The intermediary between client and authentication server. Requests credentials from the client, forwards them to the RADIUS server, and enforces the server's access decision (open or block the port). The switch does NOT make the authentication decision itself.
Role 3 — RADIUS Server
Authentication Server
Validates the client's identity and notifies the switch whether to grant or deny access. Example: Cisco Identity Services Engine (ISE). The server makes all access decisions — the switch simply enforces them.
  802.1X Process:
  Client plugs into switch port
    ↓
  Switch port starts in UNAUTHORIZED state
  (only 802.1X traffic allowed — all other traffic blocked)
    ↓
  Switch sends EAP-Request for client identity
    ↓
  Client sends EAP-Response with credentials
    ↓
  Switch forwards credentials to RADIUS authentication server
    ↓
  RADIUS server authenticates → returns Accept or Reject
    ↓
  Accept: switch opens the port (AUTHORIZED state)
  Reject: switch keeps the port blocked
10.3Layer 2 Security Threats▾

10.3.1 Layer 2 Vulnerabilities

Security is only as strong as the weakest link. Layer 2 is that weak link in the OSI model.

🚨
If Layer 2 is compromised, ALL upper layers (3–7) are also compromised — regardless of what VPNs, firewalls, or IPS systems are implemented at those layers. A threat actor capturing Layer 2 frames bypasses all upper-layer security completely.

LANs were originally designed as trusted environments under a single organization's administrative control. BYOD and insider threats have changed this. Today, Layer 2 security must be actively implemented — it no longer can be assumed.

10.3.2 Switch Attack Categories

10.3.3 Switch Attack Mitigation Techniques

⚠️
Layer 2 solutions only work if management protocols are also secured. Telnet, FTP, TFTP, SNMP, and Syslog are all insecure — use SSH, SCP, SFTP, and SSL/TLS instead. Also use a dedicated management VLAN and ACLs to restrict management access.
10.4MAC Address Table Attack▾

10.4.2 MAC Address Table Flooding

A switch's MAC address table has a fixed size. The MAC flooding attack exploits this by filling the table with fake entries until no space remains.

  1. Threat actor runs macof — a tool that generates up to 8,000 fake random source MAC address frames per second
  2. The MAC address table fills completely — the switch runs out of memory for new entries
  3. The switch can no longer look up destination MACs — treats all frames as unknown unicast
  4. Switch begins flooding all frames out all ports on the same VLAN — behaves like a hub
  5. Threat actor runs a packet sniffer — captures all traffic from every device on the VLAN
show mac address-table dynamic — normal table before attack 
S1# show mac address-table dynamic
          Mac Address Table
-------------------------------------------
Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
   1    0001.9717.22e0    DYNAMIC     Fa0/4
   1    000a.f38e.74b3    DYNAMIC     Fa0/1
   1    0090.0c23.ceca    DYNAMIC     Fa0/3
   1    00d0.ba07.8499    DYNAMIC     Fa0/2
! After macof attack: table is full of fake entries
! Switch floods ALL subsequent frames out every port on VLAN 1
⚠️
Attack scope is limited to the local VLAN. The threat actor can only capture traffic on the VLAN they are connected to. Traffic on other VLANs is not exposed. A Catalyst 6500 holds 132,000 MAC entries — macof can overflow it in seconds.
💡
If macof stops running, the switch ages out the fake entries (default 5 minutes) and resumes normal forwarding. The attack must run continuously to maintain the flooded state.

10.4.3 MAC Address Table Attack Mitigation

Port Security limits the number of source MAC addresses learned on a port. If the limit is exceeded, additional MACs trigger a violation action — the frame is dropped or the port shuts down. This cuts the attack off at the source because the threat actor cannot fill the table from one port.

✅
Port Security configuration is covered in detail in Module 11. The key concept here: Port Security directly prevents MAC table flooding by limiting how many MAC addresses can be associated with any single switch port.
10.5LAN Attacks▾

10.5.2 VLAN Hopping Attacks

Goal: Send traffic to another VLAN without going through a router — by tricking the switch into forming a trunk link with the attacker's device.

  Default behavior (DTP auto-trunking enabled):
  Threat actor's host ──── Switch port (DTP: auto)
  
  Attack:
  Threat actor spoofs 802.1Q + DTP signaling
    ↓
  Switch negotiates trunk link with attacker's host
    ↓
  Attacker now has access to ALL VLANs on the switch
    ↓
  Can send and receive traffic on any VLAN without routing

Mitigation:

  • Disable trunking on all access ports: switchport mode access
  • Disable DTP (auto-trunking): switchport nonegotiate
  • Manually configure trunk ports: switchport mode trunk
  • Ensure native VLAN is only used for trunk links

10.5.3 VLAN Double-Tagging Attack

Goal: Deliver a frame to a target VLAN that the attacker is not a member of, by embedding a hidden inner 802.1Q tag inside an outer tag.

Requirement: Attacker must be connected to a port in the same VLAN as the native VLAN of the trunk port.

📦 Double-Tagging Attack — Step by Step
1
Threat actor (on native VLAN 10) sends a frame with two 802.1Q tags: outer tag = VLAN 10 (native), inner tag = VLAN 20 (target victim VLAN)
2
First switch sees outer tag = VLAN 10 (native VLAN). Native VLAN frames are not re-tagged when forwarded — switch strips the outer VLAN 10 tag and forwards the frame. The inner VLAN 20 tag is still intact and has not been inspected.
3
Second switch receives the frame. It has no knowledge of the original outer tag. It sees only the inner VLAN 20 tag — the attacker's planted tag. Switch forwards the frame to VLAN 20 hosts.
4
Target host on VLAN 20 receives the attacker's frame. The attack succeeds — traffic crossed from VLAN 10 to VLAN 20 without routing.
🚨
Critical limitation — this attack is UNIDIRECTIONAL. The attacker can send TO VLAN 20 but CANNOT receive traffic back. Return traffic is addressed normally within VLAN 20 and never crosses back to the attacker's native VLAN. The attacker can deliver payloads but cannot establish a true two-way session through this mechanism alone.
  WHY it's unidirectional:
  
  Attacker frame (double-tagged) → Victim VLAN 20 ✅
  
  Victim reply → Victim's default gateway → routing table → VLAN 10
  But reply is sent normally (single tag VLAN 20 or via router)
  The reply NEVER reaches the attacker's VLAN 10 port via this mechanism ❌
  
  The path only works in one direction because:
  - Only the attacker controls the double-tagging
  - Return traffic from VLAN 20 uses normal single-tag routing
  - No mechanism sends VLAN 20 traffic back into native VLAN 10

Mitigation (same as VLAN hopping):

  • Change the native VLAN to an unused VLAN — never use the default native VLAN (VLAN 1) on trunk ports
  • Disable trunking on all access ports
  • Manually configure all trunk ports — disable DTP

10.5.5 DHCP Attacks — Starvation vs Spoofing

🔴 DHCP Starvation Attack — Denial of Service
  • Tool used: Gobbler
  • Method: Sends thousands of DHCP DISCOVER messages with fake/random MAC addresses
  • Effect: Legitimate DHCP server leases IPs to all fake requests — IP address pool exhausted
  • Result: Legitimate clients broadcast DHCP DISCOVER but receive no response — no IP address assigned
  • This is a DoS attack — not a man-in-the-middle
  • Mitigation: DHCP Snooping (rate-limits DHCP messages per port) + Port Security (limits MACs per port)
🟣 DHCP Spoofing Attack — Man-in-the-Middle
  • Tool: Rogue DHCP server connected to network
  • Method: Rogue server races the legitimate server to respond first to DHCP DISCOVER
  • If rogue server wins: Client accepts rogue configuration containing:
  • Wrong default gateway → all client traffic flows through attacker (MitM)
  • Wrong DNS server → redirects users to malicious websites
  • Wrong IP address → DoS for the affected client
  • Mitigation: DHCP Snooping — marks ports as trusted (server-facing) or untrusted (client-facing); drops DHCP responses on untrusted ports
🎯 STARVATION vs SPOOFING — KEY DISTINCTION
Starvation = exhaust the DHCP address pool → Denial of Service (clients get no IP)
Spoofing = provide false configuration → Man-in-the-Middle (clients get wrong gateway/DNS)

Both are mitigated by DHCP Snooping — but they are completely different attacks with different goals. Starvation uses fake client MACs. Spoofing uses a fake server.

10.5.7 ARP Attacks — Spoofing and Poisoning

ARP has no authentication mechanism. Any host can send an unsolicited ARP Reply (called a gratuitous ARP) claiming any IP-to-MAC mapping, and all hosts that receive it will update their ARP cache without question.

  1. Normal state: All hosts have correct ARP caches — PC1 knows router R1's real MAC, R1 knows PC1's real MAC
  2. Threat actor sends gratuitous ARP — spoofing: Sends two unsolicited ARP Replies: "MAC address for 10.0.0.1 (R1/gateway) = CC:CC:CC (attacker's MAC)" and "MAC address for 10.0.0.11 (PC1) = CC:CC:CC (attacker's MAC)"
  3. ARP cache poisoning: All hosts update their ARP caches with the false mappings — R1 and PC1 now think the attacker's MAC belongs to each other
  4. Man-in-the-middle established: All traffic between PC1 and R1 now flows through the attacker, who can capture, read, and modify it before forwarding
  Before attack:
  PC1 ARP cache:  10.0.0.1 → AA:AA:AA (R1's real MAC) ✅
  R1 ARP cache:   10.0.0.11 → BB:BB:BB (PC1's real MAC) ✅

  After ARP poisoning:
  PC1 ARP cache:  10.0.0.1 → CC:CC:CC (attacker's MAC) ❌
  R1 ARP cache:   10.0.0.11 → CC:CC:CC (attacker's MAC) ❌

  Result:
  PC1 sends traffic to "gateway" → actually goes to attacker
  R1 sends traffic to "PC1" → actually goes to attacker
  Attacker reads/modifies all traffic and forwards it → neither side notices
✅
ARP spoofing vs ARP poisoning: These are two stages of the same attack. Spoofing = sending the fake gratuitous ARP. Poisoning = the resulting state — the victim's ARP cache now has incorrect entries. Mitigation: Dynamic ARP Inspection (DAI) — validates ARP packets against a DHCP snooping binding table before updating the ARP cache.

10.5.8 Address Spoofing Attack

IP Address Spoofing

Threat actor hijacks a valid IP address belonging to another device on the subnet, or uses a random IP from the same subnet. Difficult to detect because the forged IP appears to belong to a legitimate host. Mitigation: IPSG (IP Source Guard).

MAC Address Spoofing

Threat actor changes their NIC's MAC address to match a known target device's MAC address. The switch receives frames with the spoofed MAC and updates its MAC table — mapping that MAC to the attacker's port. All traffic destined for the legitimate device is now forwarded to the attacker.

🚨
Layer 2 has no mechanism to verify the source of MAC addresses. The switch blindly trusts whatever MAC address appears in the source field of a frame. This is an inherent architectural vulnerability — no switch feature can detect MAC spoofing at the hardware level alone. IPSG is required to mitigate this.

10.5.9 STP Attack

Goal: Force the attacker's host to become the STP root bridge — capturing all traffic in the switched domain.

  1. Threat actor sends crafted BPDUs advertising a very low (or zero) bridge priority — lower than any legitimate switch in the network
  2. STP election process sees this lower priority and elects the attacker's host as the new root bridge
  3. STP recalculates the entire topology with the attacker's host as the central reference point
  4. All traffic in the switched domain now flows through the attacker's host — enabling capture, modification, or redirection of all frames
  Before STP attack:
  S1 (priority 4096) = root bridge — legitimate
  S2, S3 calculate paths toward S1

  During STP attack:
  Attacker sends BPDUs with priority 0
  STP election: 0 < 4096 → attacker wins!
  New topology: all switches recalculate paths toward attacker's host
  All traffic now passes through the attacker
✅
Mitigation: BPDU Guard on all access ports. Access ports connected to end devices should never receive BPDUs — only switches send BPDUs. BPDU Guard immediately err-disables any port that receives a BPDU, preventing the attacker's host from participating in STP elections.

10.5.10 CDP Reconnaissance

CDP (Cisco Discovery Protocol) is enabled by default on all Cisco devices. It sends periodic, unencrypted, unauthenticated broadcasts containing:

  • Device IP address
  • Exact IOS software version (including minor release number)
  • Device model and platform
  • Device capabilities (router, switch, etc.)
  • Native VLAN
🚨
The IOS version is the most dangerous disclosure. An attacker connected to a Cisco device receives CDP broadcasts automatically. The exact IOS version number allows the attacker to look up every known vulnerability for that specific version — without needing any credentials.
CDP and LLDP mitigation commands 
! Disable CDP globally (all ports stop sending/receiving CDP):
Switch(config)# no cdp run

! Re-enable CDP globally:
Switch(config)# cdp run

! Disable CDP on a specific interface (untrusted edge ports):
Switch(config)# interface fa0/1
Switch(config-if)# no cdp enable

! Re-enable CDP on a specific interface:
Switch(config-if)# cdp enable

! LLDP (Link Layer Discovery Protocol — vendor-neutral equivalent of CDP)
! is ALSO vulnerable to reconnaissance attacks:
Switch(config)# no lldp run               ! Disable LLDP globally
Switch(config-if)# no lldp transmit       ! Disable LLDP transmit on this port
Switch(config-if)# no lldp receive        ! Disable LLDP receive on this port
💡
Best practice: Disable CDP on all edge ports connecting to untrusted devices or users. Keep CDP enabled on internal network ports where it is used for legitimate network management and troubleshooting. LLDP should also be disabled on untrusted ports.

🎯Common Exam Traps — Module 10▾
❌
Trap 1: Layer 2 compromise bypasses ALL upper-layer security.
If a threat actor captures Layer 2 frames, VPNs, firewalls, and IPS systems at Layer 3–7 are useless. Layer 2 security is foundational — not optional.
❌
Trap 2: MAC flooding makes the switch behave like a hub — it does NOT go offline.
The switch keeps running but floods all frames because it can't look up destination MACs. Flooding is limited to the local VLAN. The attacker captures all traffic on that VLAN with a packet sniffer.
❌
Trap 3: DHCP starvation and DHCP spoofing are different attacks.
Starvation = exhaust the IP pool → DoS (clients get no IP). Spoofing = rogue DHCP server → clients get wrong gateway/DNS → MitM or DoS. Both mitigated by DHCP Snooping but they are completely different in mechanism and goal.
❌
Trap 4: VLAN double-tagging is UNIDIRECTIONAL.
The attacker can send TO the target VLAN but cannot receive traffic back through this mechanism. Return traffic from the victim VLAN uses normal routing and never crosses back to the attacker's native VLAN. This is a critical limitation the exam tests directly.
❌
Trap 5: Gratuitous ARPs are legitimate — but attackers abuse them.
Gratuitous ARPs are unsolicited ARP Replies that hosts use legitimately (e.g., to announce a new IP after reconfiguration). The problem: there is NO verification mechanism. Any host can claim any IP-to-MAC mapping and all devices on the subnet will update their ARP caches.
❌
Trap 6: ARP spoofing and ARP poisoning are two stages — not two separate attacks.
Spoofing = sending the fake gratuitous ARP (the action). Poisoning = the resulting corrupted ARP cache (the outcome). The exam uses both terms — know that they refer to the same attack at different stages. Both mitigated by DAI.
❌
Trap 7: STP attack uses low bridge priority — not high.
In STP, lower priority wins the root bridge election. The attacker sends BPDUs with priority 0 (lowest possible) to guarantee election as root bridge. Once elected, all traffic passes through the attacker's host.
❌
Trap 8: CDP is enabled by default on ALL Cisco devices.
CDP broadcasts are sent on every Cisco interface by default — unencrypted and unauthenticated. The exact IOS version is included, allowing attackers to identify known vulnerabilities without any credentials. Disable with no cdp enable on untrusted ports.
⚠️
Trap 9: RADIUS vs TACACS+.
RADIUS = open standard, UDP, encrypts password only → network access (VPN, wireless). TACACS+ = Cisco proprietary, TCP, encrypts entire packet, separates AAA → device administration (Cisco routers/switches). Wrong answer on this distinction is very common.
⚠️
Trap 10: 802.1X — the switch does NOT make the authentication decision.
The switch is the authenticator (intermediary) — it passes credentials to the RADIUS server and enforces the server's decision. The RADIUS/authentication server makes all access decisions. Three roles: Supplicant (client), Authenticator (switch/AP), Authentication Server (RADIUS).
⚠️
Trap 11: ESA monitors SMTP (email). WSA monitors HTTP/HTTPS (web).
Two separate appliances with different functions. ESA = email filtering and security. WSA = web traffic filtering and security. Both integrate with Cisco Talos threat intelligence updated every 3–5 minutes.
⚠️
Trap 12: Cisco Talos updates ESA every 3–5 minutes.
The specific time interval (3–5 minutes) is a direct exam question. This rapid update cycle is what makes the ESA effective against new and evolving threats.
⚠️
Trap 13: MAC flooding scope is limited to the local VLAN.
VLAN segmentation still provides protection even during a flooding attack. The attacker can only see traffic within the VLAN they are connected to — not traffic on other VLANs.
⚠️
Trap 14: VLAN double-tagging requires the attacker to be on the native VLAN.
The attack only works when the attacker's port is in the same VLAN as the native VLAN of the trunk port. Changing the native VLAN to an unused VLAN prevents this attack entirely.
✅
Quick attack-to-mitigation memory map:

MAC flooding → Port Security
DHCP attacks (both) → DHCP Snooping
ARP attacks → DAI (Dynamic ARP Inspection)
IP/MAC spoofing → IPSG (IP Source Guard)
