6.1EtherChannel Operation▾

6.1.1 Link Aggregation

You already know from Module 5 that STP blocks redundant links to prevent Layer 2 loops. But what if you need both redundancy AND more bandwidth between switches? Adding more cables won't help — STP will block them.

EtherChannel solves this. It groups multiple physical Ethernet links into one single logical link. STP sees the entire bundle as one link — so it never blocks the individual physical ports inside it.

  Without EtherChannel (STP blocks redundant link):
  [S1] ══Fa0/1══ [S2]   ← active (STP forwarding)
  [S1] ══Fa0/2══ [S2]   ← BLOCKED by STP — wasted capacity

  With EtherChannel (both links active):
  [S1] ══Fa0/1══╗
                ╠══ Port-Channel 1 ══ STP sees ONE logical link
  [S1] ══Fa0/2══╝
  Both links carry traffic — load balanced — STP never blocks either
💡
EtherChannel provides fault-tolerance, load sharing, increased bandwidth, and redundancy between switches, routers, and servers — all while remaining transparent to STP.

6.1.2 EtherChannel and Port Channels

EtherChannel was originally developed by Cisco as a switch-to-switch technique. When an EtherChannel is configured, the resulting virtual interface is called a port channel. The physical interfaces are bundled into this port channel interface.

ConceptDetail
Port channelThe virtual logical interface created when EtherChannel is configured. Referred to as Port-channel1, Po1 etc. in IOS
Member portsThe physical interfaces bundled into the port channel (e.g. Fa0/1, Fa0/2)
BandwidthCombined — two 1 Gbps links = 2 Gbps port channel. Eight 1 Gbps links = 8 Gbps port channel
ConfigurationApplied to the port channel interface — automatically propagated to all member ports

6.1.3 Advantages of EtherChannel

AdvantageExplanation
Simplified configurationConfigure the port channel interface once — settings apply to all member ports automatically. No need to configure each physical port individually.
No hardware upgrade neededUses existing switch ports — no need for a faster or more expensive single link to increase bandwidth
Load balancingTraffic distributed across all physical links using source/destination MAC or IP hashing. Method depends on hardware platform.
STP compatibilitySTP sees the entire EtherChannel as one logical link. If STP blocks the port channel, it blocks all member ports. If STP forwards, all member ports forward.
Redundancy without STP recalculationIf one physical link in the bundle fails, traffic shifts to remaining links automatically. No STP topology recalculation — the logical link is still up.
🎯 MOST IMPORTANT ADVANTAGE FOR THE EXAM
Loss of one physical link within an EtherChannel does NOT trigger an STP recalculation. STP still sees the port channel interface as up. Traffic automatically redistributes across the remaining active physical links — no topology change, no convergence delay.

6.1.4 Implementation Restrictions

Violating any of these restrictions will prevent the EtherChannel from forming. These are all exam-tested:

RestrictionDetail
No mixed interface typesFastEthernet and GigabitEthernet cannot be in the same EtherChannel — all member ports must be the same type
Maximum 8 ports per EtherChannelUp to 8 physical links per bundle. Max bandwidth: 800 Mbps (Fast EtherChannel) or 8 Gbps (Gigabit EtherChannel)
Maximum 6 EtherChannels on Catalyst 2960The 2960 supports up to 6 EtherChannel groups total
All ports must have identical configurationSpeed, duplex, VLAN assignment, native VLAN, trunk allowed VLANs — all must match on both ends of the link
All ports must be Layer 2All member ports in an EtherChannel must be configured as Layer 2 switchports
Configure via port channel interfaceApply settings to the port channel interface — it propagates to all member ports. Configuring individual member ports after EtherChannel formation can cause compatibility issues.

6.1.5 AutoNegotiation Protocols

EtherChannels can be formed three ways:

🔵 PAgP — Cisco Proprietary
  • Port Aggregation Protocol
  • Cisco devices only
  • Modes: on, desirable, auto
  • Packets sent every 30 seconds
✅ LACP — IEEE Standard (Preferred)
  • Link Aggregation Control Protocol
  • IEEE 802.3ad / 802.1AX
  • Works in multivendor environments
  • Modes: on, active, passive
  • Supports 8 active + 8 standby links
⚠️ Static (On Mode) — No Negotiation
  • Forces EtherChannel without any protocol
  • Both sides must be set to on
  • No compatibility checking — risky
  • No negotiation packets exchanged

6.1.6 PAgP Operation

PAgP (Port Aggregation Protocol) is Cisco-proprietary. It automatically creates EtherChannel links by sending PAgP packets between capable ports to negotiate channel formation. PAgP also manages the channel after formation — sending packets every 30 seconds to verify configuration consistency.

PAgP ModeBehaviorInitiates Negotiation?
OnForces EtherChannel with no PAgP packets. Other side must also be on.❌ No — bypasses PAgP entirely
DesirableActive — sends PAgP packets to initiate negotiation. Forms channel with desirable or auto.✅ Yes — actively initiates
AutoPassive — responds to PAgP packets but never sends first. Waits for the other side.❌ No — only responds
💡
PAgP also ensures that when an EtherChannel is created, all ports have the same type of configuration. Any port modification after creation also changes all other channel ports — this is enforced by PAgP automatically.

6.1.7 PAgP Mode Compatibility

S1 ModeS2 ModeEtherChannel Forms?Why
OnOn✅ YesBoth force the channel — no negotiation needed
OnDesirable❌ Noon doesn't respond to PAgP packets
OnAuto❌ Noon doesn't respond to PAgP packets
DesirableDesirable✅ YesBoth actively negotiate — channel forms
DesirableAuto✅ YesDesirable initiates, auto responds
AutoDesirable✅ YesDesirable initiates, auto responds
AutoAuto❌ NoBoth passive — neither initiates — channel never forms
❌
Auto + Auto = NO EtherChannel. Both sides are passive — each waits for the other to start negotiation. Neither does. This is the single most common PAgP misconfiguration. At least one side must be desirable.

6.1.8 LACP Operation

LACP (Link Aggregation Control Protocol) is an IEEE standard (IEEE 802.3ad / IEEE 802.1AX) that performs the same function as PAgP but works across any vendor's equipment. LACP is the preferred protocol for new deployments.

LACP ModeBehaviorInitiates Negotiation?
OnForces EtherChannel with no LACP packets. Other side must also be on.❌ No — bypasses LACP entirely
ActiveSends LACP packets to initiate negotiation. Forms channel with active or passive.✅ Yes — actively initiates
PassiveResponds to LACP packets but does not initiate. Waits for the other side.❌ No — only responds
🎯 LACP STANDBY LINKS — UNIQUE TO LACP
LACP supports up to 8 active links + 8 standby links (16 total configured, 8 active at a time).

If one active link fails, a standby link automatically becomes active — immediately, with no STP recalculation.

PAgP has no standby link concept — only 8 active links maximum.

6.1.9 LACP Mode Compatibility

S1 ModeS2 ModeEtherChannel Forms?Why
OnOn✅ YesBoth force the channel — no negotiation needed
OnActive❌ Noon doesn't respond to LACP packets
OnPassive❌ Noon doesn't respond to LACP packets
ActiveActive✅ YesBoth actively negotiate — channel forms
ActivePassive✅ YesActive initiates, passive responds
PassiveActive✅ YesActive initiates, passive responds
PassivePassive❌ NoBoth passive — neither initiates — channel never forms
✅
PAgP vs LACP parallel — the modes map directly:
PAgP desirable ↔ LACP active (both = initiator)
PAgP auto ↔ LACP passive (both = responder)
on is identical in both — forces channel, no packets, other side must also be on.
6.2Configure EtherChannel▾

6.2.1 Configuration Guidelines

Before configuring EtherChannel, all four of these requirements must be satisfied on all member interfaces:

  1. EtherChannel support — All Ethernet interfaces must support EtherChannel. No requirement that interfaces be physically adjacent or on the same module.
  2. Speed and duplex match — All interfaces in the bundle must operate at the same speed and duplex mode. A half-duplex port on one switch and full-duplex on the other = no EtherChannel.
  3. VLAN match — All interfaces must be assigned to the same VLAN (access mode) OR all configured as trunks. You cannot mix access and trunk ports in one EtherChannel.
  4. Allowed VLAN range match — If trunking, all interfaces must have the identical allowed VLAN range. Different allowed VLAN lists prevent EtherChannel formation even if modes are compatible.
🚨
Configure settings on the port channel interface — not on individual member ports. After EtherChannel is formed, changes applied to the port channel propagate to all members. Changes applied directly to a member port can cause incompatibility and STP errors (ports may go err-disabled).

6.2.2 LACP Configuration Example (Three Steps)

Configuring EtherChannel always follows the same three-step sequence regardless of protocol:

Step 1
Select the interfaces using interface range
Use interface range to select all the physical ports that will be part of the EtherChannel bundle in one command.
Step 2
Create the port channel and assign the mode
Use channel-group [id] mode [mode] to create the logical port channel interface and specify PAgP or LACP mode. IOS automatically creates the port channel interface and you will see console messages as ports briefly cycle.
Step 3
Configure the port channel interface
Enter interface port-channel [id] and configure trunking, VLANs, or other settings here. Settings propagate to all member ports automatically.
S1 — Complete LACP EtherChannel Configuration 
! STEP 1: Select the physical interfaces
S1(config)# interface range FastEthernet 0/1 - 2

! STEP 2: Create port channel with LACP active mode
S1(config-if-range)# channel-group 1 mode active
Creating a port-channel interface Port-channel 1

! IOS console messages -- normal, not errors:
*Mar 21 00:02:28.184: %LINEPROTO-5-UPDOWN: Line protocol on Interface
  FastEthernet0/1, changed state to down
*Mar 21 00:02:28.193: %LINEPROTO-5-UPDOWN: Line protocol on Interface
  FastEthernet0/2, changed state to down
*Mar 21 00:02:36.179: %LINEPROTO-5-UPDOWN: Line protocol on Interface
  FastEthernet0/1, changed state to up
*Mar 21 00:04:34.114: %LINK-3-UPDOWN: Interface Port-channel1, changed state to up
*Mar 21 00:04:35.121: %LINEPROTO-5-UPDOWN: Line protocol on Interface
  Port-channel1, changed state to up

! STEP 3: Configure the port channel interface
S1(config-if-range)# exit
S1(config)# interface port-channel 1
S1(config-if)# switchport mode trunk
S1(config-if)# switchport trunk allowed vlan 1,2,20
S2 — Mirror configuration (LACP active or passive — both work with S1 active) 
S2(config)# interface range FastEthernet 0/1 - 2
S2(config-if-range)# channel-group 1 mode active
S2(config-if-range)# exit
S2(config)# interface port-channel 1
S2(config-if)# switchport mode trunk
S2(config-if)# switchport trunk allowed vlan 1,2,20
PAgP Alternative — replace mode active with mode desirable 
! For PAgP instead of LACP, use 'desirable' instead of 'active'
! Everything else is identical

S1(config)# interface range FastEthernet 0/1 - 2
S1(config-if-range)# channel-group 1 mode desirable
S1(config-if-range)# exit
S1(config)# interface port-channel 1
S1(config-if)# switchport mode trunk
S1(config-if)# switchport trunk allowed vlan 1,2,20
💡
Channel group number: The number after channel-group (e.g., 1) is a local identifier — it does not have to match on both switches. What matters is that the physical ports on both sides connect to each other and have compatible modes. However, Cisco best practice is to use the same group number on both ends for clarity.

6.3.2 Common Issues with EtherChannel Configurations

All four of these are directly tested on the CCNA exam. Each one prevents EtherChannel from forming:

IssueWhy It Breaks EtherChannelFix
Ports in different VLANsAll access ports must be in the same VLAN. Ports with different native VLANs cannot form an EtherChannel.Assign all member ports to the same VLAN, or configure all as trunks
Trunking on some ports but not allNever configure trunking on individual member ports. Configure trunk on the port channel interface only.Remove trunk config from member ports; configure on port-channel interface instead
Different allowed VLAN rangesIf allowed VLAN lists differ, ports do not form EtherChannel — even when PAgP/LACP modes are compatible.Ensure identical allowed VLAN range on all member ports (via port channel interface)
Incompatible negotiation modesOn + active/passive = no channel. Auto + auto = no channel. Passive + passive = no channel.Ensure at least one side is desirable (PAgP) or active (LACP). Or set both to on.
⚠️
Easy to confuse — PAgP/LACP vs DTP: Both operate on trunk links but serve different purposes. PAgP/LACP negotiate EtherChannel formation (link aggregation). DTP negotiates trunk formation. When configuring an EtherChannel trunk, configure EtherChannel (PAgP/LACP) first, then configure trunking on the port channel interface.

6.3.3 Troubleshoot EtherChannel Example

🔍 TROUBLESHOOT SCENARIO
S1 and S2 have EtherChannel configured on Fa0/1 and Fa0/2. The EtherChannel is not operational. Find and fix the problem.

Step 1 — Check the summary:

show etherchannel summary — identify the problem 
S1# show etherchannel summary
Group  Port-channel  Protocol    Ports
------+-------------+-----------+---------------------------
1      Po1(SD)         -      Fa0/1(D)    Fa0/2(D)
!           ↑↑                      ↑
!           SD = Layer2, DOWN        D = port is down
! EtherChannel is completely non-functional

Step 2 — Check the running config on both switches:

show run | begin interface port-channel — compare both sides 
S1# show run | begin interface port-channel
interface FastEthernet0/1
 channel-group 1 mode on        ← S1 is set to "on"

interface FastEthernet0/2
 channel-group 1 mode on        ← S1 is set to "on"
!================================================
S2# show run | begin interface port-channel
interface FastEthernet0/1
 channel-group 1 mode desirable ← S2 is set to "desirable"

interface FastEthernet0/2
 channel-group 1 mode desirable ← S2 is set to "desirable"

! PROBLEM: S1 = "on", S2 = "desirable" -- incompatible!
! "on" forces EtherChannel but sends NO negotiation packets
! "desirable" sends PAgP packets and waits for a response
! Since "on" never responds to PAgP, the channel never forms

Step 3 — Fix it (critical order of operations):

Fix — remove and recreate port channel (do NOT change mode directly) 
! WARNING: Do NOT just change channel-group mode on active ports
! Doing so causes STP to put the ports into err-disabled state
! Always remove the port channel first, then recreate

S1(config)# no interface port-channel 1       ! Remove first
S1(config)# interface range fa0/1 - 2
S1(config-if-range)# channel-group 1 mode desirable   ! Recreate
S1(config-if-range)# no shutdown
S1(config-if-range)# exit
S1(config)# interface port-channel 1
S1(config-if)# switchport mode trunk
S1(config-if)# switchport trunk allowed vlan 1,2,20
S1(config-if)# end

Step 4 — Verify the fix:

show etherchannel summary — confirm operational 
S1# show etherchannel summary
Group  Port-channel  Protocol    Ports
------+-------------+-----------+---------------------------
1      Po1(SU)         PAgP      Fa0/1(P)    Fa0/2(P)
!           ↑↑                        ↑
!           SU = in Use (working)     P = bundled
! EtherChannel is now operational
🚨
Critical order of operations: Always use no interface port-channel [id] to remove the port channel BEFORE reconfiguring the channel-group mode. Changing the mode directly on active member ports causes STP to err-disable the ports. The remove-then-recreate approach avoids this.

🎯Common Exam Traps — Module 6▾
❌
Trap 1: Auto + Auto = no EtherChannel (PAgP). Passive + Passive = no EtherChannel (LACP).
Both sides are passive — each waits for the other to initiate. Neither does. At least one side must be desirable (PAgP) or active (LACP) for the channel to form.
❌
Trap 2: On + Desirable or On + Active = no EtherChannel.
The on mode forces EtherChannel without sending any negotiation packets. A side set to desirable or active sends negotiation packets and waits for a response — on never responds. The only working combination with on is on + on.
❌
Trap 3: Losing one physical link in an EtherChannel does NOT trigger STP recalculation.
STP sees the port channel as one logical link. As long as at least one physical link is up, the port channel is still up from STP's perspective. Traffic redistributes automatically — no topology change, no convergence delay.
❌
Trap 4: Configure settings on the port channel interface — never on individual member ports.
Changes on the port channel propagate to all members. Changes on individual member ports after EtherChannel formation cause incompatibility errors and may err-disable the ports.
❌
Trap 5: When reconfiguring EtherChannel mode, remove and recreate — never change directly.
Always use no interface port-channel [id] first, then recreate with the correct mode. Changing channel-group mode directly on active member ports causes STP to err-disable those ports.
❌
Trap 6: All member interfaces must match on speed, duplex, VLAN assignment, and trunk allowed list.
Any single mismatch in any of these four prevents EtherChannel formation — even if PAgP/LACP modes are correctly and compatibly configured on both sides.
❌
Trap 7: Interface types cannot be mixed.
FastEthernet and GigabitEthernet cannot be bundled in the same EtherChannel. All member ports must be the same interface type and speed.
⚠️
Trap 8: Maximum 8 physical ports per EtherChannel. LACP also supports 8 standby ports.
LACP uniquely supports 8 active + 8 standby links (16 total configured). If an active link fails, a standby takes over immediately. PAgP has no standby concept — only 8 active links maximum.
⚠️
Trap 9: SU = working, SD = broken in show etherchannel summary.
The two-letter code next to the port channel number is the fastest diagnostic. SU (Layer 2, in Use) = operational. SD (Layer 2, Down) = not working. P next to a member port = bundled and active.
⚠️
Trap 10: PAgP = Cisco proprietary. LACP = IEEE standard (multivendor).
PAgP only works between Cisco devices. LACP (IEEE 802.3ad / 802.1AX) works between any vendor that supports the standard. LACP is preferred when connecting Cisco to non-Cisco equipment.
⚠️
Trap 11: EtherChannel and DTP are different protocols with different purposes.
PAgP and LACP negotiate EtherChannel (link aggregation). DTP negotiates trunking. Both operate on the same link simultaneously. Configure EtherChannel first (PAgP or LACP), then configure trunking on the port channel interface.
✅
Quick mode compatibility summary:

PAgP: desirable+desirable ✅  |  desirable+auto ✅  |  auto+auto ❌  |  on+on ✅  |  on+desirable/auto ❌

LACP: active+active ✅  |  active+passive ✅  |  passive+passive ❌  |  on+on ✅  |  on+active/passive ❌

Memory trick: At least one side must be "active" in both protocols (desirable for PAgP, active for LACP). Two passive sides = no channel. on only pairs with on.
