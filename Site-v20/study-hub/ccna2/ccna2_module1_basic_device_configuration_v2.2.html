1.1Configure a Switch with Initial Settings▾

1.1.1 Switch Boot Sequence

When a Cisco switch is powered on it goes through a 5-step boot sequence before it is ready to configure. Each step happens in a specific location — knowing which is which is an exam question.

1
POST — Power-On Self-Test (stored in ROM)
Tests the CPU subsystem, DRAM, and the flash file system portion. If POST fails the switch will not proceed.
2
Boot Loader loads (stored in ROM)
A small program that runs immediately after POST succeeds. This is the failsafe — it can access flash even when IOS is missing or corrupt.
3
CPU Initialization
Boot loader initializes CPU registers — controls physical memory mapping, quantity, and speed.
4
Flash File System Initialization
Boot loader initializes the flash file system on the system board.
5
IOS Loads (from Flash)
Boot loader locates and loads the IOS image from flash into memory, then hands control to IOS. IOS then initializes interfaces using startup-config.
🎯 EXAM TIP — Where does each thing live?
  • POST → stored in ROM
  • Boot Loader → stored in ROM
  • IOS → loaded from Flash
  • startup-config (config.text) → stored in Flash
  • running-config → stored in RAM (lost on reload)

1.1.2 The boot system Command

If the BOOT environment variable is not set, the switch loads the first executable file it finds in flash. Use boot system to specify exactly which IOS image to load.

Set the IOS boot image path 
S1(config)# boot system flash:/c2960-lanbasek9-mz.150-2.SE/c2960-lanbasek9-mz.150-2.SE.bin

! Verify which IOS will load on next boot
S1# show boot
Part of CommandMeaning
boot systemMain command — specifies where to find IOS
flash:Storage device (flash memory)
c2960-lanbasek9-mz.150-2.SE/Path to the directory containing the IOS file
c2960-lanbasek9-mz.150-2.SE.binThe IOS image filename
💡
The startup-config file is named config.text and is stored in flash. After IOS loads, it reads this file to restore the device configuration.

1.1.3 Switch LED Indicators

The Cisco Catalyst 2960 has a Mode button that toggles the port LED display between STAT, DUPLX, SPEED, and PoE modes. Six status LEDs provide quick health information.

SYST — System LED
Color / StateMeaning
OffNo power
GreenOperating normally
AmberPowered but malfunctioning
RPS — Redundant Power System LED
Color / StateMeaning
OffRPS is off or not connected
GreenRPS connected and ready to provide backup power
Blinking greenRPS connected but providing power to another device
AmberRPS in standby or fault condition
Blinking amberInternal PSU failed — RPS is now powering this switch

Color / StateMeaning
OffNo link, or port was administratively shut down
GreenLink is present
Blinking greenActivity — port is sending or receiving data
Alternating green-amberLink fault
AmberPort blocked by STP — normal for first ~30 seconds after activation
Blinking amberPort blocked to prevent a loop
DUPLX — Port Duplex LED
Color / StateMeaning

Green (port LED)Port is in full-duplex mode
SPEED — Port Speed LED
Color / StateMeaning

Green100 Mbps

PoE — Power over Ethernet LED
Color / StateMeaning

⚠️
Amber STAT LED ≠ hardware failure. A port showing amber in STAT mode means STP is blocking it — this is completely normal for the first ~30 seconds after a port is activated. Students often panic and think something is broken. It is not.

1.1.4 Recovering from a System Crash

If IOS is missing or damaged, the boot loader provides a CLI to access flash directly. This is how you recover or replace a corrupted IOS image.

Steps to enter boot loader mode:

  1. Connect a PC to the switch console port. Configure terminal emulation software (PuTTY, etc.).
  2. Unplug the switch power cord.
  3. Reconnect the power cord — within 15 seconds, press and hold the Mode button while the System LED is still flashing green.
  4. Continue holding until the System LED briefly goes amber then solid green — then release the Mode button.
  5. The switch: prompt appears in the terminal emulation software.
Boot loader commands — recover from crash 
switch: set              ! View current BOOT environment variable
switch: flash_init       ! Initialize the flash file system
switch: dir flash:       ! List files and directories in flash

! Example output of dir flash:
!   2  -rwx  11834846   c2960-lanbasek9-mz.150-2.SE8.bin
!   3  -rwx  2072        multiple-fs

! Set new IOS boot path
switch: BOOT=flash:c2960-lanbasek9-mz.150-2.SE8.bin

! Verify the change
switch: set

! Boot the switch with the new IOS
switch: boot
💡
The boot loader can also be used to recover a lost or forgotten enable password — one of the most common real-world support tasks for network administrators.

1.1.5 Switch Management Access

A switch needs an IP address to be managed remotely. This IP address is assigned to a Switch Virtual Interface (SVI) — a virtual interface, not a physical port.

  [Admin PC] ----console cable---- [S1 Switch]
                                        |
                                   VLAN 99 SVI
                                   IP: 172.17.99.11/24
                                   Gateway: 172.17.99.1

  After initial config, manage S1 remotely via SSH to 172.17.99.11
What You NeedWhy
IP address on an SVIGives the switch a management address
Subnet maskDefines the local network
Default gatewayRequired only if managing from a different network
🖥️
Default management VLAN is VLAN 1. Best practice: use a dedicated management VLAN other than VLAN 1 (e.g., VLAN 99) for security. This keeps management traffic isolated from user data and the default VLAN.
⚠️
The SVI IP address is for management access only — it does NOT enable the switch to route Layer 3 traffic between VLANs. To do inter-VLAN routing on a switch, you need ip routing (Module 4).

1.1.6 Switch SVI Configuration Example

Three-step process to configure remote management access on a switch:

Step 1 — Configure the Management SVI

S1 — Configure management SVI on VLAN 99 
S1# configure terminal
S1(config)# interface vlan 99
S1(config-if)# ip address 172.17.99.11 255.255.255.0
S1(config-if)# ipv6 address 2001:db8:acad:99::1/64
S1(config-if)# no shutdown
S1(config-if)# end
S1# copy running-config startup-config

Step 2 — Configure the Default Gateway

S1 — Set default gateway for remote management 
S1# configure terminal
S1(config)# ip default-gateway 172.17.99.1
S1(config)# end
S1# copy running-config startup-config

Step 3 — Verify

S1 — Verify SVI configuration 
S1# show ip interface brief
Interface     IP-Address     OK? Method   Status    Protocol
Vlan99        172.17.99.11   YES manual   down      down

S1# show ipv6 interface brief
Vlan99                 [down/down]
    FE80::C27B:BCFF:FEC4:A9C1
    2001:DB8:ACAD:99::1
🚨
SVI shows down/down — this is expected if:
1. VLAN 99 has not yet been created in the VLAN database, OR
2. No device is connected to a port assigned to VLAN 99

Both conditions must be true for the SVI to come up. Creating the SVI and assigning an IP is not enough by itself.

1.2Configure Switch Ports▾

1.2.1 Duplex Communication

ModeDescriptionCollision Domain?When Used
Full-duplexBoth ends transmit and receive simultaneouslyNo — collision detection disabledAll modern switches, dedicated links
Half-duplexOnly one direction at a timeYes — collisions can occurOlder hardware (hubs), legacy setups
  • Gigabit Ethernet and 10 Gb NICs require full-duplex to operate
  • Full-duplex: collision detection on the NIC is disabled
  • Full-duplex = 100% efficiency in both directions — effectively doubles usable bandwidth
  • Fiber-optic ports (1000BASE-SX): always full-duplex at one preset speed

1.2.2 Configure Switch Ports at the Physical Layer

S1 — Manually set duplex and speed on a port 
S1# configure terminal
S1(config)# interface FastEthernet 0/1
S1(config-if)# duplex full
S1(config-if)# speed 100
S1(config-if)# end
S1# copy running-config startup-config
SettingDefault (Catalyst 2960/3560)Notes
Duplexauto10/100/1000 ports: full-duplex required at 1000 Mbps
SpeedautoAutonegotiates with connected device
🎯 EXAM TIP — Duplex Mismatch
A duplex mismatch is one of the most common causes of slow performance or intermittent connectivity. One side full-duplex, the other half-duplex:

  • The half-duplex side sees collisions and late collisions
  • The full-duplex side sees input errors and CRC errors
  • Both sides think they are up — traffic flows, just very poorly
  • Root cause: autonegotiation failure on one side

Fix: manually set duplex full and speed on both ends of the connection.

1.2.3 Auto-MDIX

Auto-MDIX (automatic medium-dependent interface crossover) eliminates the need to choose between straight-through and crossover cables. The interface detects the cable type automatically and adjusts.

FeatureDetail
Without Auto-MDIXMust use correct cable type: straight-through (switch to host/router) or crossover (switch to switch)
With Auto-MDIXEither cable type works — interface adjusts automatically
RequirementSpeed and duplex MUST be set to auto for Auto-MDIX to work
Default on 2960/3560Enabled by default
Not available onOlder Catalyst 2950 and 3550 switches
Enable Auto-MDIX and verify 
S1(config-if)# mdix auto

! Verify Auto-MDIX state on a specific interface
S1# show controllers ethernet-controller fa0/1 phy | include MDIX
 Auto-MDIX           :  On   [AdminState=1   Flags=0x00052248]

1.2.6 Network Access Layer Issues

The first line of show interfaces output tells you everything about the interface state. Learn to read this instantly:

Status LineMeaningCommon Cause
up / upFully operationalNormal — interface working correctly
up / downPhysical layer up, data link problemEncapsulation mismatch, error-disabled, hardware issue
down / downPhysical and data link both downCable unplugged, device powered off, other end admin-down
administratively down / downManually disabledshutdown command was applied to this interface

1.2.7 Interface Input and Output Errors

The error counters in show interfaces output pinpoint Layer 1 and Layer 2 problems. Know these for the exam:

Error TypeDescriptionCommon Cause
Input ErrorsTotal of all receive-side errorsSummary — includes all errors below
RuntsFrames shorter than 64 bytes (minimum Ethernet size)Malfunctioning NIC, collisions
GiantsFrames larger than 1518 bytes (maximum Ethernet size)Malfunctioning NIC, jumbo frame misconfiguration
CRCCalculated checksum ≠ received checksumElectrical interference, damaged cable, loose connection — cable noise
Output ErrorsTotal transmit-side errorsSummary of transmit failures
CollisionsNormal in half-duplex; never in full-duplexHalf-duplex operation or duplex mismatch
Late CollisionsCollision occurs after first 512 bits transmittedCable too long, duplex mismatch (most common)
🎯 EXAM TIP — Diagnose the Error Type
  • High CRC errors = physical cable problem or electrical interference. Check and replace the cable.
  • Late collisions = duplex mismatch OR cable too long. First check duplex settings on both ends.
  • Collisions on full-duplex = impossible in correct config — this is a clear sign of a duplex mismatch.
  • A properly designed and configured network should never have late collisions.

1.2.8 Troubleshooting Network Access Layer Issues

Use this structured approach when a switch port has no connection or a bad connection:

🔍 TROUBLESHOOT — Interface is DOWN
1. Check cables — wrong type? damaged connectors? Replace if suspect.
2. If still down: check for speed mismatch — manually set the same speed on both ends.
🔍 TROUBLESHOOT — Interface is UP but Performance is Bad
1. Run show interfaces — look for high counts of runts, giants, CRC errors = noise on the cable. Find and remove noise source. Verify cable type and max length.
2. Look for collisions or late collisions = duplex mismatch. Manually set duplex full on both ends.
show interfaces — key counters to watch 
S1# show interfaces fastEthernet 0/18
FastEthernet0/18 is up, line protocol is up (connected)
...
     0 runts, 0 giants, 0 throttles
     3 input errors, 3 CRC, 0 frame, 0 overrun, 0 ignored
     0 watchdog, 74 multicast, 0 pause input
     ...
     8 output errors, 1790 collisions, 10 interface resets
     235 late collision, 0 deferred

! 3 CRC errors: possible cable noise -- inspect the cable
! 1790 collisions + 235 late collisions: duplex mismatch suspected
1.3Secure Remote Access▾

1.3.1 Telnet Operation

FeatureTelnet
TCP Port23
EncryptionNone — everything sent in plaintext
What is exposedUsername, password, and all management data visible to anyone with Wireshark
Use in production?Never — always replace with SSH
🚫
Telnet transmits both login credentials and all management traffic in cleartext. A threat actor capturing packets can read the username and password directly from a Wireshark capture. Telnet should never be used on any production network.

1.3.2 SSH Operation

FeatureSSH
TCP Port22
EncryptionStrong encryption for both authentication and all data
What is protectedUsername, password, and all management data are encrypted
Use in production?Always — SSH replaces Telnet for all management
🎯 MEMORIZE — TCP PORTS
Telnet = TCP port 23 (older, plaintext, insecure)
SSH = TCP port 22 (modern, encrypted, secure)

Memory trick: SSH (22) came before Telnet (23) alphabetically, and is the better protocol — 22 < 23.

1.3.3 Verify the Switch Supports SSH

SSH requires an IOS image with cryptographic (crypto) features. Look for "k9" in the IOS filename — this confirms crypto capability.

show version — check IOS image name for k9 
S1# show version
Cisco IOS Software, C2960 Software (C2960-LANBASEK9-M), Version 15.0(2)SE7, RELEASE SOFTWARE (fc1)
!                                        ^^^^^^^^
!                                    "K9" confirms crypto support -- SSH is available

1.3.4 Configure SSH — 6 Steps

All six steps must be completed in order. Students most often forget Step 2 (domain name) and Step 6 (version 2).

Step 1Verify SSH support
Check if SSH is available 
S1# show ip ssh
! If the command is unrecognized, the IOS does not support crypto -- wrong image
Step 2Configure the IP domain name
Set domain name — required before generating RSA keys 
S1(config)# ip domain-name cisco.com
! This is required -- crypto key generate rsa will FAIL without a domain name
Step 3Generate RSA key pair (this enables SSH)
Generate RSA keys — minimum 1024 bits recommended 
S1(config)# crypto key generate rsa
How many bits in the modulus [512]: 1024

! To delete the RSA key and disable SSH:
S1(config)# crypto key zeroize rsa
💡Generating RSA keys automatically enables the SSH server. Larger key size (1024+ bits) = more secure but slightly slower to generate.
Step 4Configure local user authentication
Create local username and password 
S1(config)# username admin secret ccna
! 'secret' stores the password with MD5 hashing -- always preferred over 'password'
Step 5Configure VTY lines for SSH only
Restrict VTY lines to SSH — block Telnet 
S1(config)# line vty 0 15
S1(config-line)# transport input ssh    ! Blocks all non-SSH (Telnet, etc.)
S1(config-line)# login local            ! Authenticate using local username database
S1(config-line)# exit
Step 6Enable SSH version 2
Force SSH version 2 — version 1 has security flaws 
S1(config)# ip ssh version 2
! Without this command, both v1 and v2 are accepted
! SSH v1 has known vulnerabilities -- always explicitly set v2
🚨
Most common SSH configuration mistakes:
— Forgetting ip domain-name before trying to generate RSA keys (Step 2 before Step 3)
— Not adding ip ssh version 2 — leaves SSH v1 accepted
— Using login instead of login local on VTY lines — won't authenticate against local usernames

1.3.5 Verify SSH is Operational

Verify SSH version and active sessions 
S1# show ip ssh

S1# show ssh

1.4Basic Router Configuration▾

1.4.1 Configure Basic Router Settings

Routers and switches share the same initial configuration tasks. These should be performed on every device in every network:

R1 — Complete basic router initial configuration 
Router# configure terminal
Router(config)# hostname R1

! Privileged EXEC password -- always use 'secret' not 'password'
R1(config)# enable secret class

! Console access password
R1(config)# line console 0
R1(config-line)# password cisco
R1(config-line)# login
R1(config-line)# exit

! VTY (remote management) password -- lines 0-4 for Telnet/SSH
R1(config)# line vty 0 4
R1(config-line)# password cisco
R1(config-line)# login
R1(config-line)# exit

! Encrypt all plaintext passwords stored in running-config
R1(config)# service password-encryption

! Legal warning banner -- displayed before login
R1(config)# banner motd $ Authorized Access Only! $

! Save to NVRAM
R1# copy running-config startup-config
🎯 enable secret vs enable password
  • enable secret → stored using MD5 hash — strongly encrypted, always use this
  • enable password → stored in plaintext by default (Type 7 with service password-encryption — weak)
  • If both are configured: enable secret takes precedence — enable password is completely ignored
  • Best practice: only configure enable secret — never configure enable password

1.4.3–1.4.4 Configure Router Interfaces (Dual Stack)

Router interfaces support both IPv4 and IPv6 (dual stack). Every interface needs at minimum an IP address and no shutdown to become active.

🚨
Critical difference from switches: Router interfaces are administratively down by default. Switch ports are up by default. Forgetting no shutdown on a router interface is the most common missed step — the interface shows down/down and nothing routes.
R1 — Configure dual-stack interfaces (IPv4 + IPv6) 
R1(config)# interface gigabitethernet 0/0/0
R1(config-if)# ip address 192.168.10.1 255.255.255.0
R1(config-if)# ipv6 address 2001:db8:acad:1::1/64
R1(config-if)# description Link to LAN 1
R1(config-if)# no shutdown                    ! Required -- interfaces default to shutdown!
R1(config-if)# exit

R1(config)# interface gigabitethernet 0/0/1
R1(config-if)# ip address 192.168.11.1 255.255.255.0
R1(config-if)# ipv6 address 2001:db8:acad:2::1/64
R1(config-if)# description Link to LAN 2
R1(config-if)# no shutdown
R1(config-if)# exit

R1(config)# interface serial 0/0/0
R1(config-if)# ip address 209.165.200.225 255.255.255.252
R1(config-if)# ipv6 address 2001:db8:acad:3::225/64
R1(config-if)# description Link to R2
R1(config-if)# no shutdown
R1(config-if)# end
💡
Interface descriptions are optional but strongly recommended in production networks. A good description (who the other end connects to, the circuit ID) saves significant time during troubleshooting. Max 240 characters.

1.4.6 IPv4 Loopback Interfaces

A loopback interface is a logical, software-only interface that is always up as long as the router is running. It can never go down due to a physical cable problem.

PropertyDetail
Physical port?No — it is a software interface internal to the router
StateAlways up/up as long as the router is functioning
Can it fail?Only if the router itself fails
Common usesTesting routing processes, simulating networks, representing the router in routing protocols (OSPF Router ID), simulating WAN/internet links in labs
R1 — Create loopback interface 
R1(config)# interface loopback 0
R1(config-if)# ip address 10.0.0.1 255.255.255.0
R1(config-if)# exit

! No 'no shutdown' needed -- loopbacks are automatically up
%LINEPROTO-5-UPDOWN: Line protocol on Interface Loopback0, changed state to up
✅
Multiple loopback interfaces can be created on one router (Loopback0, Loopback1, etc.). Each must have a unique IP address. In CCNA labs, a loopback is commonly used to simulate a link to the internet or a remote network without additional hardware.

1.5.3 Verify IPv6 Link Local and Multicast Addresses

Every IPv6-enabled interface automatically gets a link-local address (FE80::/10) whenever a global unicast address is assigned. Link-local addresses are required for IPv6 — global unicast addresses are optional.

show ipv6 interface — see link-local, global unicast, and multicast 
R1# show ipv6 interface gigabitethernet 0/0/0
GigabitEthernet0/0/0 is up, line protocol is up
  IPv6 is enabled, link-local address is FE80::7279:B3FF:FE92:3130
  Global unicast address(es):
    2001:DB8:ACAD:1::1, subnet is 2001:DB8:ACAD:1::/64
  Joined group address(es):
    FF02::1           (all IPv6 nodes on the local link)
    FF02::1:FF00:1    (solicited-node multicast)
    FF02::1:FF92:3130

1.5.5 Verify Routes

In Cisco IOS 15, each active connected interface creates two routing table entries:

CodeMeaningMask
CConnected — the network reachable via this interface/24 (the full subnet)
LLocal — the router's own IP address on that interface/32 for IPv4, /128 for IPv6
show ip route and show ipv6 route 
R1# show ip route
Codes: L - local, C - connected, S - static ...
Gateway of last resort is not set
      192.168.10.0/24 is variably subnetted, 2 subnets, 2 masks
C        192.168.10.0/24 is directly connected, GigabitEthernet0/0/0
L        192.168.10.1/32 is directly connected, GigabitEthernet0/0/0
      192.168.11.0/24 is variably subnetted, 2 subnets, 2 masks
C        192.168.11.0/24 is directly connected, GigabitEthernet0/0/1
L        192.168.11.1/32 is directly connected, GigabitEthernet0/0/1
      209.165.200.0/24 is variably subnetted, 2 subnets, 2 masks
C        209.165.200.224/30 is directly connected, Serial0/1/0
L        209.165.200.225/32 is directly connected, Serial0/1/0
💡
Why two entries per interface? The C entry tells the router how to reach the network. The L entry (host route with /32) tells the router "this specific IP address is mine" — used to efficiently process packets addressed directly to the router itself, without a full routing lookup.

1.5.8 Command History Feature

The IOS CLI stores recently entered commands in a history buffer, allowing them to be recalled without retyping.

ActionKey
Recall previous command (older)Ctrl+P or ↑ Up Arrow
Move forward (more recent)Ctrl+N or ↓ Down Arrow
View history listshow history
Change buffer size (session only)terminal history size 200
Command history commands 
! Default: last 10 commands stored
R1# show history
  show ip int brief
  show interface g0/0/0
  show ip route
  show running-config
  show history

! Increase buffer to 200 commands (current session only)
R1# terminal history size 200
💡
Default history size is 10 commands. Maximum that can be set with terminal history size is 256. This setting is session-only — it resets when you disconnect.

🎯Common Exam Traps — Module 1▾
❌
Trap 1: IOS loads from ROM, not flash.
POST is stored in ROM. The Boot Loader is stored in ROM. But the IOS itself loads from flash. The startup-config (config.text) is also in flash. Running-config lives in RAM and is lost on reload.
❌
Trap 2: Router interfaces default to shutdown.
Unlike switch ports (which are up by default), all router LAN and WAN interfaces are administratively down until no shutdown is applied. Forgetting this is the single most common missed step when configuring router interfaces. An interface with correct IP but no no shutdown shows administratively down / down and does not route.
❌
Trap 3: Switch management SVI shows down/down.
Two conditions BOTH must be true for the SVI to be up/up: (1) the VLAN must exist in the VLAN database, AND (2) at least one active port must be assigned to that VLAN. Creating the SVI with an IP is not enough.
❌
Trap 4: enable secret vs enable password.
Always use enable secret — it uses MD5 hashing. enable password stores in plaintext by default (Type 7 with service password-encryption is still weak). If both are configured, enable secret wins — enable password is ignored entirely.
❌
Trap 5: SSH requires domain name BEFORE generating RSA keys.
The command crypto key generate rsa will fail if no domain name has been configured with ip domain-name. This is Step 2 before Step 3 — students frequently skip it and wonder why key generation fails.
❌
Trap 6: transport input ssh intentionally blocks Telnet.
Once transport input ssh is applied to VTY lines, Telnet is completely blocked. This is expected behavior — not a mistake. If Telnet worked before and stops working after SSH config, the configuration is correct.
❌
Trap 7: ip ssh version 2 must be explicitly set.
Without this command, the switch accepts both SSH v1 and v2. SSH v1 has known security vulnerabilities. Always configure ip ssh version 2 as Step 6. The exam may show a config that accepts v1 and ask what is wrong.
⚠️
Trap 8: Amber STAT LED = STP blocking, not hardware failure.
A port showing amber in STAT mode is being blocked by Spanning Tree Protocol. This is completely normal — especially in the first ~30 seconds after a port is activated. It is not a failure, not a duplex mismatch, and not a cable problem. Ports normally transition from amber to green within 30–50 seconds.
⚠️
Trap 9: Late collisions = duplex mismatch (usually).
Late collisions occur after the first 512 bits of a frame are transmitted. On a correctly configured network, late collisions should never occur. If you see them, the most common cause is a duplex mismatch — one end is full-duplex, the other is half-duplex. You see late collisions on the half-duplex end.
⚠️
Trap 10: High CRC errors = cable noise, not duplex.
CRC errors indicate a checksum mismatch — the received frame was corrupted in transit. The most common cause is physical cable problems: electrical interference, damaged cable, loose connectors, or cable exceeding maximum length. CRC errors are a Layer 1 signal — start by inspecting the cable.
✅
Quick recap — where things are stored:

ROM → POST, Boot Loader (read-only, survives power loss)
Flash → IOS image, startup-config (config.text), VLAN database (vlan.dat)
RAM → running-config, ARP table, routing table, MAC address table (lost on reload)
NVRAM → startup-config on some platforms (same as flash on 2960)

This is tested directly on the CCNA exam.
