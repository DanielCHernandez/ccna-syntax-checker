16.1Packet Processing with Static Routes▾

16.1.1 11-Step Packet Forwarding Walkthrough

Topology: PC1 → R1 → R2 → R3 → PC3. R1 uses a default static route. R2 uses a specific static route. R3 has a connected route to PC3's LAN.

📦 PC1 → PC3 — Complete Packet Journey
1
ARRIVE
Packet arrives on R1's GigabitEthernet 0/0/0 from PC1. R1 strips the Ethernet frame and examines the destination IP.
2
LOOKUP
R1 has no specific route to 192.168.2.0/24. Uses the default static route (0.0.0.0/0) → next-hop R2.
3
ENCAP
R1 encapsulates in new frame for Serial link. Point-to-point → R1 adds "all 1s" L2 destination address. No ARP needed on P2P links.
4
TRANSIT
Frame exits R1's Serial 0/1/0 → arrives on R2's Serial 0/1/0. R2 strips the frame.
5
LOOKUP
R2 finds a specific static route to 192.168.2.0/24 out Serial 0/1/1 via R3.
6
ENCAP
R2 encapsulates in new frame for Serial link to R3. Point-to-point → "all 1s" L2 address again. No ARP.
7
TRANSIT
Frame exits R2's Serial 0/1/1 → arrives on R3's Serial 0/1/1. R3 strips the frame.
8
LOOKUP
R3 finds a connected route to 192.168.2.0/24 on its GigabitEthernet 0/0/0. No static route needed — R3 owns this network.
9
ARP
R3 checks ARP table for PC3's MAC (192.168.2.10). If not found → R3 sends ARP request on G0/0/0 → PC3 replies with its MAC address.
10
ENCAP
R3 builds Ethernet frame: src = R3's G0/0/0 MAC, dst = PC3's MAC. This is the first Ethernet hop since the source LAN.
11
DELIVER
Frame exits R3's GigabitEthernet 0/0/0 → arrives at PC3's NIC. End-to-end delivery complete. ✅
🎯 KEY TAKEAWAYS FROM THE FORWARDING WALKTHROUGH
  • Point-to-point serial links = "all 1s" L2 address, no ARP — only two devices on the link; router always knows who the other end is
  • Ethernet links = ARP required — multiple devices may share the segment; MAC must be resolved
  • The IP packet's source and destination IPs never change — only the L2 frame is rebuilt at each hop
  • Default route on stub router (R1) — no specific routes needed; everything goes to R2
  • Connected route on the last router (R3) — no static route configured; R3 directly owns the destination LAN
16.2Common Troubleshooting Commands▾

16.2.1 Why Networks Break

Static routes do not adapt to topology changes. Any of these events can break connectivity that was previously working:

  • Interface failure (physical cable, transceiver, hardware)
  • Service provider drops a WAN connection
  • Link becomes oversaturated (congestion)
  • Administrator enters wrong configuration — the most common cause of static route problems

When connectivity fails, isolate the problem using the five standard troubleshooting commands in a methodical order.

CMD Five Troubleshooting Commands

ping / ping [ip] source [intf]
Tests IP reachability end-to-end. Tests both the forward path AND the return path — if either direction is broken, ping fails.

Extended ping — specifies the source interface. Critical for simulating what PC users actually experience:
✅ Validates Layer 3 — IP routing and reachability
traceroute [ip]
Traces the actual hop-by-hop path. Shows exactly which router is the last to respond — that is where to look next.

Reading output: Each row = one hop. Three values = three probes (RTT in ms). * = no reply.
Routing loop indicator: same two IPs repeating indefinitely = routing loop between those two routers.
✅ Validates Layer 3 path — reveals exactly where packets stop or loop
show ip route
Displays the routing table. Use this to:
• Verify a static route is present (look for S entries)
• Verify the next-hop IP is correct (look at via x.x.x.x)
• Check for missing routes (destination not in table)
• Identify wrong next-hop (route installed but pointing to wrong router)
✅ Validates Layer 3 routing — route presence and correctness
show ip interface brief
Quick status of all interfaces — Status and Protocol columns tell you which OSI layer has a problem.

Critical for static routes: IOS will NOT install a static route in the routing table if the exit interface or next-hop is unreachable. A correctly configured route that is missing from the table = interface is down.
✅ Validates Layer 1 and Layer 2 — physical and data link status
show cdp neighbors / show cdp neighbors detail
Lists directly connected Cisco devices. Validates L1/L2 connectivity without needing a working IP address.

• Neighbor in CDP table but can't ping → Layer 3 problem (IP/routing)
• Neighbor NOT in CDP table → Layer 1/2 problem (cable, encapsulation, hardware)
• detail version also shows neighbor's IP address — useful for verifying next-hop
✅ Validates Layer 1 and Layer 2 — physical connectivity without needing IP

INT Interface Status — All Four Combinations

up / up
Fully operational. ✅ Physical and data link layers working. Static routes using this interface will be installed.
up / down
Layer 2 problem. Physical connection exists but data link failed. Check: encapsulation mismatch (HDLC vs PPP), keepalive settings, clocking on serial links.
down / down
Layer 1 problem. No physical signal. Check: cable connected?, interface not shut down?, hardware failure? The interface may need no shutdown.
admin down / down
Manually disabled. Admin ran shutdown on this interface. Fix: no shutdown. Static routes using this interface will NOT be in routing table.
show ip interface brief — sample output 
R1# show ip interface brief
Interface              IP-Address      OK? Method Status           Protocol
GigabitEthernet0/0/0   172.16.3.1      YES manual up               up      ← ✅ up/up
GigabitEthernet0/0/1   unassigned      YES unset  up               up
Serial0/1/0            172.16.2.1      YES manual up               up      ← ✅ up/up
Serial0/1/1            unassigned      YES unset  up               up

16.2.3Complete Walkthrough — Solve a Connectivity Problem▾

SCENARIO PC1 Cannot Reach PC3's LAN

Topology: PC1 (172.16.3.x) → R1 (G0/0/0: 172.16.3.1, S0/1/0: 172.16.2.1) ← serial → R2 (S0/1/0: 172.16.2.2, S0/1/1: 192.168.1.2) ← serial → R3 (S0/1/1: 192.168.1.1, G0/0/0: 192.168.2.1) → PC3 (192.168.2.x)

🔎 Step 1 — Confirm the problem with extended ping
Extended ping — sourced from R1's LAN interface (simulates PC1)
R1# ping 192.168.2.1 source g0/0/0
Packet sent with a source address of 172.16.3.1
.....
Success rate is 0 percent (0/5)    ! Confirmed — LAN cannot reach R3's LAN
Use extended ping with source g0/0/0 — this simulates what PC1 experiences. The LAN interface is the source for all user traffic.
🔗 Step 2 — Test the next-hop router (R2)
Ping R2's serial interface — tests R1 ↔ R2 link
R1# ping 172.16.2.2
!!!!!
Success rate is 100 percent (5/5)    ! R1 ↔ R2 is fine
R1 can reach R2. The problem is beyond R2 — something further in the path.
🔗 Step 3 — Ping R3's LAN from R1's serial interface (not LAN)
Standard ping — sourced from R1's serial interface (172.16.2.1)
R1# ping 192.168.2.1
!!!!!
Success rate is 100 percent (5/5)    ! Works from serial source
This is the key diagnostic clue: Ping works from R1's serial interface but NOT from R1's LAN interface (Step 1). This means R3 has a return route for 172.16.2.0/24 (serial link) but NOT for 172.16.3.0/24 (R1's LAN). The problem is the return route for R1's LAN subnet — it's missing or wrong on R2 or R3.
❌ Step 4 — Inspect R2's routing table — find the wrong route
show ip route on R2 — spot the misconfigured next-hop
R2# show ip route | begin Gateway
Gateway of last resort is not set
      172.16.0.0/16 is variably subnetted, 5 subnets, 2 masks
C        172.16.1.0/24 is directly connected, GigabitEthernet0/0/0
L        172.16.1.1/32 is directly connected, GigabitEthernet0/0/0
C        172.16.2.0/24 is directly connected, Serial0/1/0
L        172.16.2.2/32 is directly connected, Serial0/1/0
S        172.16.3.0/24 [1/0] via 192.168.1.1   ! ← WRONG! 192.168.1.1 = R3, should be R1
      192.168.1.0/24 is variably subnetted, 2 subnets, 2 masks
C        192.168.1.0/24 is directly connected, Serial0/1/1
L        192.168.1.2/32 is directly connected, Serial0/1/1
S     192.168.2.0/24 [1/0] via 192.168.1.1
R2's route to 172.16.3.0/24 (R1's LAN) points to 192.168.1.1 = R3 instead of 172.16.2.1 = R1. Return traffic goes R2 → R3 → R2 → R3 in an endless loop.
❌ Step 5 — Confirm with show running-config
show running-config | include ip route — see the bad command
R2# show running-config | include ip route
ip route 172.16.3.0 255.255.255.0 192.168.1.1    ! ← wrong next-hop
ip route 192.168.2.0 255.255.255.0 192.168.1.1
Confirmed — the static route command has the wrong next-hop. Time to fix it.
✅ Step 6 — Fix the misconfigured route
Remove wrong route, add correct route
R2(config)# no ip route 172.16.3.0 255.255.255.0 192.168.1.1   ! Remove wrong
R2(config)# ip route 172.16.3.0 255.255.255.0 172.16.2.1       ! Add correct → R1
Important: The no ip route command must exactly match the original command's parameters. If any parameter differs, IOS will not recognize it as the same route and the bad route remains.
🔍 Step 7 — Verify the corrected routing table
show ip route on R2 — confirm correct next-hop
R2# show ip route | begin Gateway
S        172.16.3.0/24 [1/0] via 172.16.2.1    ! ✅ Now pointing to R1 (172.16.2.1)
S     192.168.2.0/24 [1/0] via 192.168.1.1     ! ✅ Still correct for R3's LAN
✅ Step 8 — Confirm with extended ping — connectivity restored
Extended ping from R1's LAN interface — same test as Step 1
R1# ping 192.168.2.1 source g0/0/0
Packet sent with a source address of 172.16.3.1
!!!!!
Success rate is 100 percent (5/5)    ! ✅ PC1 ↔ PC3 connectivity restored
Final step: Have PC1 also ping PC3 directly to confirm end-to-end user connectivity — not just router-to-router.
PATSix Common Static Route Problem Patterns▾
1 Missing Route
Symptom
Ping fails. show ip route has no entry for the destination.
Cause
Static route was never configured, was accidentally deleted, or never saved after configuration.
Diagnose
show ip route — no S entry for the destination network.
Fix
Add the missing ip route command.
2 Wrong Next-Hop
Symptom
Ping fails. Route IS in the table but traffic goes the wrong direction or loops.
Cause
Admin typed the wrong next-hop IP — the most common static route misconfiguration.
Diagnose
show ip route — route present but via [wrong-ip]. Compare against topology.
Fix
no ip route [net] [mask] [wrong-ip] then ip route [net] [mask] [correct-ip].
3 Wrong Network or Mask
Symptom
Ping to specific hosts fails. Route exists but doesn't match the actual destination.
Cause
Typo in the network address or subnet mask when entering the static route.
Diagnose
show running-config | include ip route — compare configured network/mask against actual topology.
Fix
Remove wrong route, add correct one with right network and mask.
4 Exit Interface Down
Symptom
Static route is configured but MISSING from routing table. Route exists in running-config but not in show ip route.
Cause
IOS automatically removes a static route from the routing table when the exit interface or next-hop becomes unreachable.
Diagnose
show ip interface brief — look for down/down or admin down on the exit interface.
Fix
Restore the interface (no shutdown) or fix the physical issue. Route re-installs automatically.
5 Routing Loop
Symptom
Ping fails. Traceroute shows the same two hops repeating indefinitely. Packets never reach destination.
Cause
Two routers have static routes pointing to each other for the same destination — R2 sends to R3, R3 sends back to R2.
Diagnose
traceroute — same two IPs alternating. show ip route on both routers — one has the wrong next-hop.
Fix
Identify which router has the wrong next-hop, correct it.
6 Asymmetric Routing (Return Path Missing)
Symptom
Ping from router's serial interface works. Ping from LAN interface fails. Traceroute stops at intermediate router.
Cause
Return route exists for the serial subnet but not for the LAN subnet. The static route on an intermediate router is missing or wrong for the return direction.
Diagnose
Compare: ping [dest] vs ping [dest] source g0/0/0. If one works and one doesn't — check routing tables on ALL routers for both forward AND return paths.
Fix
Add or correct the missing return-direction static route on the intermediate router.
METSystematic Troubleshooting Methodology▾

Apply these four phases in order. Process of elimination — eliminate one layer/possibility at a time.

Phase 1 — Identify the Scope
  1. Can the end user reach anything? Or only this specific destination fails?
  2. Is only one device affected or all devices on the LAN?
  3. Is the problem one-directional or total (ping fails both ways)?
  4. What recently changed? (new config, interface bounce, ISP issue)
Phase 2 — Test Connectivity Layer by Layer
  1. ping [next-hop-ip] — can you reach the directly connected next-hop? If no → check interface and physical
  2. Ping progressively farther destinations — find exactly where packets stop
  3. ping [dest] source [LAN-intf] — compare with standard ping from serial interface
  4. traceroute [dest] — identify the last responding hop; look for loops
  5. show cdp neighbors — verify L1/L2 to directly connected devices
Phase 3 — Examine Routing Tables
  1. show ip route on the router where traceroute stopped — look for missing or wrong next-hop
  2. show ip route on ALL routers in the path — verify both forward AND return routes
  3. show running-config | include ip route — confirm what is actually configured (reveals floating routes and typos)
  4. show ip interface brief — verify exit interfaces are up/up
Phase 4 — Fix and Verify
  1. Remove incorrect route: no ip route [net] [mask] [wrong-next-hop]
  2. Add correct route: ip route [net] [mask] [correct-next-hop]
  3. Verify: show ip route — confirm correct entry is installed
  4. Re-run extended ping from LAN interface — confirm connectivity restored
  5. Verify from end user device — PC1 pings PC3 directly

🎯Common Exam Traps — Module 16▾
❌
Trap 1: Extended ping is essential — always specify the source LAN interface.
A standard ping from a router uses the router's best-source IP (often the serial interface). Return routes may exist for that serial subnet but not for the LAN subnet. Use ping [dest] source g0/0/0 to simulate what PC users actually experience. This exact pattern appears in the M14–16 exam.
❌
Trap 2: A correctly configured static route disappears from show ip route when the exit interface goes down.
IOS automatically removes a static route from the routing table if the exit interface or next-hop becomes unreachable. The route remains in the running config. To verify: show running-config | include ip route shows it's there; show ip route static shows it's missing. Fix the interface to restore the route.
❌
Trap 3: Traceroute reveals routing loops — look for repeating hops.
If traceroute shows the same two IP addresses alternating indefinitely, a routing loop exists between those two routers. One has a wrong next-hop pointing back to the other. Examine show ip route on both routers and find the incorrect via address.
❌
Trap 4: show cdp neighbors validates L1/L2 without needing a working IP address.
If a neighbor appears in CDP output but cannot be pinged → Layer 3 problem (IP addressing or routing). If a neighbor does NOT appear in CDP output → Layer 1 or 2 problem (cable disconnected, interface down, hardware). CDP is your first check when you suspect a physical problem.
❌
Trap 5: Wrong next-hop is the most common static route misconfiguration.
The route exists in the routing table (so it looks configured correctly), but traffic goes the wrong direction because the via address points to the wrong router. Always compare the show ip route next-hop against the actual topology diagram.
⚠️
Trap 6: Always check routing in BOTH directions — forward AND return.
A ping sourced from R1's serial interface may succeed (return route exists for 172.16.2.0/24) while a ping from R1's LAN fails (no return route for 172.16.3.0/24). Check the routing table on EVERY router in the path, not just the source router.
⚠️
Trap 7: show running-config | include ip route vs show ip route static.
show ip route static = only routes currently in the active table. show running-config | include ip route = everything configured, including floating routes waiting in the wings and misconfigured routes the admin forgot about. Use both for complete verification.
⚠️
Trap 8: Interface status combinations — know all four.
up/up = working. up/down = Layer 2 problem (encapsulation, keepalive). down/down = Layer 1 problem (cable, hardware, needs no shutdown). admin down/down = manually shut, needs no shutdown. A static route whose exit interface shows anything other than up/up will NOT be installed in the routing table.
⚠️
Trap 9: Removing a static route requires exact parameter match.
no ip route 172.16.3.0 255.255.255.0 192.168.1.1 — all three parameters must exactly match the original ip route command. If any parameter differs, IOS will not find it as a match and the wrong route remains active. Use show running-config | include ip route to see the exact syntax before running no ip route.
⚠️
Trap 10: Point-to-point serial links use "all 1s" — no ARP needed.
Serial interfaces have no MAC addresses. The L2 destination is the broadcast-equivalent "all 1s" address. Ethernet interfaces require ARP to resolve the next-hop MAC address. This distinction is reviewed in 16.1 and tested in the checkpoint exam.
⚠️
Trap 11: show cdp neighbors vs show cdp neighbors detail.
Basic show cdp neighbors shows device ID, local interface, capability, platform, and port ID — confirms L1/L2. show cdp neighbors detail additionally shows the neighbor's IP address — useful for confirming the next-hop router is reachable at the address configured in the static route.
✅
