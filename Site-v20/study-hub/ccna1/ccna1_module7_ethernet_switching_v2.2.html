7.1Ethernet Frames▾

7.1.1 Ethernet Overview

Ethernet is one of two LAN technologies used today (the other being WLAN). It uses wired communications — twisted pair, fiber-optic, and coaxial cables. Ethernet operates at both the data link layer and the physical layer, defined by IEEE 802.2 and 802.3 standards.

SpeedStandard Name
10 Mbps10BASE-T (classic Ethernet)
100 MbpsFast Ethernet (100BASE-TX)
1000 Mbps (1 Gbps)Gigabit Ethernet
10 Gbps10 Gigabit Ethernet
40 Gbps / 100 GbpsHigh-speed data center Ethernet

7.1.2 LLC and MAC Sublayers in Ethernet

SublayerStandardWhereFunction
LLCIEEE 802.2SoftwareCommunicates between upper-layer software and lower-layer hardware. Places information in the frame identifying which L3 protocol is used. Allows IPv4 and IPv6 to share the same NIC.
MACIEEE 802.3 / 802.11 / 802.15Hardware (NIC)Data encapsulation (frame structure, addressing, error detection) + media access control for shared media.

7.1.3 MAC Sublayer — Encapsulation and Media Access

IEEE 802.3 data encapsulation provides three things:

  • Ethernet frame — the internal structure
  • Ethernet addressing — source and destination MAC to deliver frame from NIC to NIC on the same LAN
  • Ethernet error detection — FCS trailer for error detection
🎯 KEY — Legacy vs Modern Ethernet
Legacy Ethernet (bus topology / hubs): half-duplex → uses CSMA/CD for media access control
Modern Ethernet (switches): full-duplex → NO CSMA/CD needed — no shared medium, no collisions possible

7.2Ethernet MAC Address▾

7.2.1 MAC Address and Hexadecimal

An Ethernet MAC address is a 48-bit binary value. Because 1 hex digit = 4 bits, a 48-bit address requires exactly 12 hex digits to represent.

Address TypeNumber SystemLength
IPv4 addressDecimal (base 10)4 octets (e.g., 192.168.1.1)
IPv6 addressHexadecimal (base 16)32 hex digits
MAC addressHexadecimal (base 16)12 hex digits = 6 bytes = 48 bits
💡
Leading zeros are always shown in hex notation: binary 00001010 = hex 0A (not just A). Hex notation variants: 0x73, 73H, or subscript₁₆ — all mean the same thing.

7.2.2 MAC Address Structure — OUI and Vendor Code

Ethernet MAC Address Structure (48 bits = 12 hex digits)
First 6 hex digits (24 bits)
OUI
Organizationally Unique Identifier
Assigned by IEEE to vendor
Last 6 hex digits (24 bits)
Vendor Code
Assigned by vendor
Must be unique per device

Example — Cisco device: Cisco OUI = 00-60-2F · Vendor code = 3A-07-BC · Full MAC = 00-60-2F-3A-07-BC

Every vendor selling Ethernet devices must register with IEEE to obtain their OUI. The vendor is responsible for ensuring no two devices get the same MAC. Duplicate MACs can occur from manufacturing errors, VM configurations, or software modification.

7.2.3 Frame Processing — BIA

The MAC address is called a BIA (Burned-In Address) — hard-coded into the NIC's ROM. On boot: NIC copies MAC from ROM → RAM.

Frame reception process:

  1. NIC receives an Ethernet frame
  2. NIC compares the destination MAC address to its own MAC stored in RAM
  3. Match → frame accepted → passed up the OSI layers for de-encapsulation
  4. No match → frame discarded
  5. Exception: NIC also accepts frames with a broadcast or multicast MAC the host belongs to
⚠️
MAC addresses can be changed in software on modern operating systems — this makes MAC-based filtering less reliable as a security control. An attacker can spoof a trusted MAC address.

7.2.4–7.2.6 Three MAC Address Types

👤 Unicast MAC
Frame sent from one source to one specific destination. Source MAC is always unicast. Destination unicast MAC = specific NIC's address.

How destination MAC is found:
· IPv4 → uses ARP (Address Resolution Protocol)
· IPv6 → uses Neighbor Discovery (ND)
📢 Broadcast MAC — FF-FF-FF-FF-FF-FF
Destination MAC = FF-FF-FF-FF-FF-FF (48 ones in binary). Received and processed by every device on the LAN.

· Switch floods out all ports except incoming
· NOT forwarded by routers (stops at router = broadcast domain boundary)
· Examples: DHCP requests · ARP requests
👥 Multicast MAC
Received by a specific group of devices that subscribe to that multicast address.

· IPv4 multicast → MAC starts with 01-00-5E
· IPv6 multicast → MAC starts with 33-33
· IPv4 multicast range: 224.0.0.0 – 239.255.255.255
· IPv6 multicast prefix: ff00::/8
· Flooded out all ports except incoming (unless multicast snooping)
· NOT forwarded by routers by default
· Source is ALWAYS unicast; only destination can be multicast
7.3The MAC Address Table▾

7.3.1 Switch Fundamentals — CAM Table

A Layer 2 Ethernet switch makes forwarding decisions based solely on Layer 2 MAC addresses. It is completely unaware of the data protocol in the payload (IPv4, IPv6, ARP, etc.).

The switch maintains a MAC address table (also called a CAM table — Content Addressable Memory). A freshly powered-on switch has an empty MAC address table:

MAC AddressPort
— Table is empty — switch has not learned any MAC addresses yet —

Unlike a hub (which repeats frames out ALL ports), a switch uses the MAC address table to make intelligent forwarding decisions — sending frames only to the port where the destination device is located.

7.3.2 Switch Learning and Forwarding — Two Steps Per Frame

Step 1 — LEARN: Examine Source MAC
1
Frame arrives on a port. Switch reads the source MAC address + incoming port number.
2
New MAC → add entry: source MAC + port number → MAC table
3
MAC exists, same port → reset the 5-minute aging timer
4
MAC exists, different port → update entry with new port (device moved)
Step 2 — FORWARD: Find Destination MAC
✓
Destination MAC IS in table → forward frame out only that specific port (filtering)
?
Destination MAC NOT in table → flood frame out all ports except incoming → called unknown unicast
📢
Destination is broadcast (FF-FF-FF-FF-FF-FF) → flood out all ports except incoming
👥
Destination is multicast → flood out all ports except incoming (unless multicast snooping enabled)
✅
MAC address table aging timer = 5 minutes by default. If no frame with that source MAC is received for 5 minutes, the entry is deleted. This prevents the table from filling with stale entries for devices that have left the network.

7.3.3 Filtering Frames — How a Learned Switch Works

As the switch receives more frames, it populates the MAC table. Once both source and destination are in the table, the switch filters — sending only to the specific destination port:

MAC Address (learned)Port
AA:AA:AA:AA:AA:AAPort 1 (PC-A)
BB:BB:BB:BB:BB:BBPort 2 (PC-B)
CC:CC:CC:CC:CC:CCPort 3 (PC-C)
DD:DD:DD:DD:DD:DDPort 4 (PC-D)

When PC-A sends to PC-D: switch looks up DD:DD:DD:DD:DD:DD → found on Port 4 → forwards ONLY out Port 4. PC-B and PC-C receive nothing.

💡
A single switch port can have multiple MAC addresses — this is normal when a port connects to another switch. The upstream switch learns all MAC addresses of devices behind the downstream switch, all associated with the one port connecting the two switches.

Default gateway MAC: When a host needs to reach a device on a remote network, it sends the frame to the router's MAC address (default gateway). The switch forwards that frame to whichever port the router is on.
7.4Switch Speeds and Forwarding Methods▾

7.4.1 Store-and-Forward vs Cut-Through Switching

📦 Store-and-Forward
  • Receives the entire frame first
  • Computes CRC — if valid, forwards; if invalid, discards
  • Looks up destination MAC, forwards out correct port
  • Eliminates corrupt frames from the network
  • Required for QoS analysis (VoIP prioritization)
  • Higher latency (must wait for full frame)
⚡ Cut-Through
  • Starts forwarding before entire frame received
  • Only reads enough to get destination MAC (first 6 bytes after preamble)
  • No CRC check — may forward corrupt frames
  • Lower latency
  • Cannot perform QoS classification

7.4.2 Cut-Through Variants

⚡ Fast-Forward Switching
Forwards immediately after reading destination MAC. Lowest latency of any method. Latency = first bit received → first bit transmitted. May relay frames with errors (infrequently). Typical cut-through method.
🔶 Fragment-Free Switching
Stores the first 64 bytes before forwarding. Most errors and collisions occur in the first 64 bytes — this catches most problems. Compromise between store-and-forward (full integrity) and fast-forward (lowest latency). Middle ground on both latency and error checking.
💡
Adaptive switching: Some switches start in cut-through mode on a per-port basis. When errors exceed a user-defined threshold, that port automatically switches to store-and-forward. When errors drop below the threshold, it switches back to cut-through.

7.4.3 Memory Buffering on Switches

Buffering stores frames temporarily when the destination port is busy (congested). Two methods:

🚦 Port-Based Memory
Frames stored in queues linked to specific ports. All frames ahead in a queue must transmit before the next frame goes. One busy destination port blocks ALL frames behind it — even if other ports are free. Less efficient.
💾 Shared Memory
All frames in a common buffer shared by all ports. Memory dynamically allocated per port as needed. Frames linked to destination port dynamically — no physical moving between queues. Supports asymmetric switching (different port speeds). More efficient, fewer dropped frames.
💡
Asymmetric switching = different data rates on different ports. Example: server on 10 Gbps port, PCs on 1 Gbps ports. Shared memory buffering handles the speed difference gracefully.

7.4.4 Duplex, Speed, and Autonegotiation

SettingDescription
Full-duplexBoth ends send and receive simultaneously. No collisions possible. Default for modern switches.
Half-duplexOnly one end transmits at a time. Requires CSMA/CD. Legacy hubs and WLANs.
AutonegotiationTwo devices automatically negotiate the best speed and duplex. If both support full-duplex, it is chosen along with the highest common bandwidth.

Key rules:

  • Gigabit Ethernet ports only operate in full-duplex
  • Cisco switches and NICs default to autonegotiation
  • Best practice: explicitly configure both sides as full-duplex
🚨
Duplex mismatch — one port at half-duplex, the other at full-duplex. The full-duplex side sends whenever it wants. The half-duplex side sees these as collisions, backs off, and retransmits constantly. Result: severe performance degradation with high late-collision counts. Cause: autonegotiation fails when one side is disabled, or one side is manually reconfigured without updating the other.

7.4.5 Auto-MDIX

Auto-MDIX (Automatic Medium-Dependent Interface Crossover) — the switch automatically detects the cable type (straight-through or crossover) attached to the port and configures the interface accordingly. Either cable type works regardless of what device is on the other end.

  • Enabled by default on switches running Cisco IOS 12.2(18)SE or later
  • Can be disabled — best practice: still use the correct cable type, don't rely on auto-MDIX
  • Re-enable with command: mdix auto (interface configuration mode)
  • Makes crossover cables legacy for most scenarios
🎯Common Exam Traps — Module 7▾
❌
Trap 1: Minimum Ethernet frame = 64 bytes. Preamble NOT counted in frame size.
The preamble (7B) + SFD (1B) = 8 bytes are excluded from the size calculation. The 64-byte minimum starts at the Destination MAC field. Less than 64 bytes = runt/collision fragment → automatically discarded. The data field requires at least 46 bytes of payload — padding is added if the IP packet is smaller.
❌
Trap 2: Ethernet frame order — Destination MAC comes BEFORE Source MAC.
The full order: Preamble(7B) → SFD(1B) → Destination MAC(6B) → Source MAC(6B) → EtherType(2B) → Data(46–1500B) → FCS(4B). Students commonly reverse source and destination, or forget where preamble/SFD sit.
❌
Trap 3: EtherType values — 0x0800=IPv4, 0x86DD=IPv6, 0x0806=ARP. Memorize these.
These hex values appear in Wireshark output, frame analysis questions, and protocol identification questions. The EtherType field is also called Type, Length, or EtherType depending on the standard version referenced.
❌
Trap 4: The switch learns by examining the SOURCE MAC — not the destination.
The switch records which port each SOURCE MAC came from. It uses this table to decide where to FORWARD frames toward the DESTINATION. Students often flip this — the learning happens from source, the forwarding decision uses destination.
❌
Trap 5: Unknown unicast = destination MAC not in table = flood all ports except incoming.
This is NOT the same as a broadcast. An unknown unicast is flooded because the switch doesn't know where to send it yet. Once the destination device sends any frame back, its MAC is learned and future frames are filtered to one port only.
❌
Trap 6: Broadcast MAC = FF-FF-FF-FF-FF-FF. NOT forwarded by routers. Stops at the router.
Routers separate broadcast domains. A broadcast is flooded by switches out all ports except incoming, but routers will not forward it. This is why each router interface defines a new broadcast domain.
⚠️
Trap 7: Multicast MAC for IPv4 starts with 01-00-5E. For IPv6 starts with 33-33.
Multicast is NOT the same as broadcast. Broadcast goes to all devices. Multicast goes to devices that have joined a specific group. Source is always unicast — only destination can be multicast. Routers don't forward multicast by default.
⚠️
Trap 8: MAC address = 48 bits = 12 hex digits = 6 bytes. OUI = first 6 hex digits (assigned by IEEE). Vendor code = last 6 hex digits.
The OUI identifies the manufacturer. The vendor is responsible for making the last 6 digits unique per device. If two devices on the same network segment have the same MAC, communication breaks for both.
⚠️
Trap 9: Store-and-forward required for QoS. Cut-through has lower latency but may forward corrupt frames.
Store-and-forward validates the entire CRC before forwarding — this is required for QoS traffic classification (like prioritizing VoIP over web traffic). Cut-through starts forwarding after reading only the destination MAC — lower latency but no CRC validation.
⚠️
Trap 10: Fragment-free stores first 64 bytes. Fast-forward reads only destination MAC.
Fragment-free is a compromise — it checks the first 64 bytes (where most errors and collisions occur) without checking the full frame. Fast-forward checks nothing — it's pure speed. Both are cut-through variants and neither performs a full CRC check.
⚠️
Trap 11: Shared memory buffering supports asymmetric switching. Port-based can cause head-of-line blocking.
Port-based memory: one frame waiting for a busy port blocks all frames behind it in the queue (even if they're destined for free ports). Shared memory fixes this. Shared memory also supports different port speeds (10 Gbps server + 1 Gbps PCs).
⚠️
Trap 12: MAC aging timer = 5 minutes. A switch port can have multiple MAC addresses.
Entries are removed after 5 minutes of inactivity (no frame received with that source MAC). Multiple MACs per port is normal when a port connects to another switch — the upstream switch sees all MACs from devices behind the downstream switch on that one port.
