17.1Devices in a Small Network▾

17.1.2 Device Selection — Four Key Factors

FactorDetails
CostDetermined by capacity, port count, backplane speed, built-in redundancy, management features, embedded security. Cable runs also factor in.
Speed and Port TypesMatch ports to device NICs (1 Gbps common; some servers need 10 Gbps). Selecting higher-speed devices future-proofs the network.
ExpandabilityFixed = specific port count, cannot expand. Modular = expansion slots for new modules as needs grow. Consider uplink port options.
OS FeaturesMust support needed functions: Layer 3 switching, NAT, DHCP, Security, QoS, VoIP support

17.1.3 IP Addressing Scheme by Device Type

Plan, document, and maintain an IP addressing scheme organized by device type. Structured ranges enable easier troubleshooting and summarization. Example for 192.168.x.0/24:

Device TypeRangeSubnet
Default gateway (Router).1–.2.0/30
Switches (max 2).5–.6.4/30
Access points (max 6).9–.14.8/29
Servers (max 6).17–.22.16/29
Printers (max 6).25–.30.24/29
IP Phones (max 6).33–.38.32/29
Wired devices (max 62).65–.126.64/26
Wireless devices (max 62).193–.254.192/26

17.1.4 Redundancy

Redundancy eliminates single points of failure. Methods: duplicate equipment OR duplicate links for critical areas.

⚠️
Small networks typically have a single router as the exit to the internet. If that router fails, all internet connectivity is lost. Consider contracting a second ISP as a backup WAN connection for business-critical networks.

17.1.5 Traffic Management — QoS

QoS (Quality of Service) classifies network traffic by priority so that real-time traffic (voice, video) gets preferential treatment over regular data traffic. Configure on both routers and switches. Without QoS, voice calls degrade significantly when the network is congested.

17.2Applications and Protocols▾

17.2.1–17.2.2 Common Applications and Protocols

Two types of software providing network access:

  • Network Applications — directly implement application layer protocols (email clients, web browsers)
  • Application Layer Services — programs that interface with the network on behalf of other applications (file transfer services, print spooling)
✅
Best practice — always use the secure version:
SSH over Telnet · SFTP/FTPS over FTP · HTTPS over HTTP
A single server can provide multiple services simultaneously (email + FTP + web + DNS).

17.2.3 Voice and Video Applications

TechnologyDescription
VoIPConverts analog telephone signals to digital IP packets. Less expensive than IP telephony but lower quality. Examples: Skype, WebEx.
IP TelephonyVoice converted to IP using a dedicated call control server. Vendors: Cisco Business Edition 4000.
RTPReal-Time Transport Protocol — carries the actual audio/video streams across the network.
RTCPReal-Time Transport Control Protocol — monitors the QoS of RTP sessions; provides feedback on transmission quality.
💡
Both VoIP and IP telephony require QoS to minimize latency. Voice is very sensitive to delay (latency) and jitter. Even small delays cause noticeable quality degradation in voice calls.

  • Use Wireshark or similar protocol analyzer to capture and analyze traffic
  • Capture during peak utilization times to get representative data
  • Capture on different network segments — some traffic is only local to a segment
  • Use analysis to decide on traffic management, server relocation, or network redesign
17.4Verify Connectivity▾

17.4.1 Ping — Windows vs IOS

🪟 Windows
Sends 4 ICMP echo messages. Shows RTT min/avg/max. Output shows each reply with time in ms.
🔧 Cisco IOS
Sends 5 ICMP echo messages. Shows !/./U indicators. Shows success rate percentage and RTT.

IOS Ping Output Indicators:

!Success
Echo reply received — Layer 3 connectivity confirmed
.Timeout
No reply received — connectivity problem somewhere along path
UUnreachable
Router sent ICMP Type 3 Destination Unreachable — no route to destination
IOS Ping — Success and Failure Examples
R1# ping 10.1.1.10
Sending 5, 100-byte ICMP Echos to 10.1.1.10, timeout is 2 seconds:
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/2 ms

R1# ping 10.2.2.10
Sending 5, 100-byte ICMP Echos to 10.2.2.10, timeout is 2 seconds:
.....
Success rate is 0 percent (0/5)

R1# ping 172.16.1.1
UUUUU
Success rate is 0 percent (0/5)    ← Router knows there's no route

17.4.2 Extended Ping

Standard ping uses the outgoing interface IP as the source address. Extended ping lets you specify a different source address — critical for testing whether specific subnets are reachable through a router.

Extended Ping — Privileged EXEC Mode
R1# ping                         ← Type ping with no destination
Protocol [ip]:                   ← Press Enter for IPv4
Target IP address: 10.1.1.10
Repeat count [5]:
Datagram size [100]:
Timeout in seconds [2]:
Extended commands [n]: y         ← Type y for extended options
Source address or interface: 192.168.10.1   ← Specify source
Type of service [0]:
...
!!!!!
Success rate is 100 percent (5/5)

R1# ping ipv6                    ← For IPv6 extended ping

17.4.3–17.4.4 Traceroute / tracert

PlatformCommandProtocol UsedInterrupt
WindowstracertICMP Echo RequestsCtrl-C
Cisco IOS / LinuxtracerouteUDP with invalid port (destination responds with ICMP Port Unreachable)Ctrl-Shift-6
💡
Extended traceroute: Like extended ping, enter traceroute with no destination in privileged EXEC to specify source address, probe count, timeout, and more. Useful for testing specific subnet paths, detecting routing loops, and finding where packets are dropped or denied.

17.4.5 Network Baseline

A baseline captures normal performance benchmarks over time for future comparison.

  • Method: copy/paste ping or traceroute output with timestamps into a text file
  • Run captures at different times — peak and off-peak
  • Archive baseline files and compare against future captures
  • Significant RTT increase = potential latency/congestion issue
  • Baseline enables detecting performance degradation before it becomes a crisis

17.5.4 arp -a Command

arp -a displays the ARP cache — IP-to-MAC mappings for recently communicated devices. Works on Windows, Linux, and macOS.

💡
ARP cache only shows devices recently communicated with. Ping a device first to populate the cache entry for it. To clear the cache on Windows (requires admin): netsh interface ip delete arpcache

17.5.5 Common IOS show Commands

show running-configCurrent active configuration and all settings

show ip interfaceLayer 3 information for each interface
show arpKnown hosts on local Ethernet LANs (IP-to-MAC table)
show ip routeLayer 3 routing table — how to reach destinations
show protocolsWhich protocols are enabled and operational
show versionMemory, interface count, IOS version, and licenses

17.5.6 CDP — Cisco Discovery Protocol

CDP is Cisco proprietary, runs at Layer 2, and automatically discovers neighboring Cisco devices regardless of their Layer 3 (IP) status. Very useful when two devices are directly connected but routing between them isn't working.

CDP provides per neighbor: hostname · IP addresses · local and remote port IDs · capabilities (L2/L3 switch, router) · hardware platform

show cdp neighbors and detail
R3# show cdp neighbors
Device ID  Local Intrfce  Holdtme  Capability  Platform    Port ID
S3         Gig 0/0/1      122      S I         WS-C2960+   Fas 0/5

R3# show cdp neighbors detail
! Also shows IP address of neighbor — useful when routing is broken
! and you need to verify the neighbor's IP configuration
⚠️
CDP security risk: CDP reveals detailed network infrastructure information. Best practice: enable CDP only on interfaces connecting to other Cisco infrastructure devices.
no cdp enable — disable CDP on a specific interface (user-facing ports)
no cdp run — disable CDP globally on the device

17.5.7 show ip interface brief

The most frequently used summary command. Shows all interfaces, assigned IP addresses, and operational status in a compact format.

show ip interface brief — Output Example
R1# show ip interface brief
Interface           IP-Address       OK?  Method  Status    Protocol
GigabitEthernet0/0/0  209.165.200.225  YES  manual  up        up
GigabitEthernet0/0/1  192.168.10.1     YES  manual  up        up
Serial0/1/0           unassigned       NO   unset   down      down
🎯 STATUS vs PROTOCOL
Status = Layer 1 (Physical) — is the cable connected?
Protocol = Layer 2 (Data Link) — is encapsulation working?

Both must be up/up for full operation.
Status up / Protocol down = Layer 2 encapsulation problem
Status down / Protocol down = no physical connection (or administratively shut down)
17.6Troubleshooting Methodologies▾

17.6.1 Six-Step Troubleshooting Process

1
Identify the Problem — Gather information from users, logs, and monitoring tools. Define the symptoms clearly.
2
Establish Theory of Probable Causes — List multiple possible causes from most likely to least likely. Don't jump to conclusions.
3
Test the Theory to Determine Cause — Apply quick tests to confirm or eliminate each theory. Narrow down to the actual cause.
4
Establish Plan of Action and Implement the Solution — Fix the identified cause. If the fix requires major changes, develop a plan first.
5
Verify Solution and Implement Preventive Measures — Confirm full functionality is restored. Take steps to prevent the problem from recurring.
6
Document Findings, Actions, and Outcomes — Record everything: the problem, cause, solution, and timeline. Critical for future reference and pattern recognition.
💡
Escalate when: the issue requires a manager decision, specific expertise beyond the technician's level, or network access that the technician doesn't have. Company policy should define escalation procedures.

17.6.3 debug Command

debug displays real-time system messages for troubleshooting. It is a high-priority CPU process — overuse can make the system unresponsive. Only use for specific, targeted problems.

debug Command Usage
R1# debug ip icmp          ! Enable ICMP debug output
R1# ping 10.1.1.1          ! Trigger some ICMP traffic
ICMP: echo reply rcvd, src 10.1.1.1, dst 209.165.200.225

R1# no debug ip icmp       ! Disable specific debug
R1# undebug ip icmp        ! Alternative syntax (same result)
R1# undebug all            ! ALWAYS run this when done — turns off ALL active debugs
🚨
Never run in production: debug all and debug ip packet generate massive output and can crash a router under load. Always undebug all when finished debugging. Use only for targeted, specific troubleshooting.

17.6.4 terminal monitor

By default, debug output only appears on the console port. It does NOT appear on remote (Telnet/SSH) vty sessions. Use terminal monitor to enable debug/log messages on the current vty session.

terminal monitor — Enable Debug on vty
R1# terminal monitor       ! Enable debug/log output on this vty session
R1# debug ip icmp          ! Now debug output will appear here too
R1# terminal no monitor    ! Disable debug output on this vty session
17.7Troubleshooting Scenarios▾

17.7.1–17.7.5 Five Common Troubleshooting Scenarios

🔄 Duplex Mismatch
Symptom: Link works but performance is very poor (high collisions, retransmissions).
Cause: One end set to full-duplex, other end half-duplex. Caused by misconfiguration or failed autonegotiation.
Why hard to detect: The link is UP — traffic passes — but throughput is severely degraded.
Fix: Set both ends to the same duplex mode manually, or ensure autonegotiation is enabled on both ends.
🔢 Wrong IP Address on Device
Symptom: Device cannot reach expected destinations; IP conflicts.
Cause: Manual assignment error OR DHCP assigned wrong address.
Verify: show ip interface brief (IOS) or ipconfig (Windows).
Fix: Correct the IP address assignment.
🚨 APIPA — 169.254.x.x Address
Symptom: Windows host shows 169.254.x.x address; cannot communicate with other devices.
Cause: Windows could NOT reach the DHCP server. APIPA assigns from 169.254.0.0/16 automatically.
Note: Linux and macOS do NOT auto-assign — they leave the interface unconfigured when DHCP fails.
Fix: Restore DHCP connectivity or manually assign an IP address. Run ipconfig /release then ipconfig /renew after restoring DHCP.
🌐 Default Gateway Issue
Symptom: Host can reach local network devices but cannot reach anything on remote networks.
Cause: Gateway IP missing, wrong, or not in the same subnet as the host.
Verify: ipconfig (Windows) · show ip route | begin Gateway (IOS — "Gateway of last resort")
Fix: Correct the default gateway address to match the router interface on the same subnet.
🔍 DNS Failure (Looks Like Network Is Down)
Symptom: User reports "internet is down" — websites won't load by name.
Reality: IP connectivity is fine — DNS resolution has failed. All other network services still work.
Test: Ping 8.8.8.8 (Google DNS) directly — if it succeeds, network is up; DNS is the problem.
Verify: ipconfig /all (shows configured DNS servers) · nslookup (manual DNS query)
Public DNS servers (fallback):
Google: 8.8.8.8 / 2001:4860:4860::8888
OpenDNS (Cisco): 208.67.222.222 / 208.67.220.220

🎯Common Exam Traps — Module 17▾
❌
Trap 1: Windows ping = 4 packets. Cisco IOS ping = 5 packets. IOS symbols: ! = success, . = timeout, U = unreachable.
The count and output format differ completely. Windows shows text with RTT. IOS shows symbols. The U symbol means a router explicitly replied with ICMP Destination Unreachable — different from a timeout (.) where no response came back at all.
❌
Trap 2: APIPA = 169.254.0.0/16 = Windows DHCP failure. Linux/macOS do NOT auto-assign when DHCP fails.
Seeing a 169.254.x.x address on a Windows host means one thing: DHCP server is unreachable. The host self-assigned from the APIPA range. Linux and macOS leave the interface unconfigured instead. This distinction is directly tested.
❌
Trap 3: DNS failure looks like a full network outage to users — but the network is working fine.
"The internet is down" often means DNS is failing. Test by pinging an IP directly (8.8.8.8). If the ping succeeds, the network is fine and only DNS has failed. Use nslookup to further diagnose DNS problems.
❌
Trap 4: Six troubleshooting steps in order: Identify → Theory → Test → Plan/Implement → Verify/Prevent → Document.
Step 6 (documentation) is the most commonly forgotten step in scenarios. Steps 2 and 3 are also commonly confused — you establish the theory first, then test it. Never skip directly from identifying the problem to implementing a fix without forming and testing a theory.
❌
Trap 5: debug output only appears on console by default — NOT on vty. Use terminal monitor to fix this.
A very common practical mistake. SSH into a router, run debug ip icmp, see nothing. The fix is terminal monitor before the debug command. Always run undebug all when done to avoid CPU overload.
⚠️
Trap 6: show ip interface brief — Status = L1 (physical), Protocol = L2 (data link). Both must be up/up.
Status up / Protocol down = encapsulation mismatch or L2 problem. Status down / down = no physical connection or interface is shut down. This two-column read tells you exactly which layer has the problem.
⚠️
Trap 7: CDP is Cisco proprietary, Layer 2, discovers directly connected Cisco neighbors only.
CDP does not require IP connectivity — it works at Layer 2. show cdp neighbors shows hostname, port, and platform. show cdp neighbors detail also shows IP address. Disable on user-facing ports (no cdp enable) for security.
⚠️
Trap 8: tracert (Windows uses ICMP). traceroute (IOS/Linux uses UDP with invalid port).
The underlying protocol is different. On IOS/Linux, the final destination replies with ICMP Port Unreachable (not Echo Reply) because UDP was sent to an invalid port. This is why IOS traceroute sometimes shows different results than Windows tracert.
⚠️
Trap 9: Extended ping/traceroute allows specifying a custom source address — entered with no destination argument.
Type ping or traceroute in privileged EXEC with no destination to enter extended mode. Critical for testing whether traffic from a specific subnet or interface can reach a destination — important for verifying NAT, routing, and ACL configurations.
⚠️
Trap 10: Duplex mismatch = link appears UP but performance is extremely poor.
This is what makes it deceptive — the interface is not down, so monitoring may not alert on it. Collisions spike, throughput drops severely. Always check duplex settings when performance problems occur on a link that appears operational.
⚠️
Trap 11: Default gateway must be in the SAME subnet as the host. Wrong gateway = no remote communication.
If a host's gateway IP is from a different subnet, the host can't ARP for it and can't send packets off-network. The host can still reach local devices on the same subnet, but nothing beyond the local network will work.
⚠️
Trap 12: RTP carries voice/video streams. RTCP monitors QoS of RTP. Both need QoS configured.
RTP and RTCP work together for real-time media. VoIP converts analog to digital IP packets (lower cost, less quality). IP Telephony uses a dedicated call control server (higher quality, more infrastructure). QoS must be configured on both routers and switches for voice/video to work acceptably.
