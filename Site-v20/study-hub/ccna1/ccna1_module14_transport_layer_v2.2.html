14.1Transportation of Data▾

14.1.1 Role of the Transport Layer

The transport layer provides logical communications between applications running on different hosts. It is the link between the application layer and the lower layers responsible for network transmission.

The transport layer has no knowledge of: destination host type, media type, path taken, congestion on a link, or network size. Its two protocols are TCP and UDP.

14.1.2 Five Transport Layer Responsibilities

#ResponsibilityDescription
1Track conversationsEach app-to-app flow = a separate "conversation" tracked independently. Multiple simultaneous conversations per host.
2Segment and reassemble dataDivides app data into blocks. TCP calls them segments; UDP calls them datagrams.
3Add header informationTransport header enables reassembly, error checking, and port identification at the destination.
4Identify applicationsUses port numbers to route data to the correct application process.
5Conversation multiplexingMultiple conversations interleaved on the same network simultaneously using segmentation and port numbers.

14.1.4–14.1.6 TCP vs UDP — When to Use Which

🔒 TCP — Reliable
  • Connection-oriented
  • Reliable — guaranteed delivery
  • In-order delivery (sequence numbers)
  • Flow control (window size)
  • 20-byte header overhead
  • Stateful
  • Slower but complete
Use for: HTTP, HTTPS, FTP, SMTP, SSH, Telnet, POP3, IMAP, databases, stored video/audio
⚡ UDP — Fast
  • Connectionless
  • Best-effort — no guarantee
  • Delivers in order received (no reorder)
  • No flow control
  • 8-byte header overhead
  • Stateless
  • Faster but lossy possible
Use for: VoIP, live video, DNS, DHCP, TFTP, SNMP, video conferencing
💡
Stored audio/video (on-demand streaming): Uses TCP. Buffering allows the app to pause and re-establish if the connection drops. The "buffering…" message = TCP working to restore the stream.

Real-time audio/video (live): Uses UDP. A momentary glitch is more acceptable than the delay caused by waiting for retransmission.
14.2TCP Overview▾

14.2.1 TCP Four Key Features

FeatureDescription
Establishes a SessionConnection-oriented — negotiates a session (three-way handshake) before sending any data
Ensures Reliable DeliveryTracks each segment sent; retransmits any that are lost or corrupted
Provides Same-Order DeliverySequence numbers ensure segments are reassembled in the correct order even if they arrive out of order
Supports Flow ControlWindow size field adjusts data transmission rate to prevent receiver overload

14.2.2–14.2.3 TCP Header — 10 Fields · 20 Bytes Total

TCP adds 20 bytes (160 bits) of overhead to each segment:

Source Port16 bits
Identifies the sending application by port number
Destination Port16 bits
Identifies the receiving application by port number
Sequence Number32 bits
Position of first data byte in this segment; used for reordering and reassembly
Acknowledgment #32 bits
Next byte expected from sender; confirms all bytes before this were received
Header Length4 bits
"Data offset" — length of the TCP header
Reserved6 bits
Reserved for future use
Control Bits6 bits
Flags: URG, ACK, PSH, RST, SYN, FIN
Window Size16 bits
Bytes receiver can accept before requiring an ACK — used for flow control
Checksum16 bits
Error checking for header and data
Urgent16 bits
Indicates urgent data that should be processed immediately

14.2.3 Six TCP Control Flags

SYNSynchronize — initiates connection; establishes ISN
ACKAcknowledge — confirms receipt; used in handshake and data transfer
FINFinish — no more data from sender; graceful close
RSTReset — abruptly closes connection on error or timeout
PSHPush — send data to application immediately without buffering
URGUrgent — data in this segment should be processed first
💡
TCP applications: HTTP (80) · HTTPS (443) · FTP (20/21) · SSH (22) · Telnet (23) · SMTP (25) · POP3 (110) · IMAP (143)
14.3UDP Overview▾

14.3.1 UDP Features

  • Data reconstructed in order received — no reordering
  • Lost segments are NOT resent
  • No session establishment — connectionless
  • Sender is NOT informed about resource availability at receiver
  • Stateless — neither client nor server tracks session state

14.3.2–14.3.3 UDP Header — 4 Fields · 8 Bytes Total

UDP adds only 8 bytes (64 bits) of overhead per datagram — much simpler than TCP:

Source Port16 bits
Identifies the sending application by port number
Destination Port16 bits
Identifies the receiving application by port number
Length16 bits
Length of the UDP datagram header and data combined
Checksum16 bits
Error checking of the datagram header and data
💡
UDP is described as "best-effort" because there is no mechanism to confirm delivery, request retransmission, or control the rate of data flow. What it lacks in reliability it makes up in speed and simplicity.

14.3.4 Three Categories of UDP Applications

CategoryWhy UDPExamples
Live video and multimediaTolerates some loss; cannot tolerate delay from retransmissionVoIP, live video streaming
Simple request-replySmall transactions; if no reply, client simply resends the requestDNS (port 53), DHCP (67/68)
App handles reliability itselfApplication layer manages sequencing and recoverySNMP (161), TFTP (69)
⚠️
DNS uses UDP by default (port 53), but switches to TCP when response exceeds 512 bytes (e.g., zone transfers or large responses with many records). SNMP can also use TCP in some configurations.
14.4Port Numbers▾

14.4.1 Source and Destination Ports

Port numbers are 16-bit values (range 0–65535) that identify which application process should handle the data.

Port TypeWho Assigns ItPurpose
Source PortDynamically assigned by the client OS when connection is initiatedIdentifies the specific client conversation — acts as the return address
Destination PortWell-known or registered (specified by client in request)Identifies the service being requested on the server
💡
When the server responds, it reverses the port numbers: the original destination port becomes the source port of the response, and the original source port becomes the destination port of the response. This is how the response gets back to the correct client application.

14.4.2 Sockets and Socket Pairs

Socket = IP address + port number (identifies one endpoint of a connection)

Socket Examples
Client socket:  192.168.1.5:1099    (IP:ephemeral-port)
Server socket:  192.168.1.7:80      (IP:well-known-port)
Socket pair:    192.168.1.5:1099, 192.168.1.7:80  (unique conversation)

A socket pair uniquely identifies every conversation on the network. This is how a server distinguishes between thousands of simultaneous client connections to the same port — each has a different client socket (different source IP or port).

14.4.3 Three Port Number Groups

0 – 1,023 · Well-Known PortsReserved for common services (HTTP, FTP, SSH, etc.). Defined by IANA. Clients use these as destination ports to request specific services.
1,024 – 49,151 · Registered PortsAssigned by IANA to specific applications on request (e.g., Cisco RADIUS = 1812). Used by vendor-specific applications.
49,152 – 65,535 · Private / Dynamic / Ephemeral PortsDynamically assigned by the client OS when initiating a connection. Serve as the source port for the client. Released when the session ends.

14.5TCP Communication Process▾

14.5.2 TCP Three-Way Handshake — Connection Establishment

TCP is full-duplex. Before any data is sent, a three-way handshake establishes the connection:

1
Client → Server
SYN — Client requests connection. Sends its Initial Sequence Number (ISN). "I want to start a session on this port."
2
Server → Client
SYN + ACK — Server acknowledges client SYN and sends its own ISN. "I acknowledge your SYN and I'm ready. Here's my sequence number."
3
Client → Server
ACK — Client acknowledges server SYN. Connection is now established. Data can flow.
✅
The three-way handshake accomplishes three things:
1. Confirms destination device is present on the network
2. Confirms destination has an active service on the requested port
3. Informs destination that source intends to establish a session on that port

14.5.3 TCP Session Termination — Four Exchanges

TCP termination requires 4 exchanges because TCP is full-duplex — each direction is closed separately. Either side can initiate:

1
Client → Server
FIN — Client has no more data to send. "I'm done sending."
2
Server → Client
ACK — Server acknowledges client FIN. Server may still have data to send.
3
Server → Client
FIN — Server has no more data to send. "I'm done sending too."
4
Client → Server
ACK — Client acknowledges server FIN. Connection fully closed.
⚠️
Handshake = 3 steps (SYN → SYN-ACK → ACK). Termination = 4 steps (FIN → ACK → FIN → ACK). Never confuse these. Termination is 4 because each one-way session closes independently.
14.6Reliability and Flow Control▾

14.6.1 Sequence Numbers, ISN, and Acknowledgments

ConceptDescription
Sequence NumberPosition of the first data byte in a segment within the full data stream. Used to reorder and reassemble segments at the destination.
ISN (Initial Sequence Number)Randomly chosen starting value — NOT 1 in real networks (prevents security attacks). Negotiated during the three-way handshake.
Acknowledgment NumberNext byte expected from the sender. Confirms all bytes before this number were received. (Example: ACK=301 means "I received bytes 1–300, send byte 301 next.")

14.6.3 Data Loss, Retransmission, and SACK

Without SACK: If segments 3 and 4 are missing out of 10 sent, the receiver ACKs segment 3 (next expected). The sender must retransmit segments 3–10, even though segments 5–10 arrived successfully → wasted bandwidth.

With SACK (Selective Acknowledgment): Receiver explicitly reports which segments it has received, including non-contiguous ones. Sender retransmits only the missing segments (3 and 4 in the example).

💡
SACK is optional and must be negotiated during the three-way handshake. Most modern operating systems support SACK. TCP also uses timers — if a segment isn't acknowledged within the timer period, the sender retransmits it.

14.6.5 Flow Control — Window Size and Sliding Windows

Sliding Window — How Flow Control Works
1
During handshake, PC B tells PC A its window size = 10,000 bytes — "you can send up to 10,000 bytes before I need to ACK"
2
PC A begins sending data. It does NOT wait for all 10,000 bytes to be acknowledged before sending more — it keeps sending within the window.
3
PC B sends ACK after receiving some bytes (e.g., ACK 2,921 = "I've received bytes 1–2920, send me 2921 next")
4
PC A's send window slides forward — it can now send bytes 2,921 through 12,920 (still a 10,000-byte window)
5
If PC B's buffers fill → it reduces window size → PC A slows down. Window can increase again as buffers free up.
💡
Window size = 16-bit field in TCP header = maximum bytes receiver can accept before requiring an ACK.
Sliding windows = the continuous process of receiver sending ACKs + sender adjusting its send window forward. Allows continuous data flow without stop-and-wait.

14.6.6 Maximum Segment Size (MSS)

MSS = maximum payload (data) bytes in a single TCP segment — does NOT include the TCP header. Negotiated during the three-way handshake.

Ethernet MTU:1,500 bytes
minus IP header:−20 bytes
minus TCP header:−20 bytes
Default MSS:1,460 bytes

14.6.7 Congestion Avoidance

When a router drops packets due to congestion → segments go unacknowledged → source detects congestion → source reduces the number of unacknowledged bytes it sends (not the window size set by the destination).

⚠️
It is the source that reduces its send rate in response to congestion — not the destination window size. The destination window size reflects the receiver's buffer capacity; the source's self-imposed limit is the congestion control mechanism.
14.7UDP Communication▾

14.7.1–14.7.4 UDP Communication Details

AspectUDP Behavior
ReassemblyUDP delivers datagrams to the application in the order they arrive — no reordering. If sequencing matters, the application must handle it.
Lost datagramsSimply lost — UDP has no mechanism to detect or recover them. No retransmission.
Server port numbersUDP servers listen on well-known or registered port numbers, just like TCP servers.
Client source portUDP client dynamically selects an ephemeral source port (49152–65535) when initiating a session.
Server responseServer reverses source and destination ports in its response — same mechanism as TCP.
Port consistencySame source/destination port pair used for all datagrams in a transaction.

🎯Common Exam Traps — Module 14▾
❌
Trap 1: TCP = connection-oriented, reliable, stateful. UDP = connectionless, best-effort, stateless.
The most fundamental distinction in this module. TCP establishes a session (handshake) before sending. UDP sends without any connection setup. TCP tracks every segment and retransmits if needed. UDP does not.
❌
Trap 2: TCP header = 20 bytes (10 fields). UDP header = 8 bytes (4 fields).
TCP: Source Port + Destination Port + Sequence # + ACK # + Header Length + Reserved + Control Bits + Window Size + Checksum + Urgent. UDP: Source Port + Destination Port + Length + Checksum. The 4 extra TCP fields (Sequence, ACK, Window, Control Bits) enable reliability and flow control.
❌
Trap 3: Handshake = 3 steps (SYN→SYN-ACK→ACK). Termination = 4 steps (FIN→ACK→FIN→ACK).
These are directly tested in sequence questions. The handshake opens one bidirectional channel in 3 steps. Termination closes each direction separately — hence 4 steps (2 FIN/ACK pairs). Either side can initiate termination.
❌
Trap 4: Acknowledgment number = next expected byte, NOT the last received byte.
If bytes 1–300 were received, the ACK number = 301 ("send me byte 301 next"). Students often confuse this as 300. The ACK number is always one more than the last successfully received byte.
❌
Trap 5: ISN is randomly chosen — NOT starting at 1 in real networks.
The random ISN prevents certain security attacks that could predict sequence numbers. Exams may use ISN=1 for simplicity in worked examples, but always note "for simplicity" — the real ISN is random and negotiated during the handshake.
⚠️
Trap 6: Port groups — 0–1023 (well-known), 1024–49151 (registered), 49152–65535 (dynamic/ephemeral).
The boundary numbers are tested. Well-known = common server services. Registered = vendor applications. Dynamic/ephemeral = client source ports assigned by the OS. Know all three ranges and their names.
⚠️
Trap 7: Socket = IP + port. Socket pair = unique conversation identifier.
A single socket identifies one endpoint. A socket pair (source IP:port + destination IP:port) uniquely identifies a specific conversation. Multiple browser tabs to the same website = different source ports = different socket pairs = different conversations tracked separately.
⚠️
Trap 8: MSS = 1,460 bytes = MTU(1500) − IP header(20) − TCP header(20).
MSS is the TCP payload size, NOT including the TCP header. Negotiated during the three-way handshake. A larger MSS means fewer segments for the same amount of data = more efficient transmission.
⚠️
Trap 9: SACK allows retransmission of ONLY the missing segments. Without SACK, all subsequent segments must be retransmitted.
SACK (Selective Acknowledgment) is negotiated during the three-way handshake. Without it, if segment 3 is missing from segments 1–10, the sender must retransmit 3–10 (even though 4–10 arrived fine). With SACK, only 3 is retransmitted.
⚠️
Trap 10: Congestion avoidance — SOURCE reduces its send rate. Not the destination window.
When the source detects congestion (unacknowledged segments), it self-limits the number of bytes it sends without acknowledgment. The destination's window size reflects buffer capacity — a separate concept from congestion control.
⚠️
Trap 11: DNS uses UDP port 53 by default but switches to TCP port 53 for responses >512 bytes.
Standard DNS queries and responses = UDP. DNS zone transfers between servers = always TCP. Very large responses (many records) = TCP. Both are port 53.
⚠️
Trap 12: UDP does NOT reorder datagrams — delivers in order received. Application handles sequencing if needed.
Unlike TCP which buffers segments and reorders them before passing to the application, UDP simply passes each datagram to the application in the order it arrives. Out-of-order datagrams stay out of order unless the application corrects them.
✅
