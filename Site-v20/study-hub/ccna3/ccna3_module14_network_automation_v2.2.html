14.1Automation Overview▾

14.1.2 The Increase in Automation

Automation = any process that is self-driven and reduces — or potentially eliminates — the need for human intervention.

Benefits of automation:

  • Machines work 24/7 without breaks → greater output volume
  • Machines produce a more uniform, consistent product — fewer human errors
  • Enables collection of vast amounts of data for rapid analysis and informed decision-making
  • Robots handle dangerous conditions (mining, firefighting, industrial accident cleanup) → reduces risk to humans
  • Smart devices can alter behavior to reduce energy usage, aid medical diagnosis, improve driving safety

14.1.3 Thinking Devices and Smart Devices

A smart device = any device that takes a course of action based on an outside piece of information. Having "smart" in a device name indicates it can alter behavior depending on its environment.

💡
For smart devices to "think" and react, they must be programmed using network automation tools. Without programming, devices cannot make intelligent decisions — they simply execute fixed instructions.
14.2Data Formats▾

14.2.2 The Three Common Data Formats

Data formats = structured ways to store and exchange data so computers can understand each other. The three primary formats used in network automation and programmability:

{ } JSON — JavaScript Object Notation
Human readable. Very popular for web services and APIs. Easy to parse. Works with most modern programming languages including Python. Uses curly braces { } for objects and square brackets [ ] for arrays.
⬛ YAML — YAML Ain't Markup Language
Minimalist and most human-readable. Superset of JSON. Uses indentation instead of brackets or commas to define structure. A hyphen `-` separates list elements. No quotation marks on keys.
</> XML — eXtensible Markup Language
Like HTML but with no predefined tags — you define your own. Self-descriptive: data enclosed within paired tags <tag>data</tag>. Most verbose of the three formats. Lists use repeated instances of the same tag.
💡
The format selected depends on the application, tool, or script being used. Many systems support more than one format and allow user preference.

14.2.3 Data Format Rules — Key/Value Pairs

All data formats have rules and structure (similar to programming languages):

  • Syntax — brackets used [ ] ( ) { }, whitespace/indentation, quotes, commas
  • How objects are represented — characters, strings, lists, arrays
  • Key/value pairs — key (left side) identifies the data; value (right side) is the actual data
ISS Location API — same data in all three formats 

JSON:
{
  "message": "success",
  "timestamp": 1560789260,
  "iss_position": {
    "latitude": "25.9990",
    "longitude": "-132.6992"
  }
}


YAML:
message: success
timestamp: 1560789260
iss_position:
    latitude: '25.9990'
    longitude: '-132.6992'


XML:
<?xml version="1.0" encoding="UTF-8" ?>
<root>
  <message>success</message>
  <timestamp>1560789260</timestamp>
  <iss_position>
    <latitude>25.9990</latitude>
    <longitude>-132.6992</longitude>
  </iss_position>
</root>

14.2.5–14.2.6 JSON Syntax Rules — Objects and Arrays

JSON Objects — one or more key/value pairs enclosed in curly braces { }:

  • Keys must be strings in double quotation marks " "
  • Values must be a valid JSON type: string, number, array, Boolean, null, or another object
  • Keys and values separated by a colon :
  • Multiple key/value pairs separated by commas ,
  • Whitespace is not significant — can add for readability without affecting data

JSON Arrays — ordered list of values enclosed in square brackets [ ]:

  • Key followed by colon, then list in [ ]
  • Each array element separated by comma
  • Can contain strings, numbers, Booleans, objects, or other arrays
JSON interface example with array 
{
    "ietf-interfaces:interface": {
         "name": "GigabitEthernet0/0/0",
         "description": "Wide Area Network",
         "enabled": true,
         "ietf-ip:ipv4": {
             "address": [
                 {
                     "ip": "172.16.0.2",
                     "netmask": "255.255.255.0"
                 },
                 {
                     "ip": "172.16.0.3",
                     "netmask": "255.255.255.0"
                 }
             ]
          }
    }
}
! { } = object   [ ] = array
! Keys MUST be in double quotes
! "enabled": true   ← Boolean value (no quotes)
! Array of address objects uses [ ]

14.2.7 YAML Syntax Rules — Indentation

  • Superset of JSON — all valid JSON is valid YAML
  • Uses indentation to define structure (no brackets or commas)
  • Key/value pairs separated by colon — no quotation marks on keys
  • A hyphen - separates each element in a list
  • Considered most human-readable of the three formats
YAML interface example 
ietf-interfaces:interface:
  name: GigabitEthernet2
  description: Wide Area Network
  enabled: true
  ietf-ip:ipv4:
    address:
    - ip: 172.16.0.2          ← hyphen marks list element
      netmask: 255.255.255.0
    - ip: 172.16.0.3          ← second list element
      netmask: 255.255.255.0
! No { } brackets · No [ ] brackets · No commas
! Indentation defines hierarchy
! Hyphens separate list items

14.2.8 XML Syntax Rules — Tags

  • Like HTML but no predefined tags or document structure
  • Self-descriptive — encloses data within related tags: <tag>data</tag>
  • Key/value pair: beginning tag = key, data inside = value: <key>value</key>
  • Lists use repeated instances of the same tag for each element
  • Most verbose of the three formats
XML interface example 
<?xml version="1.0" encoding="UTF-8" ?>
<ietf-interfaces:interface>
  <name>GigabitEthernet2</name>
  <description>Wide Area Network</description>
  <enabled>true</enabled>
  <ietf-ip:ipv4>
    <address>                         <!-- list item 1 -->
      <ip>172.16.0.2</ip>
      <netmask>255.255.255.0</netmask>
    </address>
    <address>                         <!-- list item 2 -->
      <ip>172.16.0.3</ip>
      <netmask>255.255.255.0</netmask>
    </address>
  </ietf-ip:ipv4>
</ietf-interfaces:interface>
! <tag>value</tag> = key/value pair
! No predefined tags (unlike HTML)
! Lists = repeated instances of same tag

14.3APIs▾

14.3.2 The API Concept

API (Application Programming Interface) = software that allows other applications to access its data or services. A set of rules describing how one application can interact with another.

🍽️
Waiter analogy: The waiter (API) takes the customer's order (API request) to the kitchen (server) and delivers the food (API response) back. The customer doesn't need to know how the kitchen works — the waiter handles all the interaction. The message from the requesting application to the server = API call.

14.3.4 Three Types of APIs

🌐 Open / Public APIs
Publicly available with no restrictions. Many require a free key or token to control request volume and identify the source. Example: ISS Location API, Google Maps (requires free key).
🔒 Internal / Private APIs
Used only within a company or organization to access internal data and services. Not available to the public or partners. Example: salespeople accessing internal sales data on mobile devices.
🤝 Partner APIs
Used between a company and its business partners or contractors. Requires license or permission to use. Example: a travel service using an airline's API to display flight information and pricing.

14.3.5 Four Types of Web Service APIs

SOAP
XML only · Released 1998 · Designed by Microsoft · Slow to parse, complex, rigid · Usually over HTTP or SMTP. Predecessor to REST.
REST ⭐
JSON, XML, YAML + others · Released 2000 · Most widely used — over 80% of all API types · Flexible, scalable, simple, reliable · Works on HTTP.
XML-RPC
XML only · Released 1998 · Predecessor to SOAP · Simple but less flexible · Later evolved into SOAP.
JSON-RPC
JSON only · Released 2005 · Very simple protocol · Similar to XML-RPC but uses JSON instead of XML.
🎯 REST = MOST WIDELY USED — EXAM KEY
REST accounts for over 80% of all web service API types used.
SOAP was first but is slow, complex, and rigid. REST replaced it with simpler HTTP-based implementation.
RPC types (XML-RPC, JSON-RPC) are similar to REST but differ in formatting and flexibility.
14.4REST▾

14.4.2 REST and RESTful API — Three Requirements

REST (Representational State Transfer) = architectural style for designing web service applications that works on top of the HTTP protocol.

An API is RESTful if it meets all three constraints:

ConstraintMeaning
Client-ServerClient handles front end; server handles back end. Each can be replaced independently of the other.
StatelessNo client data stored on the server between requests. Session state is stored on the client.
CacheableClients can cache server responses to improve performance.

14.4.3 HTTP Methods → CRUD Operations

RESTful APIs use HTTP methods that map directly to CRUD operations:

POSTCreate
GETRead
PUT / PATCHUpdate
DELETEDelete

14.4.4 URI, URN, and URL

URI (Uniform Resource Identifier) = string of characters identifying a specific network resource. Has two specializations:

  • URN (Uniform Resource Name) — identifies only the namespace/name of the resource, without specifying protocol or location
  • URL (Uniform Resource Locator) — defines the full network location including protocol (HTTP, HTTPS, FTP, SFTP, SSH)
🔗 Parts of a URI
https://www.example.com/author/book.html#page155
Protocol
https:// — scheme (HTTPS, HTTP, FTP, SFTP, SSH, mailto, etc.)
Hostname
www.example.com — the server's domain name
Path/Filename
/author/book.html — path to the specific resource
Fragment
#page155 — specific section within the resource

14.4.5 Anatomy of a RESTful Request

A RESTful request to a resource's URI gets a response — typically a JSON payload.

PartDescriptionExample
API ServerURL of the server answering REST requestswww.mapquestapi.com
ResourcesWhich specific API is being requested/directions/v2/route
FormatRequested data format (usually JSON)json
KeyAuthorization token (if required)key=YOUR_KEY
ParametersSpecific info for the requestfrom=San+Jose,Ca&to=Monterey,Ca

Why API providers require keys:

  • Authenticate the source (verify authorization)
  • Limit the number of users and requests per user
  • Track and capture data being requested
  • Gather information about API users

14.4.6 RESTful API Tools

14.5Configuration Management Tools▾

14.5.2 Traditional Configuration — The Problem

  • CLI on each device, device by device — time-consuming and error-prone
  • Not scalable — impossible for thousands of devices
  • SNMP limitation: Works for monitoring but NOT configuration — security concerns, difficult implementation; cannot serve as an automation tool for today's networks
  • APIs can automate deployment and management — administrators use tools to hook into network APIs for routine provisioning tasks

14.5.4 Automation vs Orchestration

💡
Automation = a tool automatically performs a specific task on a system. Example: configuring an interface, deploying a VLAN, applying an ACL.

Orchestration = the process of arranging and coordinating multiple automated tasks. Defines the order, dependencies, and workflow — what must complete before another task can begin. Orchestration is the overall workflow.

What configuration management tools automate:

  • Software and version control across all devices
  • Device attributes (names, addressing, security settings)
  • Protocol configurations
  • ACL configurations

14.5.5 Ansible · Chef · Puppet · SaltStack

Ansible Agentless · Push · Playbook
Language: Python + YAML · Agent: Agentless (push-based) · Controller: Any computer can be controller (no dedicated master) · Config file: Playbook
The master connects to devices and pushes/executes configuration. No agent software needed on managed devices.
Chef Agent-based · Pull · Cookbook
Language: Ruby · Agent: Agent-based (pull-based) · Controller: Chef Master · Config file: Cookbook
Agent on managed device periodically connects to Chef Master to pull its configuration.
Puppet Both · Manifest

SaltStack Both · Pillar

🎯 AGENT PUSH vs PULL — EXAM KEY
Agent-based (Pull): Agent on managed device periodically connects to master → pulls configuration
Agentless (Push): Master connects to device → pushes and executes configuration directly

Only Ansible is agentless among the four tools.
Because Ansible is agentless → any computer can be the controller (no dedicated master needed).
Ansible + SaltStack = Python (easier). Chef + Puppet = Ruby (harder).
14.6IBN and Cisco DNA Center▾

14.6.2 Intent-Based Networking (IBN)

IBN = the emerging industry model for next-generation networking. Builds on SDN, transforming from hardware-centric and manual to software-centric and fully automated.

Business objectives are expressed as intent. IBN uses analytics, machine learning, and automation to continuously align the network as business needs change.

Three Essential IBN Functions (Cisco)

1. Translation
Enables the network administrator to express the expected networking behavior that will best support the business intent. Converts human business goals into network specifications.
2. Activation
Captured intent is interpreted into policies and then installed into the physical and virtual network infrastructure using network-wide automation.
3. Assurance
Continuously checks that the expressed intent is honored by the network at any point in time. Maintains a continuous validation-and-verification loop.

14.6.3 Network as Fabric — Overlay and Underlay

LayerDescriptionFunction
OverlayLogical topology above physical hardware. The "fabric" administrators program through policies.Limits devices admin must program · Provides services not controlled by physical devices · Where IPsec and CAPWAP encapsulation occur · IBN administrators specify policy here
UnderlayPhysical topology — all hardware required to meet business objectives.Reveals all physical devices and connections · End points access network through Layer 2 devices · Responsible for simple forwarding tasks

14.6.4 Cisco DNA — Solutions

Cisco implements IBN using Cisco DNA (Digital Network Architecture). Business intent is deployed into the network fabric. Cisco DNA continuously gathers data from devices and applications, analyzes it, and ensures network performance aligns with business intent.

SolutionWhat it Does
SD-AccessFirst intent-based enterprise solution using Cisco DNA. Single fabric across LAN and WLAN. Segments user/device/application traffic. Automates user-access policies. Enables network access in minutes for any user or device.
SD-WANSecure cloud-delivered architecture for centrally managing WAN connections. Simplifies delivery of secure, flexible WAN services. Better application experiences; cost savings through transport independence.
DNA AssuranceAdvanced analytics and machine learning for performance monitoring and issue resolution. Real-time notifications. Predicts problems before they occur. Single dashboard with drill-down insights.
DNA SecurityNetwork as a sensor for real-time analysis. Granular control to enforce policy and contain threats — including encrypted traffic. 360-degree visibility; lower security complexity.

14.6.5 Cisco DNA Center — Five Areas

Cisco DNA Center = foundational controller and analytics platform at the heart of Cisco DNA. A "single-pane-of-glass" — one interface focusing on Assurance, Analytics, and Automation.

🎨 Design
Model the entire network — sites, buildings, devices, links (physical and virtual); campus, branch, WAN, and cloud
📋 Policy
Use policies to automate and simplify network management; reduce cost and risk; speed rollout of new and enhanced services
⚙️ Provision
Provide new services to users with ease, speed, and security across the enterprise network regardless of size and complexity
📊 Assurance
Proactive monitoring and insights from network, devices, and applications; predicts problems; validates business intent and user experience
🔌 Platform
APIs to integrate with preferred IT systems; create end-to-end solutions; add support for multi-vendor devices
🎯Common Exam Traps — Module 14▾
❌
Trap 1: Automation ≠ Orchestration. Automation performs the task; orchestration manages the workflow.
Automation = tool automatically performs a specific task (configure interface, deploy VLAN). Orchestration = process of arranging and coordinating multiple automated activities — the order, dependencies, and overall workflow. Without orchestration, automated tasks might run in the wrong order.
❌
Trap 2: JSON uses { } for objects and [ ] for arrays. Keys MUST be in double quotation marks.
This syntax is directly tested. Objects = curly braces. Arrays = square brackets. Keys MUST be quoted with double quotes (single quotes are not valid JSON). Values can be string, number, array, Boolean, null, or another object. Whitespace is not significant in JSON.
❌
Trap 3: YAML uses indentation and hyphens — NO brackets, NO commas, NO quotation marks on keys.
YAML is a superset of JSON (all valid JSON is valid YAML). Structure is defined by indentation. A hyphen "-" separates each list element. Keys have no quotation marks. YAML is the most minimalist and human-readable of the three formats.
❌
Trap 4: REST = most widely used web service API — over 80% of all API types.
SOAP was first (1998) but is slow, complex, and rigid. REST (2000) replaced it with simpler HTTP-based implementation. REST accounts for over 80% of all web service APIs. XML-RPC (1998) evolved into SOAP. JSON-RPC (2005) is similar but uses JSON.
❌
Trap 5: REST requirements: Client-Server + Stateless + Cacheable. All three required to be RESTful.
Stateless means no client data is stored on the server between requests — session state stays on the client. Cacheable means clients can store server responses. Client-Server means each side can be replaced independently. Missing any one of these = not RESTful.
❌
Trap 6: HTTP methods → CRUD: POST=Create, GET=Read, PUT/PATCH=Update, DELETE=Delete.
This exact mapping is tested directly. GET retrieves (reads) existing data. POST creates new resources. PUT/PATCH modifies existing resources. DELETE removes resources. Remember: GET = Read (like reading a web page).
⚠️
Trap 7: Only Ansible is agentless (push). Chef, Puppet, SaltStack support agent-based (pull).
Agentless (push) = master connects to device and executes configuration directly — no agent needed on managed device. Agent-based (pull) = agent on device periodically checks master for configuration updates. Because Ansible is agentless, ANY computer can be the controller — no dedicated master required.
⚠️
Trap 8: Know the four config tool file names: Playbook (Ansible), Cookbook (Chef), Manifest (Puppet), Pillar (SaltStack).
These appear in matching questions on the exam. Playbook → Ansible. Cookbook → Chef. Manifest → Puppet. Pillar → SaltStack. These names are unique and don't overlap.
⚠️
Trap 9: Ansible and SaltStack use Python. Chef and Puppet use Ruby.
Python is generally considered easier to learn. Ruby is cross-platform but typically harder. This appears in language-matching questions. Ansible = Python + YAML (both languages). SaltStack = Python. Chef = Ruby. Puppet = Ruby.
⚠️
Trap 10: IBN three functions — Translation, Activation, Assurance.
Translation: express business intent as network behavior. Activation: convert to policies and deploy network-wide via automation. Assurance: continuously verify intent is honored. These are Cisco's three essential IBN functions. IBN builds on SDN, making networks software-centric and fully automated.
⚠️
Trap 11: Overlay = logical topology (policies, encapsulation). Underlay = physical topology (hardware).
The overlay is what IBN administrators program through policies. IPsec and CAPWAP encapsulation occur in the overlay. The underlay is the actual physical infrastructure. Simple forwarding occurs in the underlay. End points connect to the network through Layer 2 devices in the underlay.
⚠️
Trap 12: Cisco DNA Center = "single-pane-of-glass" focusing on Assurance, Analytics, and Automation.
Five DNA Center areas: Design, Policy, Provision, Assurance, Platform. DNA Center is the foundational controller for Cisco DNA. It is hardware and software combined. SD-Access is the first intent-based enterprise solution using Cisco DNA, not DNA Center itself.
⚠️
Trap 13: SNMP works for monitoring but NOT configuration automation.
SNMP has security concerns and is difficult to implement for configuration. It cannot serve as an automation tool for today's networks. Configuration management tools (Ansible, Chef, Puppet, SaltStack) use RESTful APIs to automate tasks — SNMP does not.
⚠️
Trap 14: API types — Open/Public (free key), Internal/Private (org only), Partner (license required).
Public APIs may be free but often require a free API key to control volume and track usage. Internal APIs are never available outside the organization. Partner APIs require a license or formal business agreement — the travel service using an airline API is a classic partner API example.
⚠️
Trap 15: URI ⊃ URN (namespace only) and URL (full location with protocol).
URI is the umbrella term. URL is the most common URI — it includes protocol, hostname, path, and fragment. URN identifies by name without specifying where to find it or what protocol to use. In practice, URL is what you use in a web browser.
