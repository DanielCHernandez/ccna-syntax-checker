12.1Network Documentation▾

12.1.1 Documentation Overview

Three types of required network documentation:

  1. Physical and logical network topology diagrams
  2. Network device documentation — accurate, up-to-date records of hardware and software
  3. Network performance baseline documentation
💡
All documentation stored in one central location (hard copy or protected server). Backup copy maintained at a separate location. Without good documentation, troubleshooting is guesswork.

12.1.2 Physical vs Logical Topology Diagrams

Topology TypeContains
Physical TopologyDevice name · Device location (address, room, rack) · Interface and ports used · Cable type
Logical IPv4 TopologyDevice identifiers · IP addresses and prefix lengths · Interface identifiers · Routing protocols/static routes · Layer 2 info: VLANs, trunks, EtherChannels
Logical IPv6 TopologySame as logical IPv4 but with IPv6 addressing — may be kept separate for clarity

12.1.3 Network Device Documentation

Device TypeFields to Document
RouterInterface · IPv4 address · IPv6 address · MAC address · Routing protocol
SwitchPort · Access/Trunk · VLAN · EtherChannel · Native VLAN · Enabled/disabled
End SystemDevice name · OS · Services · MAC address · IPv4/IPv6 addresses · Default gateway · DNS server

12.1.4–12.1.7 Establishing a Network Baseline

A baseline establishes normal ("average day") network performance. Used to detect deviations that indicate problems.

Baseline must answer:

  • How does the network perform during a normal or average day?
  • Where are the most errors occurring?
  • What part of the network is most heavily / least used?
  • Which devices should be monitored and what alert thresholds set?
  • Can the network meet identified policies?

Three Steps to Establish a Baseline

  1. Determine what data to collect — start simple: interface utilization and CPU utilization. Too many variables = overwhelming data; fine-tune over time.
  2. Identify devices and ports of interest — ports connecting to other network devices, servers, key users, critical resources. Use logical topology to identify candidates. Keep list concise to minimize management load.
  3. Determine baseline duration — minimum 7 days (captures daily trends); typically 2–4 weeks; maximum 6 weeks unless long-term trends needed. Do NOT measure during unique traffic periods (holidays, events).
🎯 BASELINE DURATION RULES — EXAM KEY
Minimum: 7 days — captures daily AND weekly patterns (e.g., weekend backup surge)
Typical: 2–4 weeks adequate for most networks
Maximum: 6 weeks unless measuring specific long-term trends
Monthly trends reveal recurring patterns that 7-day baselines miss. Annual analysis or rotating baseline per section recommended.

12.2Troubleshooting Process▾

12.2.2 Seven-Step Troubleshooting Process

  1. Define the Problem — Verify the problem exists; determine symptoms from user reports, console messages, NMS alerts. Localize scope: single device? Subnet? Entire network? Use trouble ticketing software to track progress.
  2. Gather Information — Identify target devices; obtain access; collect and document symptoms using IOS commands, logs, packet captures. If issue is outside the org, contact external admin first.
  3. Analyze Information — Interpret gathered data using network docs, baselines, knowledge base, internet research, and consulting other technicians. Identify possible causes.
  4. Eliminate Possible Causes — Progressively eliminate causes to identify the most probable one. Troubleshooting experience is critical here for quickly ruling out false leads.
  5. Propose Hypothesis — Formulate a solution based on the most probable cause. Experience is valuable for proposing an effective plan.
  6. Test Hypothesis — Assess impact and urgency first. Create a rollback plan before changing anything. Implement and verify. If solution fails: document it, remove changes, return to Step 2. Consider a workaround if downtime is unacceptable.
  7. Solve the Problem — Inform users and all IT staff involved. Document cause and fix for knowledge base — helps prevent and solve similar problems in future.
⚠️
Steps are not always executed in exact order. Experienced admins can jump between steps. However, all steps must be documented throughout the process.

12.2.3 Questioning End Users

When interviewing users: speak at their technical level, listen carefully, take notes, be considerate — users under stress want rapid resolution.

Question TypePurposeExamples
Open questionsGather detailed information; determine scope and timing"What exactly is the problem?" · "When did you first notice it?" · "What has changed recently?"
Closed questionsConfirm specific facts; yes/no answers"Can you reproduce the problem?" · "Were error messages displayed?" · "Does it affect only you?"
💡
After interviewing, repeat your understanding of the problem back to the user to confirm you both agree on what is being reported. This prevents working on the wrong problem.

12.2.5 Troubleshooting with Layered Models

OSI and TCP/IP models allow you to isolate the troubleshooting scope to specific layers:

  • Layer 1 (Physical): cables, power, hardware NICs, attenuation, noise
  • Layer 2 (Data Link): encapsulation, STP loops, frame errors, ARP/MAC issues
  • Layer 3 (Network): IP addressing, routing table, OSPF/EIGRP adjacency
  • Layer 4 (Transport): ACL misconfigurations, NAT issues
  • Layer 7 (Application): service failures, application-specific issues
💡
Routers and multilayer switches appear at Layer 4 in troubleshooting diagrams because ACLs can filter traffic using Layer 4 (TCP/UDP port) information — even though routing decisions occur at Layer 3.

12.2.6 Seven Structured Troubleshooting Methods

⬆️ Bottom-Up
Start at Layer 1 (physical), work up through OSI layers. Best when physical problem suspected. Most networking problems reside at lower layers. Drawback: must check every device and interface systematically.
⬇️ Top-Down
Start at Layer 7 (application), work down. Best for software or application problems; simpler issues. Drawback: must check every application until cause found.
✂️ Divide and Conquer
Start at a middle layer (often Layer 3). Test in both directions based on results. If ping works → problem is Layer 4+. If ping fails → Layer 3 or below. Best for experienced admins with new/complex problems.
🗺️ Follow the Path
Trace the actual traffic path from source to destination. Eliminates irrelevant links and devices from the troubleshooting scope. Usually used alongside another method.
🔄 Substitution (Swap)
Physically replace suspected device with a known-working unit. If fixed → bad device. Quick for single points of failure. Drawback: doesn't work well when multiple devices may be involved.
🔍 Comparison (Spot-the-Difference)
Compare configs, software versions, and hardware between working and non-working states. Find significant differences. Weakness: may find a fix without revealing the root cause.
🎯 Educated Guess
"Shoot-from-the-hip" — educated guess based on experience and symptoms. Effective for seasoned technicians. Less reliable for newer admins — may become random troubleshooting.

12.2.7 Selecting the Right Method

SituationRecommended Method
Hardware / physical problem suspectedBottom-Up
Software / application problem suspectedTop-Down
Experienced admin; new or complex problemDivide and Conquer
Less-experienced admin; new problemBottom-Up
Critical single point of failure; speed neededSubstitution
Working vs non-working comparison availableComparison
12.3Troubleshooting Tools▾

12.3.1 Software Troubleshooting Tools

NMS Tools
Network Management System — device-level monitoring, config, fault management. Graphically displays physical network; monitors remote devices automatically. Example: WhatsUp Gold.
Knowledge Bases
Cisco Tools & Resources (cisco.com Support menu), internet search engines. Provides access to vast pool of experience-based troubleshooting information.
Baselining Tools
Automate network documentation and baselining. Draw topology diagrams, track software/hardware versions, measure baseline bandwidth. Search: "Network Performance Monitoring Tools."

12.3.2 Protocol Analyzers — Wireshark

  • Captures and decodes frames at each OSI layer
  • Displays physical layer bits, data link info, protocol headers, frame descriptions
  • Filters traffic by device, protocol, port, or other criteria
  • Helps troubleshoot network performance and application-level issues
  • Requires strong TCP/IP knowledge to interpret output effectively

12.3.3 Hardware Troubleshooting Tools

ToolPurpose
Digital Multimeter (DMM)Measures voltage, current, resistance. Check power supply levels and that devices receive power. Example: Fluke 179.
Cable TesterDetects broken wires, crossed-over wiring, shorted connections, improperly paired connections. Example: Fluke LinkRunner AT.
TDR (Time-Domain Reflectometer)Pinpoints distance to a cable break — sends signal, measures time to receive reflection. Packaged with cable analyzers.
OTDR (Optical TDR)Same as TDR but for fiber-optic cables.
Cable AnalyzerTests and certifies copper and fiber for different standards. Measures NEXT (near-end crosstalk) and RL (return loss). Example: Fluke DTX Cable Analyzer.
Portable Network AnalyzerPlugs into any switch port; shows port/VLAN config, average/peak utilization, top talkers, interface details. Example: Fluke OptiView.
Cisco Prime NAMHardware + software for performance analysis in switching/routing environments. Browser-based interface; captures and decodes packets; generates traffic reports; tracks application response times.

12.3.4 Syslog as a Troubleshooting Tool

Cisco devices can log configuration changes, ACL violations, interface status, and other events to multiple destinations:

Console
Default; viewable during live terminal session. Not stored — lost when session ends.
Terminal Lines
Active Telnet/SSH sessions only. Not stored on device.
Buffered (RAM)
Stored in RAM during operation; cleared on reboot. Useful for recent events.
SNMP Traps
Forwarded to NMS when thresholds exceeded. Requires SNMP configuration.
Syslog Server ⭐
Most useful — long-term storage, central location for all router messages, viewable without device access, not lost on reboot.
Configure syslog server and limit message level 
! Send to syslog server:
R1(config)# logging host 192.168.1.100

! Limit to levels 0-5 (Notifications and above = more critical):
R1(config)# logging trap notifications

! Enable logging:
R1(config)# logging on

! Result: levels 0 (Emergency) through 5 (Notification) sent to server
! Levels 6 (Informational) and 7 (Debugging) are NOT sent
💡
logging trap level: only messages equal to or numerically lower than specified level are logged. Lower number = more critical. notifications = level 5, so levels 0–5 are sent.
12.4Symptoms and Causes by OSI Layer▾

12.4.1 Physical Layer (Layer 1)

🔴 Layer 1 — Physical
Symptoms:
  • Performance lower than baseline (requires baseline for comparison)
  • Loss of connectivity (cable fault — verify with ping)
  • Network bottlenecks or congestion
  • High CPU utilization
  • Console error messages
Common Causes:
  • Power failures — most fundamental; check fans and power supply
  • Hardware faults (NIC) — late collisions, short frames, jabber (device transmitting random data continuously); caused by faulty NIC, corrupt driver, bad cabling, grounding problems
  • Cabling faults — damaged cables, wrong cable type, bad RJ-45 crimp, partially disconnected
  • Attenuation — cable exceeds design length; poor connections; receiving device cannot distinguish bits
  • Noise/EMI — FM radio, police radio, electric motors, crosstalk, grounding problems
  • Interface config errors — wrong clock rate/source, interface not enabled (no shutdown)
  • Exceeding design limits — component operating beyond capacity; increasing interface error counters
  • CPU overload — input queue drops, SNMP timeouts, slow ping, DHCP/Telnet failures; on switches: STP reconvergence, EtherChannel bounce, UDLD flapping; on routers: route flapping, HSRP flapping

12.4.2 Data Link Layer (Layer 2)

🔵 Layer 2 — Data Link
Symptoms:
  • No functionality or connectivity at Layer 3 or above (all L2 frames blocked)
  • Network operating below baseline — frames taking suboptimal path, or being dropped (visible via error counters)
  • Excessive broadcasts — STP loops, route flapping, poorly programmed apps, large L2 broadcast domain
  • Console messages — "line protocol down," encapsulation errors, keepalive failures
Common Causes:
  • Encapsulation errors — mismatch in encapsulation type between WAN link ends
  • Address mapping errors — stale ARP cache, failed ARP reply, misconfiguration, or ARP spoofing attack
  • Framing errors — frame not ending on 8-bit byte boundary; caused by noisy serial line, bad cable, NIC fault, duplex mismatch, incorrect CSU line clock
  • STP failures or loops — no ports blocked in redundant topology → infinite flooding; port flapping causes repetitive topology changes; well-configured networks have rare topology changes

12.4.3 Network Layer (Layer 3)

🟢 Layer 3 — Network
Symptoms: Network failure (non-functional for all users) · Suboptimal performance (subset of users/apps/destinations)

Common Causes:
  • General network issues — recent topology changes (link down), new routes added/removed, someone working on infrastructure
  • Connectivity issues — power outage, overheating, Layer 1 cabling, bad ports, ISP problems
  • Routing table problems — missing routes or unexpected routes; use debug to view routing updates and table maintenance
  • Neighbor issues — OSPF/EIGRP neighbor adjacency not formed; check neighbor table
  • Topology database issues — missing or unexpected entries in OSPF LSDB or EIGRP topology table
Improperly configured static routes can create routing loops making parts of the network unreachable. No single template for L3 troubleshooting — use methodical show commands.

12.4.4 Transport Layer — ACL Issues

🟠 Layer 4 — Transport (ACLs)
Common ACL Misconfiguration Areas:
  • Wrong interface or direction — ACL applied to wrong interface or wrong direction (in vs out)
  • Order of entries — must be specific-to-general; more specific entries BEFORE broader ones; first match wins
  • Implicit deny any — at end of every ACL; blocks all traffic not explicitly permitted
  • Wildcard mask errors — complex wildcards are error-prone; verify calculations
  • Protocol selection — specifying both TCP and UDP when only one applies opens unnecessary holes
  • Source and destination ports — inbound and outbound ACLs must mirror each other for bidirectional traffic
  • established keyword — incorrect use causes unexpected behavior in return traffic filtering
  • Uncommon protocols — VPN and encryption protocols often blocked or misconfigured
🎯 ACL + NAT PROCESSING ORDER — EXAM KEY
Inbound traffic: inbound ACL processed FIRST → then outside-to-inside NAT
Outbound traffic: inside-to-outside NAT processed FIRST → then outbound ACL

log keyword: instructs router to log an entry whenever that ACE is matched. Useful for troubleshooting and detecting intrusion attempts.

12.4.5 Transport Layer — NAT Issues

ProtocolNAT Interoperability ProblemFix
BOOTP/DHCPDHCP-Request uses source 0.0.0.0 — NAT requires valid source/dest IP addressesip helper-address
DNSNAT changes IP addresses but cannot update addressing info in DNS payloadip helper-address
SNMPSNMP agents/managers on opposite sides of NAT may not communicateip helper-address
IPsec/GRE (VPN)Encryption/tunneling protocols use specific ports/protocols that NAT cannot process; VPN traffic cannot traverse standard NATNAT-T or other VPN workarounds

12.4.6 Application Layer (Layer 7)

🟣 Layer 7 — Application
Common Application Protocols: SSH/Telnet · HTTP · FTP · TFTP · SMTP · POP · SNMP · DNS · NFS

Key point: Application layer problems can exist even when Layers 1–4 are fully functional. Full network connectivity exists but the application cannot deliver data.

Symptoms: Users report application is slow, sluggish, or not working at all — even though pings succeed and routing is correct.

Approach: Once you verify Layers 1–4 are working (ping succeeds, traceroute completes, routing table correct, no ACL blocks), focus troubleshooting on the application or server itself.
12.5Troubleshooting IP Connectivity — 8 Steps▾

Overview Primary Diagnostic Utilities

UtilityPlatformPurpose
pingIOS + WindowsICMP Echo Request/Reply — tests Layer 3 connectivity; works for IPv4 and IPv6
tracerouteCisco IOSTraces hop-by-hop path; shows last router reached when connectivity fails
tracertWindowsWindows equivalent of IOS traceroute
💡
Cisco IOS automatically detects whether an address is IPv4 or IPv6 and uses the appropriate protocol for both ping and traceroute. traceroute is commonly performed when ping fails. If ping succeeds, traceroute is usually not needed.

Step 1 Verify the Physical Layer

1 Verify Physical Layer — show interfaces
Key commands: show interfaces · show processes cpu · show memory
  • Input queue drops — router received more traffic than it could process; if consistently high → CPU bottleneck
  • Output queue drops — congestion on outbound interface; normal during peaks; consistently high → implement QoS
  • Input errors / CRC errors — cabling problems, hardware issues, or duplex mismatch
  • Output errors / late collisions — in full-duplex networks, collisions should NOT occur; late collisions = duplex mismatch
show interfaces — read key counters 
R1# show interfaces GigabitEthernet 0/0/0
GigabitEthernet0/0/0 is up, line protocol is up
  ...
  Input queue: 0/75/0/0 (size/max/drops/flushes); Total output drops: 0
  0 runts, 0 giants, 0 throttles
  0 input errors, 0 CRC, 0 frame, 0 overrun, 0 ignored
  0 output errors, 0 collisions, 1 interface resets

! drops > 0 consistently = CPU bottleneck
! CRC errors = cabling or duplex mismatch
! late collisions in full-duplex = duplex mismatch

Step 2 Check for Duplex Mismatches

2 Check Duplex — show interfaces / duplex auto
  • Autonegotiation recommended (IEEE 802.3ab mandates autoneg for Gigabit Ethernet)
  • If autoneg fails → manually set speed and duplex on both ends
  • Point-to-point Ethernet should always run full-duplex
  • In full-duplex, collisions should NEVER occur — collisions = duplex mismatch
  • CDP detects and logs mismatches: %CDP-4-DUPLEX_MISMATCH: duplex mismatch discovered on...
Diagnose and fix duplex mismatch 
! Check duplex on S1 port:
S1# show interface fa 0/20
FastEthernet0/20 is up, line protocol is up (connected)
  Full-duplex, Auto-speed, media type is 10/100BaseTX

! Check other side on S2:
S2# show interface fa 0/20
FastEthernet0/20 is up, line protocol is up (connected)
  Half-duplex, Auto-speed    ← MISMATCH!

! Fix: set both sides to autonegotiate (or both to full-duplex):
S2(config)# interface fa 0/20
S2(config-if)# duplex auto

Step 3 Verify Addressing on the Local Network

3 Verify L2/L3 Address Mappings — ARP, MAC table, VLAN
CommandPlatformPurpose
arp -aWindowsDisplay IPv4 ARP cache (IP → MAC mappings)
arp -dWindowsClear ARP cache to force re-resolution
netsh interface ipv6 show neighborWindowsDisplay IPv6 neighbor table
ip neigh showLinux/macOSDisplay IPv6 neighbor table
show arpCisco IOSRouter ARP table
show ipv6 neighborsCisco IOSRouter IPv6 neighbor table
show mac address-tableCisco IOSSwitch MAC table — MAC address, VLAN, port
⚠️
VLAN mismatch: If a host's default gateway is on a different VLAN than the host, communication beyond the local network fails — even if IP addresses look correct. Use show mac address-table to verify VLAN assignments. Fix: switchport access vlan [id].
Fix VLAN mismatch on switch 
! Verify VLAN assignments:
S1# show mac address-table
Vlan  Mac Address      Type     Ports
1     d48c.b5ce.a0c0   DYNAMIC  Fa0/1   ← R1 is in VLAN 1
10    5475.d08e.9ad8   DYNAMIC  Fa0/13  ← PC1 is in VLAN 10

! R1 and PC1 are in different VLANs — fix:
S1(config)# interface fa0/1
S1(config-if)# switchport mode access
S1(config-if)# switchport access vlan 10

Step 4 Verify Default Gateway

4 Verify Default Gateway — show ip route / ipconfig
  • On router: show ip route | include Gateway|0.0.0.0 — verify gateway of last resort
  • On Windows (IPv4): route print — verify default gateway
  • On Windows (IPv6): ipconfig — verify IPv6 GUA and default gateway
  • On Linux/macOS: ifconfig
IPv6 default gateway troubleshooting — ipv6 unicast-routing 
! PC has link-local but no global IPv6 = router not sending RAs
C:\> ipconfig
  Link-local IPv6 Address: fe80::5075:d0ff:fe8e:9ad8%13
  IPv6 Address: (none)       ← missing global address
  Default Gateway: (none)    ← missing gateway

! Check if R1 is enabled as IPv6 router:
R1# show ipv6 interface GigabitEthernet 0/0/0
  Joined group address(es):
    FF02::1                  ← NOT in FF02::2 = not an IPv6 router!

! Fix: enable IPv6 routing (causes R1 to join FF02::2 and send RAs):
R1(config)# ipv6 unicast-routing

! Verify after fix:
R1# show ipv6 interface GigabitEthernet 0/0/0
  Joined group address(es):
    FF02::1
    FF02::2                  ← now a member = sends RA messages

Step 5 Verify Correct Path

5 Verify Routing Table — show ip route / show ipv6 route
  • show ip route | begin Gateway — full IPv4 routing table starting from gateway of last resort
  • show ipv6 route — full IPv6 routing table
  • Routing table populated by: directly connected · local host routes · static · dynamic (OSPF/EIGRP) · default routes
  • Longest prefix match — router selects route with most matching leftmost bits; if no match → use default route; if no default → packet discarded

Step 6 Verify the Transport Layer

6 Test Transport Layer — Telnet to specific TCP port
  • If ping succeeds but connection fails → Layer 4+ problem (ACL, NAT, or application)
  • telnet [ip] — tests basic TCP transport layer connectivity (port 23)
  • telnet [ip] [port] — tests specific TCP port (e.g., 80 for HTTP, 443 for HTTPS)
  • If "Open" appears → transport layer accepted connection on that port
  • ⚠️ Use SSH for actual device management; Telnet is unencrypted — use for testing only
Test specific TCP port with Telnet 
! Test Layer 3 first:
R1# ping 2001:db8:acad:2::2
Success rate is 100 percent (5/5)   ← L3 and below working

! Test transport layer on port 23 (Telnet):
R1# telnet 2001:db8:acad:2::2
Trying ... Open                     ← transport layer working

! Test port 80 (HTTP):
R1# telnet 2001:db8:acad:2::2 80
Trying ... Open
HTTP/1.1 400 Bad Request            ← port 80 open, but refusing request
                                    ← problem is application layer, not transport

Step 7 Verify ACLs

7 Verify ACLs — show ip access-lists / show ip interface
  • show ip access-lists — displays all IPv4 ACLs; match counters in parentheses show how many packets hit each ACE
  • show ipv6 access-list — displays all IPv6 ACLs
  • show ip interface [intf] | include access list — verifies which interfaces have ACLs applied and in which direction
  • Common error: ACL applied to wrong interface or wrong direction (in vs out)
Diagnose and fix wrongly-placed ACL 
! Check ACL contents and match counters:
R3# show ip access-lists
Extended IP access list 100
  10 deny ip any (108 matches)
  20 permit ip any any (28 matches)

! Check which interface has the ACL applied:
R3# show ip interface serial 0/1/1 | include access list
  Inbound access list is not set    ← ACL NOT where intended!

R3# show ip interface gig 0/0/0 | include access list
  Inbound access list is 100        ← ACL applied to wrong interface!

! Fix: remove from wrong interface, apply to correct one:
R3(config)# interface GigabitEthernet 0/0/0
R3(config-if)# no ip access-group 100 in
R3(config-if)# exit
R3(config)# interface serial 0/1/1
R3(config-if)# ip access-group 100 in

Step 8 Verify DNS

8 Verify DNS — show running-config / ip host / nslookup
  • show running-config — view DNS server configuration on router/switch
  • ip host [name] [ip] — manually add hostname-to-IP mapping on router/switch (no DNS server needed)
  • nslookup [hostname] — Windows command to test DNS resolution from a PC
  • DNS problems: wrong DNS server IP, unreachable DNS server, missing DNS record
Manual hostname mapping and DNS test 
! Add manual name-to-IP mapping (no DNS server required):
R1(config)# ip host ipv4-server

! Test using hostname instead of IP:
R1# ping ipv4-server
Sending 5, 100-byte ICMP Echos to, timeout is 2 seconds:
Success rate is 100 percent (5/5)

! On Windows — test DNS resolution:
C:\> nslookup server.example.com

🎯Common Exam Traps — Module 12▾
❌
Trap 1: Baseline minimum = 7 days; typical = 2–4 weeks; max = 6 weeks.
A 7-day minimum captures daily AND weekly patterns (e.g., a backup job that runs every Saturday night is invisible in a 5-day baseline). Never baseline during holidays or unique traffic events — gives inaccurate "normal" picture.
❌
Trap 2: Seven-step process — know each step and its name.
Define → Gather → Analyze → Eliminate → Propose → Test → Solve. Step 6 (Test) requires a rollback plan before any changes. If solution fails, remove changes and return to Step 2 (Gather). Steps can be executed non-linearly by experienced admins.
❌
Trap 3: Bottom-up = hardware/physical. Top-down = software/application. Divide-and-conquer = experienced admin, new problem.
Less-experienced admins with new problems should use bottom-up. The substitution method (swap) is best for critical single points of failure where speed matters more than root cause analysis.
❌
Trap 4: TDR pinpoints distance to cable break. OTDR does same for fiber-optic.
TDRs send signals and measure reflection time, converting it to distance. Packaged with cable analyzers/testers. DMMs measure voltage/current/resistance — used for power checks, not cable breaks. Wireshark is a protocol analyzer, not a cable tool.
❌
Trap 5: WhatsUp Gold = NMS tool (not a protocol analyzer). Wireshark = protocol analyzer.
NMS tools monitor and graphically display network devices. Protocol analyzers capture and decode individual frames/packets. Cisco Prime NAM = hardware/software for performance analysis in Cisco switching/routing environments.
❌
Trap 6: duplex mismatch → collisions and late collisions in full-duplex networks.
Full-duplex links should never have collisions. Seeing collision counters increasing = duplex mismatch. CDP logs this automatically: %CDP-4-DUPLEX_MISMATCH. Fix: duplex auto on both sides (or duplex full on both). Both sides must match.
⚠️
Trap 7: Syslog logging trap — only levels equal to or numerically LOWER than specified are sent.
logging trap notifications (level 5) sends levels 0–5 to the syslog server. Levels 6 (Informational) and 7 (Debugging) are NOT sent. Lower number = more critical = more likely to be included at any trap level setting.
⚠️
Trap 8: Jabber = device transmitting random meaningless data continuously.
Caused by faulty NIC, corrupt NIC driver, bad cabling, or grounding problems. A Layer 1 physical symptom. Distinguished from normal high traffic — jabber is random and continuous regardless of network load.
⚠️
Trap 9: ACL + NAT processing order — inbound: ACL first, then NAT. Outbound: NAT first, then ACL.
Getting this order wrong causes misconfigured ACLs that appear to work but block or allow the wrong traffic. Most exam questions about ACL + NAT interactions test this processing order.
⚠️
Trap 10: ACL order = specific-to-general. First match wins. Implicit deny any at end.
A specific permit will never be reached if a broader deny appears before it. Always place more specific ACEs above broader ones. The implicit deny any at the bottom blocks everything not explicitly permitted — a common source of "mysterious" connectivity failures.
⚠️
Trap 11: NAT breaks DHCP (source 0.0.0.0), DNS (payload addressing), SNMP, and IPsec/GRE.
Fix for DHCP/DNS/SNMP: ip helper-address. Fix for IPsec/GRE: NAT Traversal (NAT-T) or place VPN endpoint outside NAT. Standard NAT cannot process VPN tunnel protocols because they encrypt the transport/network layer headers that NAT needs to modify.
⚠️
Trap 12: VLAN mismatch — same IP subnet but different VLANs = cannot communicate.
VLAN isolation is Layer 2 — even if two hosts have IPs in the same subnet, different VLANs prevent communication without a router. Symptom: ARP table missing default gateway entry. Diagnosis: show mac address-table. Fix: switchport access vlan [correct-vlan].
⚠️
Trap 13: IPv6 SLAAC issue — PC has link-local but no GUA = router not sending RAs.
A PC always auto-generates a link-local address. A global unicast address via SLAAC requires the router to send RA messages. If the router is not enabled with ipv6 unicast-routing, it does not send RAs, does not join FF02::2, and hosts cannot get IPv6 addresses or default gateways via SLAAC.
⚠️
Trap 14: show ip access-lists shows match counters in parentheses.
Each ACE shows how many packets matched it: 10 deny ip any any (108 matches). This is essential for identifying which ACE is blocking traffic. Zero matches on a deny = that rule hasn't been hit yet. show ip interface [intf] | include access list reveals which interface/direction has the ACL applied.
⚠️
Trap 15: Application layer problems can exist with full Layers 1–4 connectivity.
Ping works, routing works, no ACL blocks → but users still can't access the application. This points to Layer 7 — the application server, service configuration, or app-specific issues. Don't keep troubleshooting the network if all layers below 7 are verified functional.
