9.1Network Transmission Quality▾

9.1.2 Prioritizing Traffic — When QoS Activates

🚨
A device implements QoS only when it is experiencing congestion. If the link is not congested, QoS mechanisms are dormant — all traffic flows freely regardless of classification.

Without QoS, all packets are processed in arrival order. During congestion, voice and video packets are dropped as often as email — no differentiation.

Why congestion occurs:

  • Multiple high-speed input lines funnel into a single slower output interface
  • Large data packets block smaller, time-sensitive packets in a single queue
  • Traffic bursts (e.g., large FTP downloads) consume all available bandwidth
💡
QoS solution: classify traffic into multiple priority queues so time-sensitive traffic (voice, video) is transmitted before bulk data during congestion.

9.1.3 Bandwidth, Congestion, Delay, and Jitter

Jitter = variation in the delay between received packets. Packets sent at even intervals arrive with varying gaps due to congestion, improper queuing, or config errors. Both delay and jitter must be controlled for real-time traffic.

⏱ Sources of Delay

Propagation

De-jitter
Fixed
Time to buffer a flow of packets and send them out in evenly spaced intervals

9.1.4 Packet Loss — VoIP Playout Buffer

VoIP uses RTP (Real-Time Protocol) over UDP. When packets arrive with jitter, the playout delay buffer compensates:

  • Buffers incoming audio packets → plays them out at a steady, even rate
  • If jitter exceeds the buffer range → out-of-range packets are discarded → audible dropouts
  • The DSP (Digital Signal Processor) can interpolate (fill in) for small losses — users don't notice
  • When jitter exceeds what DSP can compensate → audio problems become audible
✅
In a properly designed network, voice packet loss should be near zero. QoS mechanisms guarantee bandwidth and give priority to voice traffic — achieving zero packet loss for voice calls.

9.3Queuing Algorithms▾

9.3.2–9.3.6 Four Queuing Algorithms

Queuing is a congestion management tool — buffers, prioritizes, and reorders packets before transmission. QoS policy activates only during congestion.

📥 FIFO — First In, First Out Default (most interfaces)
  • No priority classes — all packets treated identically
  • Transmitted in exact order of arrival
  • Default on all interfaces except serial at E1 and below (those use WFQ)
  • Fastest queuing method — minimal overhead
  • Effective for large, low-congestion links
  • ❌ Time-sensitive traffic dropped as often as bulk data during congestion
⚖️ WFQ — Weighted Fair Queuing Default ≤E1 serial
  • Automated — no user-defined classes needed
  • Classifies traffic into flows/conversations based on: src/dst IP, MAC, port, protocol, ToS
  • Applies weights — low-bandwidth interactive traffic (Telnet, voice) gets priority
  • Multiple FTP flows share remaining bandwidth proportionally
  • Default on serial interfaces at E1 (2.048 Mbps) and below
  • ❌ Does NOT support tunneling or encryption (modifies header fields WFQ needs)
  • ❌ Less precise than CBWFQ — no user control over class bandwidth allocation
🗂️ CBWFQ — Class-Based WFQ User-defined classes
  • Extends WFQ with user-defined traffic classes
  • Classes defined using: protocols, ACLs, input interfaces
  • Each class gets its own dedicated FIFO queue
  • Each class assigned: guaranteed bandwidth, weight, queue limit (max packets)
  • When queue limit exceeded → tail drop (default) — drops from tail equally for all; no class distinction
  • ✅ Precise bandwidth allocation per class
🚨 LLQ — Low Latency Queuing Voice networks
  • Adds a strict priority queue (PQ) to CBWFQ
  • Strict PQ traffic (voice) is sent first — before all other queues, every time
  • Dramatically reduces jitter for voice conversations
  • Cisco recommends only voice in the strict priority queue
  • Without LLQ: CBWFQ serves all classes by weight — no strict guarantee for voice → jitter
  • ✅ Best algorithm for mixed voice + data networks

9.4QoS Models▾

9.4.2–9.4.5 Three QoS Models

📮 Best Effort

No QoS — all packets treated identically. Most scalable; no special mechanisms needed. No delivery guarantees; no preferential treatment; critical and casual traffic treated identically. Appropriate when QoS is not required.

📡 IntServ — Integrated Services

"Hard QoS" — guarantees bandwidth, delay, and packet loss end-to-end for individual flows (microflows). Uses RSVP (Resource Reservation Protocol) to signal QoS requirements along every device in the path. Each router maintains per-flow state. If reservation fails anywhere → application does not send. Explicit end-to-end admission control. ❌ Resource-intensive; not scalable to internet-scale; flow-based approach breaks down with large numbers of flows.

🌐 DiffServ — Differentiated Services ← Modern Standard

"Soft QoS" — scalable, hop-by-hop QoS. Classifies traffic into aggregates (classes), not individual flows. No per-flow state on routers; no end-to-end signaling. Network devices apply defined QoS policy per class on every hop. Provides "almost guaranteed" QoS while remaining cost-effective and scalable. ❌ No absolute guarantee; requires coordinated mechanisms across all devices.

🎯 MODEL COMPARISON — EXAM KEY
Best Effort: No QoS · most scalable · no guarantees · no config needed
IntServ: Hard QoS · RSVP signaling · per-flow state on every router · guaranteed but not scalable
DiffServ: Soft QoS · hop-by-hop · aggregate classes · scalable · modern standard

Modern networks primarily use DiffServ. IntServ/RSVP sometimes co-deployed for delay/jitter-sensitive traffic.
9.5QoS Implementation Techniques▾

9.5.2 Avoiding Packet Loss

Three approaches to prevent drops for sensitive applications:

  • Increase link capacity — ease or eliminate congestion at bottleneck points
  • Guarantee bandwidth + increase buffer — WFQ, CBWFQ, and LLQ guarantee bandwidth and provide priority forwarding to fragile flows
  • Drop lower-priority traffic early — WRED drops lower-priority packets before congestion peaks, preserving capacity for sensitive traffic

9.5.3 Three Categories of QoS Tools

Classification & Marking
Analyze flows to identify traffic class. Mark packets with QoS value in header. Must classify before any policy can be applied. Tools: ACLs, class maps, NBAR (Layers 4–7).
Congestion Avoidance
Monitor queue depth; selectively drop/delay/remark packets before congestion peaks. Primary tool: WRED — randomly drops lower-priority packets before tail drop occurs.
Congestion Management
Queue and schedule packets when traffic exceeds available resources. Tools: CBWFQ and LLQ. Typically applied on egress.
💡
QoS sequence: Ingress packets → Classify and Mark → Allocate resources (congestion avoidance) → Queue → Shape/Police on egress.
Classification and marking: ingress or egress. Queuing and shaping: typically egress only.

9.5.4 Classification and Marking

Classification = determine which traffic class a packet belongs to. Must happen before QoS policy can be applied.

Marking = add a QoS value to the packet header. Downstream devices read this value and apply matching policy.

⚠️
Mark as close to the source as possible. This establishes the trust boundary — the point where QoS markings are accepted as valid. Marking further downstream means intermediate devices may not classify correctly.

9.5.6–9.5.7 Layer 3 Marking — DSCP

IPv4 Type of Service (ToS) / IPv6 Traffic Class — 8 bits total in the IP header:

  • Original (RFC 791): IP Precedence (IPP) — 3 bits → only 8 values → not enough granularity
  • Current (RFC 2474): DSCP — 6 bits → 64 possible classes
  • Remaining 2 bits = ECN (Explicit Congestion Notification) — ECN-aware routers mark packets instead of dropping them
✅
DSCP is in the IP header — it survives routing across multiple networks. Layer 2 CoS is stripped at each Layer 3 boundary. For end-to-end QoS, DSCP is the correct marking field.

9.5.8 DSCP Values — BE, EF, and AF

Best Effort (BE / DF) DSCP 0
Default for all IP packets. No QoS. Packets dropped first during congestion. No plan implemented.
Expedited Forwarding (EF) DSCP 46
Binary 101110. Low-loss, low-latency, low-jitter forwarding. First 3 bits (101) map to CoS 5 — voice. Cisco recommends EF only for voice traffic.
Assured Forwarding (AF) AFxy
4 classes × 3 drop preferences = 12 AF values.
x = class (1–4; Class 4 = best queue, Class 1 = worst)
y = drop preference (1 = low drop, 2 = medium, 3 = high drop)
Example: AF32 = class 3, medium drop → binary 011 10 0 → DSCP 28
💡
AF drop preference rule: Lower number = less likely to be dropped. AF11 = low drop. AF13 = high drop. When congestion avoidance kicks in, AF packets with higher drop preference are dropped first.

9.5.10 Trust Boundaries

Traffic should be classified and marked as close to the source as technically and administratively feasible — this establishes the trust boundary.

LevelTrust Boundary LocationExamples
Level 1 (Best)Trusted endpoints mark their own trafficIP phones, wireless APs, video gateways — they know their own traffic type
Level 2Access Layer 2 switch marks trafficSwitch re-marks frames from PCs and other untrusted endpoints
Level 3Layer 3 switch or router marks trafficUsed when endpoint trust is not feasible at Layer 2
🚨
PCs are untrusted endpoints. A PC can mark its own packets with any DSCP value — including high-priority values it shouldn't have. The network administrator must re-mark (override) PC-generated markings at the first trusted device (access switch or router).

9.5.11 Congestion Avoidance — WRED

WRED (Weighted Random Early Detection) monitors average queue depth and selectively drops packets before the queue fills completely, triggering TCP's congestion control mechanism:

📊 WRED Queue Depth Zones
Below min threshold
No drops — queue has available capacity; all packets forwarded normally
Min → Max threshold
Small percentage of lower-priority packets randomly dropped — triggers TCP window reduction before full congestion; higher-priority packets protected
Above max threshold
All packets dropped (tail drop) — queue fully saturated
⚠️
WRED does not work for UDP traffic. UDP has no congestion control — randomly dropping UDP packets doesn't cause the sender to reduce its rate (there's no TCP window to shrink). For UDP-based voice/video, use queuing (LLQ) and compression instead.

9.5.12 Traffic Shaping vs Traffic Policing

📤 Traffic Shaping — Egress
  • Applied to outbound (egress) traffic
  • Excess packets queued and scheduled for later transmission
  • Result: smooth, controlled output rate
  • Requires queue + sufficient memory for buffering delayed packets
  • Uses CBWFQ or LLQ to schedule the shape queue
  • Smooths burst traffic — no packets dropped if buffer available
📥 Traffic Policing — Ingress
  • Applied to inbound (ingress) traffic
  • Excess traffic immediately dropped or remarked
  • No queue — no buffering; enforcement is instant
  • Used by SPs to enforce CIR (Customer Information Rate)
  • SP may allow bursting over CIR if network not congested
  • Abrupt — packets exceeding the rate are simply discarded
🎯 SHAPING vs POLICING — EXAM DISTINCTION
Shaping = EGRESS · queues excess packets · smooth output · needs buffer memory
Policing = INGRESS · drops excess immediately · no buffer · used by ISPs for CIR enforcement

Shaping is gentler — it delays excess traffic. Policing is aggressive — it discards excess traffic.

9.5.13 QoS Policy Guidelines

QoS policy must consider the full path from source to destination. One misconfigured device can break the entire QoS policy:

  1. Enable queuing at every device in the path between source and destination
  2. Classify and mark traffic as close to the source as possible — establish the trust boundary early
  3. Shape and police traffic flows as close to their sources as possible
🎯Common Exam Traps — Module 9▾
❌
Trap 1: QoS only activates during congestion.
A router implements QoS mechanisms only when experiencing congestion. No congestion = no QoS action, even if policies are fully configured. A device implements QoS only when it is experiencing some type of congestion.
❌
Trap 2: Voice requirements — ≤150ms latency, ≤30ms jitter, ≤1% loss.
Video is more tolerant: ≤200–400ms latency, ≤50ms jitter, ≤1% loss. Both use UDP — neither retransmits lost packets. Voice = predictable, smooth, 20ms intervals. Video = bursty, variable, 33ms intervals. These numbers are directly tested.
❌
Trap 3: FIFO is default on most interfaces; WFQ is default on serial interfaces at E1 and below.
E1 = 2.048 Mbps. Any serial interface at or below this rate defaults to WFQ, not FIFO. All other interfaces default to FIFO. This is a frequently tested fact.
❌
Trap 4: LLQ = CBWFQ + strict priority queue — it's not a separate algorithm.
LLQ adds a strict priority queue to CBWFQ. Cisco recommends only voice traffic in the LLQ priority queue. Without LLQ, CBWFQ serves all classes fairly by weight — no strict priority exists, causing jitter for voice.
❌
Trap 5: DiffServ is scalable (hop-by-hop, no signaling). IntServ is not scalable (RSVP, per-flow state).
DiffServ = soft QoS, aggregate classes, modern standard. IntServ = hard QoS, RSVP signaling on every device, per-flow state maintained everywhere — excellent guarantee but collapses at internet scale.
⚠️
Trap 6: DSCP = 6 bits → 64 classes. CoS = 3 bits → 8 levels. IPP = 3 bits → 8 levels.
DSCP (RFC 2474) supersedes IPP (RFC 791). The first 3 bits of DSCP = Class Selector bits = map directly to CoS and IPP for backward compatibility. Class Selectors increment by 8 in DSCP decimal (CS1=8, CS2=16, CS3=24...).
⚠️
Trap 7: EF (Expedited Forwarding) = DSCP 46 = CoS 5 = voice.
Binary 101110 = decimal 46. First 3 bits (101) = CS5 = CoS 5. Cisco recommends EF only for voice traffic. EF = low-loss, low-latency, low-jitter forwarding class.
⚠️
Trap 8: AF drop preference — lower number = less likely dropped.
AF11 = class 1, low drop. AF13 = class 1, high drop. AF43 = class 4, high drop. During congestion avoidance, higher drop preference (y=3) packets are dropped first. Class 4 is the best class; class 1 is the worst.
⚠️
Trap 9: Layer 3 DSCP carries QoS end-to-end. Layer 2 CoS does not.
CoS lives in the 802.1Q tag — stripped at every Layer 3 boundary. DSCP lives in the IP header — persists across all routers. For enterprise-wide QoS, mark at Layer 3 (DSCP). Layer 2 CoS is fine within a single Ethernet segment.
⚠️
Trap 10: Trust boundary = where you trust incoming QoS markings.
Mark as close to the source as possible. IP phones are trusted endpoints — their CoS 5 / DSCP EF markings are accepted. PCs are untrusted — a PC can self-mark with EF to get priority; the access switch must remark/override this.
⚠️
Trap 11: Shaping = egress, queues excess. Policing = ingress, drops excess.
Shaping smooths traffic by buffering excess packets and scheduling them later — needs memory. Policing enforces a rate by immediately dropping anything above the limit — no buffer needed. ISPs use policing to enforce CIR.
⚠️
Trap 12: WRED works for TCP, not UDP.
WRED randomly drops TCP packets to trigger window reduction — preventing queue overflow. UDP has no congestion control mechanism; randomly dropping UDP packets has no effect on the sender's rate. Use LLQ queuing for UDP voice/video protection.
⚠️
Trap 13: CBWFQ tail drop treats all classes equally — it does NOT differentiate.
Tail drop simply discards any packet arriving at a full queue — regardless of class or priority. This is why WRED is used: WRED can selectively drop lower-priority packets before the queue fills, protecting higher-priority traffic.
✅
