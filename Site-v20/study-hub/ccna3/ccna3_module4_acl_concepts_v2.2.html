4.1Purpose of ACLs▾

4.1.1 What Is an ACL?

An ACL (Access Control List) is a series of IOS commands that filter packets based on information in the packet header. By default, a router has no ACLs configured — all traffic is forwarded. When an ACL is applied to an interface, the router performs additional evaluation of every packet passing through that interface.

An ACL contains a sequential list of permit or deny statements called ACEs (Access Control Entries).

ACL TaskExample Policy
Limit network trafficBlock video streaming to reduce bandwidth consumption
Traffic flow controlRestrict routing updates to only known sources
Basic network securityOnly authorized users can access the HR network
Filter by traffic typePermit email (SMTP) but deny Telnet access
Screen hosts for servicesRestrict FTP or HTTP access to specific user groups
QoS classificationIdentify voice traffic for priority forwarding

4.1.2 Packet Filtering — Layer 3 and Layer 4

Packet filtering controls network access by analyzing incoming or outgoing packets and forwarding or discarding them based on criteria. ACL filtering can occur at two layers:

📋 Standard ACL
Filters at Layer 3 only
Matches on: source IPv4 address only

Cannot distinguish between protocols or destination — just where the packet came from.
📋 Extended ACL
Filters at Layer 3 AND Layer 4
Matches on: source IP, destination IP, protocol type, source/destination TCP or UDP ports

Much more granular — can allow web traffic while denying FTP from the same host.

4.1.3 ACL Operation — Inbound and Outbound

ACLs can be applied in two directions on a router interface:

DirectionWhen AppliedBest Used WhenEfficiency
Inbound ACLPackets filtered before routing lookupOne source network on inbound interfaceMore efficient — dropped packets skip routing
Outbound ACLPackets filtered after routing, before exitSame filter for traffic from multiple inbound interfacesLess efficient — routing done before filter
🚨
ACLs do NOT act on packets that originate from the router itself. ACLs only filter transit traffic — packets that enter an interface and are being forwarded through the router. A ping sourced from the router bypasses all ACL checking.

4-Step ACL Processing Logic — Inbound Standard IPv4

🔍 ACL Packet Evaluation — Sequential Top-to-Bottom
1
EXTRACT
Router extracts the source IPv4 address from the packet header
2
COMPARE
Router starts at the top of the ACL and compares the source IP against each ACE in sequential order
✓
MATCH
When a match is found → router executes the permit or deny action → stops immediately — remaining ACEs are NOT checked
✗
NO MATCH
If no ACE matches after checking the entire list → packet is discarded by the implicit deny at the end of every ACL

IMP Implicit Deny — The Hidden Rule

⚠️ Implicit Deny — Present in EVERY ACL
The very last statement of every ACL is an invisible deny any that is never shown in show running-config but is always enforced.

What this means:
→ Any packet that does NOT match any ACE in the ACL is automatically dropped
→ An ACL with only deny statements will drop ALL traffic (the implicit deny catches everything the explicit denies missed)
→ An ACL must have at least one permit statement — otherwise every single packet is denied

Students often forget this and are confused when traffic they didn't intend to deny gets dropped.

4.2Wildcard Masks in ACLs▾

4.2.1 Wildcard Mask Overview — 0 = Match, 1 = Ignore

ACEs use a 32-bit wildcard mask to specify which bits of an address to check. Wildcard masks look like subnet masks but work in reverse:

Subnet Mask
1
Network bit — must match
0
Host bit — variable (don't care)
Wildcard Mask
0
MATCH — check this bit
1
IGNORE — don't care
🎯 THE KEY RULE — EXAM CRITICAL
Wildcard mask: 0 = match (check this bit) · 1 = ignore (skip this bit)
This is the INVERSE of subnet mask logic where 1 = network bits that must match.
Quick memory trick: wildcard 0 = "zero tolerance" (must match) · wildcard 1 = "whatever" (ignore)

4.2.2 Wildcard Mask Types

Match a Single Host — 0.0.0.0
access-list 10 permit 192.168.1.1 0.0.0.0

All 32 bits of the wildcard are 0 → every bit must match exactly → only 192.168.1.1 matches. Use the host keyword as shorthand.

Match a /24 Subnet — 0.0.0.255
access-list 10 permit 192.168.1.0 0.0.0.255

First 24 bits (first 3 octets) must match exactly. Last 8 bits (last octet = 0xFF) are ignored → permits all addresses 192.168.1.0 through 192.168.1.255.

Match a Range of Subnets — 0.0.15.255
access-list 10 permit 192.168.16.0 0.0.15.255

0.0.15.255 in binary: 00000000.00000000.00001111.11111111. The lower 4 bits of the 3rd octet are wildcarded → matches 192.168.16.0/24 through 192.168.31.0/24 (16 networks).

4.2.3 Wildcard Mask Calculation

Formula: wildcard mask = 255.255.255.255 − subnet mask

4.2.4 Wildcard Mask Keywords — host and any

Two IOS keywords simplify the most common wildcard patterns:

host
Replaces 0.0.0.0 wildcard

All 32 bits must match — targets exactly one IPv4 address

any
Replaces 255.255.255.255 wildcard

Ignore all 32 bits — matches any and every IPv4 address

host and any keywords — long form vs shorthand 
! Long form — quad-zero wildcard for exact host match:
R1(config)# access-list 10 permit 192.168.10.10 0.0.0.0

! Shorthand with "host" keyword — identical result:
R1(config)# access-list 10 permit host 192.168.10.10

! Long form — all-ones wildcard to match everything:
R1(config)# access-list 11 permit 0.0.0.0 255.255.255.255

! Shorthand with "any" keyword — identical result:
R1(config)# access-list 11 permit any
4.3Guidelines for ACL Creation▾

4.3.1 Maximum ACLs per Interface

A dual-stacked (IPv4 + IPv6) interface supports a maximum of 4 ACLs:

⬇️ Inbound
IPv4 ACL
⬆️ Outbound
IPv4 ACL
⬇️ Inbound
IPv6 ACL
⬆️ Outbound
IPv6 ACL
💡
A two-interface dual-stacked router could have up to 8 ACLs total (4 per interface). ACLs do NOT have to be configured in both directions — the organization's security policy determines the requirement.

4.3.2 ACL Best Practices

GuidelineBenefit
Base ACLs on organizational security policiesEnsures implementation of established security requirements
Write out what the ACL should do before configuringAvoids inadvertent access problems
Use a text editor to create, edit, and save ACLsCreates a reusable library of configurations
Document ACLs using the remark commandHelps administrators understand the purpose of each ACE
Test ACLs on a development network before productionAvoids costly errors on live networks
remark command — document ACL purpose inline 
! Numbered ACL remark (from global config):
R1(config)# access-list 10 remark Block marketing network from accessing HR servers

! Named ACL remark (from named ACL config mode):
R1(config)# ip access-list standard BLOCK-MARKETING
R1(config-std-nacl)# remark Deny 192.168.5.0 network access to HR
R1(config-std-nacl)# deny 192.168.5.0 0.0.0.255
R1(config-std-nacl)# permit any
4.4Types of IPv4 ACLs▾

4.4.1 Standard vs Extended ACLs

FeatureStandard ACLExtended ACL
Filtering criteriaSource IPv4 address onlySource IP, destination IP, protocol, source/dest ports
OSI LayerLayer 3 onlyLayer 3 AND Layer 4
Numbered range1–99 and 1300–1999100–199 and 2000–2699
Typical placementClose to destinationClose to source
GranularityCoarse — can't control traffic typeFine — filter by specific application or port
Standard ACL vs Extended ACL — syntax comparison 
! Standard ACL — source IP address only:
R1(config)# access-list 10 permit 192.168.10.0 0.0.0.255
! Permits ALL traffic from 192.168.10.0/24 — doesn't matter where it's going
! Implicit deny blocks everything else

! Extended ACL — source + destination + protocol + port:
R1(config)# access-list 100 permit tcp 192.168.10.0 0.0.0.255 any eq www
! Permits ONLY HTTP (port 80) from 192.168.10.0/24 to any destination
! Can be on same router, same network — filters at much finer granularity

4.4.2 Numbered ACLs vs Named ACLs

🔢 Numbered ACLs
Identified by a number:
Standard: 1–99 and 1300–1999
Extended: 100–199 and 2000–2699

Less descriptive — hard to know what ACL 100 does without reading all its ACEs.
🏷️ Named ACLs (Preferred)
Identified by a descriptive name:
FTP-FILTER vs 100
BLOCK-TELNET vs 101

Individual ACEs can be added or deleted by sequence number. Use ip access-list to create.

Named ACL Rules

✅
Names can contain alphanumeric characters (letters and numbers)
✅
Convention: write names in CAPITAL LETTERS (e.g., BLOCK-FTP, PERMIT-WEB)
✅
Names should clearly identify the ACL's purpose
✅
Individual ACEs can be added or deleted within the ACL (unlike older numbered ACLs)
❌
Names cannot contain spaces
❌
Names cannot contain punctuation characters
Named ACL creation — ip access-list command 
! Create a named extended ACL:
R1(config)# ip access-list extended FTP-FILTER
R1(config-ext-nacl)# permit tcp 192.168.10.0 0.0.0.255 any eq ftp
R1(config-ext-nacl)# permit tcp 192.168.10.0 0.0.0.255 any eq ftp-data
R1(config-ext-nacl)# end

! Create a named standard ACL:
R1(config)# ip access-list standard PERMIT-LAN1
R1(config-std-nacl)# remark Permit hosts from LAN1 only
R1(config-std-nacl)# permit 192.168.1.0 0.0.0.255
R1(config-std-nacl)# end

4.4.3 Where to Place ACLs — The Golden Rules

📋 Standard ACL
Place as CLOSE to the DESTINATION as possible

Standard ACLs filter by source address only — they cannot specify what destination the source is going to. Placing a standard ACL near the source would block that source from reaching ALL destinations — not just the intended target.

Typical interface: outbound on the interface directly connected to the destination network

📋 Extended ACL
Place as CLOSE to the SOURCE as possible

Extended ACLs specify both source and destination, so unwanted traffic can be dropped immediately at the source — before it consumes bandwidth traversing the entire network to be dropped at the destination.

Typical interface: inbound on the interface connected to the source network

Constraint: can only place on devices the organization controls

FactorImpact on ACL Placement
Organizational controlCan only place ACLs on devices you administer — may prevent ideal placement
BandwidthFilter at source to prevent unwanted traffic consuming bandwidth across the network
Ease of configurationDestination placement may be simpler but wastes bandwidth; multiple extended ACLs at each source router saves bandwidth but is complex

4.4.4 Standard ACL Placement Example

Goal: Prevent 192.168.10.0/24 from reaching 192.168.30.0/24. Topology: R1 (.10 LAN) → R2 → R3 (.30 LAN, .31 LAN). Standard ACL must go on R3 (closest to destination).

Interface OptionEffectCorrect?
R3 S0/1/1 inboundWould block .10 network from reaching both .30 AND .31 — too broad❌ Wrong
R3 G0/0/0 outboundOnly blocks .10 traffic going to .30 LAN; .10 can still reach .31 LAN normally✅ Correct
✅
Rule confirmed: Standard ACL on R3 outbound G0/0/0 (connected to .30 network). The .10 network is still able to reach the .31 network — only the .30 LAN is blocked. The ACL is as close to the destination as possible without affecting other reachable networks.

4.4.5 Extended ACL Placement Example

Goal: Company A (192.168.11.0/24 via R1) wants to deny Telnet and FTP to Company B (192.168.30.0/24 via R3). Company A controls R1 only — not R3. Extended ACL must go on R1 (closest controllable device to source).

Interface OptionEffectCorrect?
R1 S0/1/0 outboundWould process ALL traffic leaving R1, including 192.168.10.0/24 (not just .11)❌ Too broad
R1 G0/0/1 inboundOnly processes packets entering from 192.168.11.0/24 — precise filter, minimal overhead✅ Correct
✅
Rule confirmed: Extended ACL inbound on R1 G0/0/1 (connected to .11 network). Only .11 traffic is filtered. Traffic from .10 network is unaffected. Unwanted Telnet/FTP is dropped at R1 immediately — it never crosses the network to R3.
🎯Common Exam Traps — Module 4▾
❌
Trap 1: Implicit deny — every ACL ends with a hidden "deny any."
This invisible statement is never shown in show running-config but always enforced. Any packet that doesn't match any ACE is automatically dropped. An ACL needs at least one permit statement — otherwise ALL traffic is denied. Students are often caught by accidentally blocking valid traffic they forgot to explicitly permit.
❌
Trap 2: First match wins — processing stops immediately on match.
Once a packet matches an ACE, the router executes that permit/deny and skips all remaining ACEs. Order matters enormously. Place more specific ACEs before more general ones. A broadly-written permit early in the ACL can accidentally allow traffic a later deny was meant to block.
❌
Trap 3: Wildcard 0 = match, wildcard 1 = ignore.
This is the inverse of subnet mask logic. Students frequently mix these up. Subnet mask: 1 = network (must match), 0 = host (variable). Wildcard mask: 0 = must match, 1 = ignore. Quick formula: wildcard = 255.255.255.255 − subnet mask.
❌
Trap 4: ACLs do NOT act on packets originating from the router itself.
Only transit traffic is filtered by ACLs. A ping sourced from the router bypasses all ACL checking. This often causes confusion when testing ACLs with router-generated pings — the test may pass even when the ACL would block user traffic.
❌
Trap 5: Standard ACL near destination — Extended ACL near source.
Standard ACLs filter by source address only — placing them near the source blocks that source from ALL destinations, not just the intended one. Extended ACLs know both source and destination — placing them near the source drops unwanted traffic early, before it wastes bandwidth crossing the network.
⚠️
Trap 6: ACL number ranges — know all four ranges.
Standard: 1–99 AND 1300–1999. Extended: 100–199 AND 2000–2699. Students often only remember the primary range and forget the expanded ranges. Both are valid and may appear in exam questions.
⚠️
Trap 7: host = 0.0.0.0 wildcard. any = 255.255.255.255 wildcard.
host 192.168.1.1 is identical to 192.168.1.1 0.0.0.0. any is identical to 0.0.0.0 255.255.255.255. Know both the keyword form and the explicit wildcard form — questions may present either.
⚠️
Trap 8: Named ACLs are the preferred method — no spaces, no punctuation.
Named ACLs are more descriptive and allow individual ACE deletion. Names must be alphanumeric with no spaces or punctuation. Convention is CAPITAL LETTERS. Use ip access-list standard|extended NAME to create them.
⚠️
Trap 9: Maximum 4 ACLs per dual-stacked interface.
One inbound IPv4, one outbound IPv4, one inbound IPv6, one outbound IPv6. This is a hard limit. ACLs don't need to be configured in both directions — depends on security policy.
⚠️
Trap 10: Extended ACL placement is constrained by organizational control.
Even though the rule is "extended ACL as close to source as possible," you can only place ACLs on devices your organization controls. If the source network is outside your control, place the ACL on the closest device you do control.
⚠️
Trap 11: Inbound ACL is more efficient than outbound.
Inbound: packet dropped before routing lookup — saves processing overhead. Outbound: packet survives routing first, then gets dropped — less efficient. Both are valid; the efficiency difference matters for exam questions about which type to prefer when both would work.
⚠️
Trap 12: An ACL with only deny statements drops ALL traffic.
Explicit deny ACEs catch specific traffic, and the implicit deny at the end catches everything else. The net result: 100% of traffic is dropped. Always include at least one permit ACE — typically permit any at the end if the goal is to deny specific traffic and permit everything else.
✅
Module 4 quick-reference summary:

ACL = series of ACEs (permit/deny) applied to an interface
Processing: top-to-bottom · first match wins · implicit deny any at end
ACLs do NOT filter: traffic originated by the router itself
Wildcard mask: 0=match · 1=ignore · formula: 255.255.255.255 − subnet mask
Keywords: host = 0.0.0.0 · any = 255.255.255.255
Standard ACL: source IP only · L3 · numbers 1–99, 1300–1999 · near DESTINATION
Extended ACL: src+dst+proto+port · L3+L4 · 100–199, 2000–2699 · near SOURCE
Named ACL: preferred · CAPITAL LETTERS · no spaces/punctuation · ip access-list
Max per interface: 4 (in/out × IPv4/IPv6)
Inbound: filtered before routing (more efficient)
Outbound: filtered after routing
