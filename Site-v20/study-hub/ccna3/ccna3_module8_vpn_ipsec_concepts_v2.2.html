8.1VPN Technology▾

8.1.1 What Is a VPN?

A VPN is:

  • Virtual — carries information as if on a private network, but transported over a public network (internet)
  • Private — traffic is encrypted to keep data confidential while crossing the public network

VPN Evolution

TechnologyEncryption?Description
GRE❌ NoEarly Cisco tunneling protocol. Encapsulates any Layer 3 protocol including multicast/broadcast. Creates virtual point-to-point link. No confidentiality.
IPsec✅ YesIETF standard. Encrypts and authenticates IP packets. Most common VPN protocol today. Supports only unicast natively.
SSL/TLS✅ YesUsed for clientless (browser-based) and client-based remote access VPNs. Uses PKI and digital certificates.
🚨
GRE does NOT provide encryption. GRE is a tunneling protocol only — it creates a tunnel but does not secure it. To protect GRE traffic, it must be wrapped inside IPsec. GRE over IPsec = tunnel + security.

Key VPN Devices

  • Cisco ASA (Adaptive Security Appliance) — standalone security device combining firewall, VPN concentrator, and IPS
  • VPN-enabled router — SOHO router providing VPN connectivity back to corporate
  • Cisco AnyConnect — client software for remote workers to establish SSL/IPsec VPN connections

8.1.2 VPN Benefits

BenefitDescription
Cost SavingsUses internet instead of expensive dedicated WAN links; increases remote connection bandwidth at lower cost
SecurityAdvanced encryption and authentication protect data from unauthorized access in transit
ScalabilityEasy to add new remote users via internet — no significant infrastructure changes needed
CompatibilityWorks across a wide variety of WAN and broadband technologies (DSL, cable, cellular, etc.)

8.1.3 Site-to-Site vs Remote-Access VPNs

🏢 Site-to-Site VPN
Gateway-to-Gateway · Permanent
  • VPN gateways pre-configured at each site
  • Traffic encrypted only between gateways
  • Internal hosts unaware VPN exists — transparent
  • Hosts send/receive normal TCP/IP
  • Gateway = router or firewall (e.g., Cisco ASA)
  • Used to connect branch offices to HQ
💻 Remote-Access VPN
User-Initiated · On-Demand
  • Dynamically created when user needs it
  • Single client ↔ VPN gateway
  • User must initiate the connection
  • Can use IPsec or SSL
  • Clientless: browser + HTTPS only
  • Client-based: AnyConnect software installed

8.2.2 SSL VPNs — IPsec vs SSL Comparison

When a client negotiates an SSL VPN, it actually uses TLS (Transport Layer Security) — the modern successor to SSL. The terms are used interchangeably. SSL uses PKI and digital certificates to authenticate peers.

8.2.3 Site-to-Site IPsec VPNs

  • Connects networks across an untrusted network (internet)
  • End hosts send/receive normal unencrypted TCP/IP — VPN gateway does all the work
  • Gateway encapsulates and encrypts outbound traffic → sends through VPN tunnel
  • Receiving gateway decrypts, strips headers, forwards to destination host on LAN
  • Secured using IPsec; gateway = router or firewall (e.g., Cisco ASA)

8.2.4 GRE over IPsec

The problem: Standard IPsec supports unicast traffic only. Routing protocols (OSPF, EIGRP) use multicast — they cannot run over plain IPsec tunnels.

The solution: GRE wraps the multicast routing packet (making it unicast), then IPsec encrypts the GRE packet.

📦 Three-Layer GRE over IPsec Encapsulation
Passenger
Layer 1
The original data packet — e.g., an OSPF Hello (multicast routing update). This is what needs to get from site A to site B.
Carrier (GRE)
Layer 2
GRE encapsulates the OSPF packet and adds a GRE header. The multicast becomes wrapped in a unicast GRE packet — now IPsec can handle it.
Transport (IPsec)
Layer 3
IPsec encrypts the GRE packet and adds IPsec headers. The result is a fully encrypted, routable unicast packet traversing the internet.
🎯 GRE over IPsec FLOW
OSPF packet (multicast) → GRE wraps it (now unicast) → IPsec encrypts it → sent over internet

Without GRE: IPsec cannot carry OSPF/EIGRP multicast → routing protocols fail over the VPN
With GRE over IPsec: routing protocols work normally across the encrypted tunnel

8.2.5 DMVPN — Dynamic Multipoint VPN

  • Cisco proprietary — software solution for building scalable VPN meshes easily
  • Solves the problem of static site-to-site configs requiring manual configuration for every pair of sites
  • Uses hub-and-spoke base config that dynamically enables full mesh communication
  • Relies on IPsec for secure transport over public networks
  • Uses mGRE (Multipoint GRE) — a single GRE interface dynamically supports multiple IPsec tunnels
  • Adding a new branch site: no reconfiguration needed on the hub router
  • Spokes can establish direct spoke-to-spoke tunnels without traversing the hub
💡
DMVPN combines hub-and-spoke simplicity with full-mesh performance. Ideal for large enterprises with many branch offices where static IPsec site-to-site configs would be unmanageable.

8.2.6 IPsec Virtual Tunnel Interface (VTI)

  • Simplifies IPsec configuration — applies IPsec to a virtual interface rather than static crypto maps on physical interfaces
  • Supports both unicast AND multicast encrypted traffic natively
  • Routing protocols work directly — no need for GRE over IPsec
  • Can be configured between sites or in hub-and-spoke topology
✅
IPsec VTI vs GRE over IPsec: VTI natively supports multicast — so routing protocols (OSPF, EIGRP) work without needing GRE. GRE over IPsec is an older approach that adds GRE as a workaround for the same problem.

8.2.7 Service Provider MPLS VPNs

MPLS provides secure isolation of customer traffic through label switching — different customers cannot see each other's traffic even on shared infrastructure.

8.3IPsec Framework▾

8.3.2 IPsec — Four Security Functions

IPsec is an IETF standard framework (RFC 2401–2412) that protects and authenticates IP packets from Layer 4 through Layer 7. It is a framework — not bound to specific algorithms. Peers negotiate a Security Association (SA) to agree on which algorithms to use.

🔒 IPsec Framework — Four Building Blocks
1 · Confidentiality
Encryption prevents reading packet contents if intercepted. Options: DES, 3DES, AES (recommended), SEAL
2 · Integrity
Hashing (HMAC) ensures packets were not altered in transit. Options: MD5, SHA-1, SHA-256 (recommended minimum)
3 · Authentication
IKE (Internet Key Exchange) authenticates VPN peers. Options: PSK (pre-shared key) or RSA (digital certificates)
4 · Diffie-Hellman
DH key exchange — two peers create a shared secret key over an insecure channel without transmitting the key itself
⚙️ IPsec Framework — Full Options Table
Protocol
AH (Authentication Header) — auth only, no encryption
ESP (Encapsulating Security Payload) — auth + encryption ← preferred
Confidentiality
DES (56-bit, weak) · 3DES (3×56-bit) · AES-128/192/256 (recommended) · SEAL (160-bit stream)
Integrity
HMAC-MD5 (128-bit) · HMAC-SHA-1 (160-bit, legacy) · SHA-256+ (recommended minimum)
Authentication
PSK (pre-shared key, simple but doesn't scale) · RSA (digital certs, scales well)
Key Exchange
DH groups 1/2/5 (deprecated ❌) · Groups 14/15/16 (2048–4096-bit, recommended) · Groups 19/20/21/24 (ECC, preferred)

8.3.3 AH vs ESP — IPsec Protocol Encapsulation

AH — Authentication Header
❌ NO encryption
  • Provides data authentication and integrity ONLY
  • Does NOT encrypt — all text transported in clear
  • Use when confidentiality is not required or not permitted
  • Cannot traverse NAT — AH breaks when NAT changes IP headers (integrity check fails)
  • AH+ESP combination also fails through NAT
  • Rarely used in modern deployments
ESP — Encapsulating Security Payload
✅ Encryption + Auth
  • Provides confidentiality (encryption) AND authentication
  • Encrypts the IP packet payload
  • Authenticates inner IP packet and ESP header
  • At minimum: either encryption OR authentication must be selected
  • Can traverse NAT (with NAT-Traversal/NAT-T)
  • Most commonly used — standard for modern VPNs
🎯 AH vs ESP — THE KEY DISTINCTION
AH = Authentication Header = integrity + origin auth ONLY. No encryption. Breaks through NAT.
ESP = Encapsulating Security Payload = encryption + authentication. Works through NAT (with NAT-T).

In almost all real deployments: use ESP. AH is rarely used because it provides no confidentiality.

8.3.4 Confidentiality — Encryption Algorithms

All are symmetric key cryptosystems — the same key is used for both encryption and decryption:

DES
56-bit
Legacy — do not use. Easily broken with modern hardware. Retained for backward compatibility only.
3DES
3×56-bit
Applies DES three times with three independent keys per 64-bit block. Much stronger than DES but less efficient than AES.
AES
128/192/256-bit
Recommended standard. Strongest and most computationally efficient. AES-256 could take ~10 quintillion years to brute-force.
SEAL
160-bit
Stream cipher — encrypts data continuously rather than in fixed blocks. Lower CPU impact than block ciphers.
💡
Key length determines brute-force resistance: A 64-bit key may take ~1 year to break; a 128-bit key could take ~10 quintillion years with current technology. Always use AES-128 minimum; AES-256 for sensitive data.

8.3.5 Integrity — HMAC Algorithms

HMAC (Hashed Message Authentication Code) guarantees data integrity — proves the packet was not altered in transit. A shared secret key is combined with the message before hashing:

AlgorithmKey SizeHash OutputStatus
HMAC-MD5128-bit shared secret128-bit hashAdequate but SHA preferred; still widely used
HMAC-SHA-1160-bit shared secret160-bit hashCisco rates as legacy; use SHA-256 minimum
HMAC-SHA-256256-bit shared secret256-bit hash✅ Recommended minimum — use this or higher

MethodPSK (Pre-Shared Key)RSA (Digital Certificates)

8.3.7 Key Exchange — Diffie-Hellman (DH) Groups

DH allows two peers to establish a shared secret key over an insecure public channel — without transmitting the key itself. This shared key is then used for symmetric encryption.

Groups 1, 2, 5
Deprecated ❌
768, 1024, 1536-bit keys. Do NOT use — considered cryptographically weak. No longer secure against modern attacks.
Groups 14, 15, 16
Recommended ✅
2048, 3072, 4096-bit keys. Recommended until 2030. Use with AES-128+ encryption.
Groups 19, 20, 21
ECC Preferred
256, 384, 521-bit ECC keys. Uses Elliptic Curve Cryptography — faster key generation at equivalent security. Preferred for next-gen encryption.
Group 24
Next-Gen ⭐
2048-bit ECC. Preferred next-generation encryption choice. Use with AES-256.
⚠️
DH group strength must match encryption strength:
AES-128 encryption → use DH Group 14, 19, 20, or 24
AES-256 encryption → use DH Group 21 or 24
Never pair strong encryption with a weak DH group — the DH group becomes the weakest link.
🎯Common Exam Traps — Module 8▾
❌
Trap 1: GRE does NOT encrypt — it only tunnels.
GRE is a tunneling protocol, not a security protocol. It encapsulates packets (including multicast and broadcast) but provides zero confidentiality. To secure GRE, wrap it inside IPsec. GRE alone = unencrypted tunnel. GRE over IPsec = encrypted tunnel that supports routing protocols.
❌
Trap 2: IPsec alone cannot carry multicast — that's exactly why GRE over IPsec exists.
Routing protocols (OSPF, EIGRP) use multicast addresses. Plain IPsec only supports unicast. GRE wraps the multicast routing packet (making it unicast), then IPsec encrypts the GRE packet. Passenger = routing protocol, Carrier = GRE, Transport = IPsec.
❌
Trap 3: AH = authentication only, no encryption. ESP = encryption + authentication.
AH (Authentication Header) provides integrity and origin authentication — but zero confidentiality. ESP (Encapsulating Security Payload) provides both encryption and authentication. AH breaks when traversing NAT because NAT changes IP addresses and AH includes those in its integrity check. Use ESP.
❌
Trap 4: Site-to-site VPN — internal hosts are completely unaware the VPN exists.
The VPN gateways (routers or firewalls) handle all encryption and decryption transparently. Internal hosts send and receive normal, unencrypted TCP/IP to the gateway. The gateway then encrypts before sending to the internet and decrypts on the return. Hosts never see VPN headers.
❌
Trap 5: DH groups 1, 2, and 5 are deprecated — do NOT use them.
Groups 1/2/5 (768, 1024, 1536-bit) are no longer cryptographically secure. Cisco recommends Groups 14/15/16 (2048–4096-bit) until 2030, and Groups 19/20/21/24 (ECC) as the preferred next-generation option. Group 24 is the top recommended for next-gen encryption.
⚠️
Trap 6: SSL VPN actually uses TLS — they're the same thing in Cisco context.
TLS is the modern, more secure version of SSL. Cisco curriculum and exams use "SSL VPN" and "TLS VPN" interchangeably. SSL VPNs use PKI and digital certificates to authenticate peers. When you see "SSL VPN," think TLS in actual implementation.
⚠️
Trap 7: Clientless VPN = just a browser. Client-based VPN = software required.
Clientless VPN uses HTTPS in a standard web browser — nothing needs to be installed. Client-based VPN (e.g., Cisco AnyConnect) requires software installed on the endpoint. Client-based can encrypt with IPsec or SSL; clientless uses SSL/HTTPS only.
⚠️
Trap 8: IPsec is better for security depth; SSL is better for ease of deployment.
IPsec supports all IP applications; SSL only supports web-based apps and file sharing. IPsec requires a pre-installed client; SSL needs only a browser. IPsec offers stronger authentication (two-way). Organizations deploy BOTH depending on the use case.
⚠️
Trap 9: DMVPN uses mGRE (Multipoint GRE) — one interface, many tunnels.
DMVPN is Cisco proprietary. It uses a single mGRE interface that dynamically builds multiple IPsec tunnels. The hub router needs no reconfiguration when new spoke sites are added. Spokes can also build direct spoke-to-spoke tunnels without going through the hub.
⚠️
Trap 10: IPsec VTI natively supports multicast — no GRE wrapper needed.
Unlike plain IPsec crypto maps, IPsec VTI applies IPsec to a virtual interface and supports both unicast and multicast traffic natively. This means OSPF and EIGRP work directly over VTI without needing the GRE over IPsec workaround.
⚠️
Trap 11: Layer 3 MPLS VPN = SP participates in routing. Layer 2 MPLS VPN = SP does not.
L3 MPLS VPN: service provider peers with customer CE routers and redistributes routes across the MPLS backbone (using MP-BGP). L2 MPLS VPN (VPLS): SP emulates an Ethernet LAN segment; customer CE routers handle all routing and appear to be on the same multiaccess network.
⚠️
Trap 12: PSK does not scale — RSA digital certificates do.
PSK requires every peer to manually know every other peer's secret key. For 100 sites, that's a massive key management problem. RSA uses digital certificates distributed via PKI — adding a new site just requires issuing a certificate. For large deployments, always use RSA.
✅
